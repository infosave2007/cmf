# Qwen3.8-27B Turbo on cortiq

*Languages: **English** · [Русский](QWEN38_TURBO.ru.md) · [中文](QWEN38_TURBO.zh.md)*

[The turbo file](https://huggingface.co/infosave/Qwen3.8-27B-Turbo-cmf) holds the 4-bit weights of
Qwen3.8-27B under a header that keeps device memory in place on long prompts. Prompts under 8192 tokens
run exact attention, as in the [standard file](https://huggingface.co/infosave/Qwen3.8-27B-cmf).

## Run

```bash
cargo install cortiq-cli
hf download infosave/Qwen3.8-27B-Turbo-cmf qwen38-27b-turbo.cmf --local-dir .
cortiq run qwen38-27b-turbo.cmf --prompt-file report.txt --greedy --no-think
cortiq run qwen38-27b-turbo.cmf --prompt-file report.txt --greedy --no-think --o1-spill /mnt/ssd/cortiq
```

| option | meaning |
|---|---|
| `--o1-spill DIR` | a long prompt's rows in files in `DIR`, also `CMF_O1_SPILL` |
| `--prompt-file FILE` | a prompt longer than a command line holds |
| `CMF_O1_PREFIX_MAX=N` | seal at `N` rows instead of the choice for the card |
| `CMF_O1=off` | the plain model, with exact attention at any length |
| `CMF_O1_SPEC=0` | no drafts over the far field |
| `CMF_O1_STAGES=0` | the far field's attention in one long thread per head |
| `CMF_WGPU_BLOCK_MB=N` | the block the Vulkan allocator shares among small buffers, 16 MiB by default |

## What happens to a long prompt

![A long prompt on a small card](https://huggingface.co/infosave/Qwen3.8-27B-Turbo-cmf/resolve/main/assets/ceiling_en.png)

1. The first rows are read exactly on the batch graph: 8192 of them, 4096 where the card's budget has no
   room for more (`o1_seal_for_card`).
2. Later chunks read a far field built over the rows so far. Their queries, keys and values leave the card
   through host-visible staging, for RAM or files (`O1Archive`).
3. Before the last 512 rows the exact rows are chosen among all the stored rows, and the far field is
   built anew from them, one layer at a time, so memory never holds two layers' rows.
4. The last rows and every decoded token read the sinks, the exact rows, the window of 1800 and 32 landmarks
   per head. The state has a fixed size.

The order in step 3 matters: a question carries what it found in the text on to the answer, so it has to
read the exact fact itself. Choosing after the question's rows finds the fact's rows and still answers 1
time in 8.

**Exact rows.** For each KV head of each full layer, two numbers per row: how far its key lies from the span
of the landmarks, and its value's norm. Each becomes a rank within the prompt, and a linear fit over the 128
ranks scores the row, with no word lists. Over planted facts, a fact's rows land in the top 0.22 % of a
prompt on average, and in the top 0.96 % at worst, on prompts the fit did not see.

**Short threads.** A workgroup stays on one SM of an NVIDIA card, so one 256-lane workgroup per head leaves
the card idle. `o1_stages` takes the arithmetic apart: near scores with a thread per key, landmark scores,
the largest score, the far part per head, the weights, the value sum in pieces, and the pieces added. A sealed
token went from 31.5 to 56 tok/s, and a verify of five rows from 57 to 41 ms.

**Drafts.** A verify chunk attends without moving the far field, and its keys and values wait on the card.
`o1_spec_commit` then moves the state over the accepted rows only. The draft head warms on the prompt's last
rows. Greedy text is identical with drafts and without.

**Device memory.** Weights of 33 to 64 MiB used to take a 64 MiB block each, so 12.6 GB of weights held 16.6 GB
of the card. Blocks of 16 MiB take this back for every model on Vulkan, at the same speed.

## On a Mac

The machine is a MacBook Air M4 with 24 GB: no fan, so long runs slow down as it heats, and the base M4's memory
bus, 120 GB/s by Apple's figure. It reads the 13.6 GB of weights a token takes at 92 to 95 GB/s, the speed of that
bus: 6.4 tok/s without drafts. An M4 Pro's bus is rated at 273 GB/s and an M4 Max's at up to 546 GB/s; those
machines were not measured. Drafts move the rest, on by default over a q4tp file (`CMF_GRAPH_SPEC=0` turns them off;
cortiq 0.8.63 and earlier need `CMF_GRAPH_SPEC=1`), and the Neural Engine, a switch that is off by default.

**Drafts.** The draft head proposes tokens and one pass over the weights checks them, so a pass
gives more than one token. MacBook Air M4, greedy, 220 tokens, the same text with drafts and without:

| answer | without drafts, tok/s | with drafts, tok/s |
|---|---:|---:|
| an essay | 6.4 | **10.1** |
| an explanation in Russian | 6.4 | **10.7** |
| a Rust function with tests | 6.4 | **12.1** |
| quotes from the prompt | 6.4 | **15.0** |
| an edit of the prompt's code | 6.4 | **20.5** |

After a prompt of 3 600 tokens: 6.0 → 8.3 tok/s. Three things give it. A check of two or three rows runs on a batched
matvec that reads the weights as fast as one row does, 95.7 and 82.4 GB/s against 60 to 67 for the GEMM, and its
logits equal the plain path's to four decimal places. The chain's depth follows how often each of its drafts holds:
two drafts on most text, where a fixed seven gave an essay nothing. Where an answer repeats a stretch of the prompt or
of itself, the tokens that followed that stretch continue the chain up to seven drafts (`CMF_SPEC_LOOKUP=0` turns this
off). Past the seal they pay too: OrcaCyber-Nano-1.0 (a Qwen3.8-27B derivative, the same shapes), 16 000 tokens read
with the Neural Engine, decodes at 8.2 tok/s with drafts against a plain token's 5.8. That needs the Neural Engine's
surfaces released once the prompt is read: kept, they pushed the weight map out of a 24 GB Mac and decode fell to 6.4.

**The Neural Engine**, `CMF_ANE=1`. It reads a prompt's chunks beside the GPU: every layer's FFN, a GDN mixer's `z`
and an attention layer's `q`. First token at 3 600 tokens 73.9 → 28.3 s, the same text; at 10 000 tokens with
`--o1-spill` 217.6 → 113.5 s with a peak footprint of 3.4 GB. Decode stays on the GPU.

`scripts/dory/q27_spec_decode.sh` runs the table; `JOURNAL_Q27_MAC_DECODE_2026-11-06.md` and
`JOURNAL_Q27_ANE_2026-11-05.md` keep the logs.

## Building a turbo file

```bash
python3 scripts/dory/router/q27_feat.py cortiq qwen38-27b-q4tp.cmf tokenizer.json wiki_test.txt keep27.bin
cortiq far-turbo qwen38-27b-q4tp.cmf qwen38-27b-turbo.cmf --exact-weights keep27.bin
```

`scripts/dory/router/keep27.bin` holds the fit for Qwen3.8-27B. `--o1 m,w,sink`, `--seal` and `--exact-rows` set
the field; the window, sinks and exact rows have to fit 2052 keys. Other models with full-attention layers take the
same command with a fit of their own; only Qwen3.8-27B has been measured.

`scripts/dory/q27_final.sh` and `q27_quality.sh` run the tables above, `q27_figures.py` draws the figures, and
`JOURNAL_Q27_TURBO_2026-11-05.md` keeps the log of what was tried.

## What stays out

- The far field runs on Vulkan, DX12 and Metal (`gpu_metal/o1c.rs`). On the CPU the file runs as the standard one. It was
  measured on an NVIDIA card and an M4.
- Past the seal the text is approximate: what lies far back fades, apart from the rows kept exact. The fit saw planted
  facts, and other kinds of important text were not tested.
- Rows that arrive after a prompt ends stay in the window or go to the far field. A turn that diverges from a sealed
  conversation reads the whole prompt again.
- On Vulkan, drafts need greedy decoding without penalties.
- A generation that starts below the seal stays exact, and its memory grows with every token.

# Spark-X2.6-4B on Metal (0.8.43)

Measurements behind the 0.8.43 Metal changes for
[Spark-X2.6-4B](https://huggingface.co/infosave/Spark-X2.6-4B-cmf) (36 layers:
9 full + 27 sliding-window 512, hidden 2560, FFN 10240 with exact GELU, 16 Q
heads × 256, 4 KV heads, tied head). Stand: Mac mini M4, 10-core GPU, 24 GB.

A decode token reads the whole weight set once: 4.12 GB for the q8_2f file,
2.14 GB for q4tp. The M4's matvecs reach 85–91 GB/s here, so the roofs are
~23 tok/s (q8_2f) and ~40 tok/s (q4tp).

## Method

The M4 drifts by ±20 % between processes (one GEMM process measured 2.90 and
2.25 TFLOP/s back to back), and desktop rendering kept its GPU 30–40 % busy
during much of this work. Every kept change was decided by one of:

- interleaved processes, A, B, A, B (`cortiq bench --core --ignore-eos`);
- an in-process A/B whose arms alternate per token (`CMF_METAL_AB=a/b`), the
  pair ratio of the GPU time per token;
- ratios inside one profiled run (`CMF_CHUNK_PROF=1`) or one bench process.

Stage costs of a decode token come from `CMF_METAL_AB=mcfr/mcfrx` with
`CMF_METAL_SKIP=<letters>`: the `x` arm drops the named stages (a attend,
p RoPE, n norms, q QKV, o O, g gate/up, d down, h head), tokens alternate.

## Results

| q8_2f, interleaved pairs | 0.8.42 | 0.8.43 |
|---|---:|---:|
| prefill, 1000-token prompt | 112–118 tok/s | 197–216 tok/s |
| prefill, 41-token prompt | 86–99 tok/s | 202–204 tok/s |
| 20–30-token prompt (`run`) | 0.85–1.29 s | 0.16–0.20 s |
| `serve` chat turn 2, 2.3k history, 65 new tokens | 11.3 s | 0.58 s |
| `serve` turn 2 after a 700-token answer | 16.7 s | 4.7 s |

| decode, in-process A/B, GPU time per token | short | depth 1000 |
|---|---:|---:|
| q4tp | 0.862× | 0.882× |
| q8_2f | 0.905× | 0.924× |

Decode on the quiet machine: q8_2f 16–19 tok/s (17.1 at depth 4k, 15.6 at
8k); q4tp ~30 tok/s with the desktop load, 32 before the attend change on a
quiet GPU. Prefill at depth: q8_2f 261 tok/s at 4000 tokens, 215 at 8000.

Quality, `cortiq ppl --tokens 4096` (wikitext-2, BOS in front):

| file | CPU | Metal 0.8.42 | Metal 0.8.43 |
|---|---:|---:|---:|
| q8_2f | 10.717 | 10.717 | 10.716 |
| q4tp | 11.758 | 11.765 | 11.765 |

Greedy outputs of 0.8.43 equal 0.8.42's on every prompt checked (both files);
the Metal and CPU paths diverge after some tokens on some prompts as before
(float order). A chat turn with prefix rollback equals a fresh prefill
character for character (48- and 700-token answers).

## Changes

1. **Dense q8_2f in the chunk prefill graph.** `chunk_run_gpu` refused every
   dense q8_2f layer: the chunk FFN had no x·col staging. gate/up now read
   `n·col` staged like q/k/v, down's field scales the GELU rows in place
   (`ChunkLayer::ffn_col`). Exact-GELU FFNs only: the SiLU down GEMM fuses its
   activation into the X load and has no field.
2. **Rollback reuse across chat turns.** `rollback_prefix_len` keeps the
   longest common prefix when every layer can drop its rows exactly; the
   sliding tail trim is anchored at the turn's prompt end
   (`trim_window_anchored`), ~216 KB per answer token in the 27 sliding layers
   until the next turn. `CMF_KV_ROLLBACK=0` restores extension-only reuse.
3. **Short prompts.** `Pipeline::chunk_min_rows`: 8 for spark2_5, 32 for every
   other model (`CMF_CHUNK_MIN_B`). Prompts of 2–7 tokens keep their
   per-position path (47–102 ms), from 8 tokens the chunk graph (~105 ms) beats
   the host walk (0.5–1.2 s).
4. **Decode attend.** Stage attribution put the attend at 19 % of a q4tp token
   at short context (6.4 ms) and 12.7 ms at depth 3100. Standalone (16 Q / 4 KV
   heads, width 256): 150 positions per-head 106 µs vs split-K in 32-row blocks
   30 µs; 512 positions split-K 128-row blocks 247 µs → 32-row 53 µs. The Spark
   plan sets `set_attend_blk(1, 32)`; `CMF_GQA_BLK`/`CMF_GQA_BLKSZ` override.
5. **Chunk attention P·V GEMM** (`mul_mm_f32nn`): K steps of 32 with packed
   float4 loads instead of 16 with bounds-checked scalars, the same 8×8 blocks
   in the same k order. Deepest 4k chunk, normalized to the gate/up GEMM of the
   same run: 0.54 → 0.40.
6. **q4tp prefill GEMM** (`q4tp_mul_mm`): one 8-byte nibble load instead of
   eight byte loads, the activation boost (a power of two) folded into the
   group scale. Rate against the q8 GEMM, alternating rounds: gate 0.86 → 0.885,
   down 0.86 → 0.93.

## Measured and rejected

- Wider q8_2f decode matvecs (16- and 8-byte loads, 1–8 rows per simdgroup):
  within ±2 % of `q8f_matvec_r4`.
- Fused q8_2f decode (gate|up|GELU in one dispatch, O and down residual in the
  epilogues, bit-exact): in-process 0.992 / 1.001.
- A 64×64 C tile for the q8 GEMM: neutral to −10 % against the 64×32 tile
  (2.3–3.1 TFLOP/s at b = 512).
- Vector loads in the scores GEMM (`mul_mm_f32nt`): no change.
- q4tp decode matvec with 2/4/8 rows per simdgroup: within noise once the GPU
  clock has ramped (the first kernel of a process measures low).

## Where the time goes now

- Decode: weight matvecs are ~83–85 % of a token. A smaller file is the lever.
- Prefill, deepest 4k chunk: weight GEMMs 64 %, attention 34 % (scores GEMM
  ~1 TFLOP/s). A fused causal flash attend is the next step for long prompts;
  at head width 256 it keeps 8 query rows per simdgroup, which caps it near
  1.6 TFLOP/s.

# Embryo-O1 в рантайме: как запускать, что измерять, что не поддержано

Статус: 24.09.2026, по коду `crates/cortiq-engine` / `crates/cortiq-cli` (контракт оператора —
`docs/EMBRYO_BOUNDED_ANCHOR.md`). Файл Embryo-O1 — это `.cmf` с
`LayerType::BoundedAttention` + `arch.anchor_core = {kind:"swa_sink_v1", window, sink, …}`
и миксерами `linear_core` вида `vmf_phase` (Embryo-0, вариант A) либо
`gated_delta_net` (вариант B). Состояние потока — запись фиксированного
размера, выводимая из заголовка; ничего в пайплайне не растёт с диалогом.

## 1. Что показывает `cortiq info`

```
cortiq info bounded-500-f32.cmf
  Layers:      8 (0 full / 1 bounded / 7 linear)
  Anchor:      swa_sink_v1 window=128 sink=4 rope=relative_in_window sink_scores=nope train_windows=[64, 128] far=null
               ring per layer: 262144 B (2 kv_heads x 128 x 128 f32, K+V)
  State/seq:   2129408 B fixed (262144 B bounded rings + 1867264 B recurrent) — O(1) in context
```

`State/seq` = `per_sequence_state_bytes()` (`loader.rs`): кольца якорей
`2·kvh·W·hd·4` на bounded-слой + рекуррентная запись миксера
(`vmf`: `heads·2·nphase·dv + (k−1)·hidden`; `gated_delta_net`:
`GdnCfg::state_len() = (kk−1)·c_dim + nv·dk·dv`). Вариант B (6×GDN 4×128×128 +
2 якоря): 1 683 456 + 524 288 = **2 207 744 B**. `growing layers 0` — ни один слой
не хранит ничего на позицию. `cortiq info <f> --tensors <prefix>` печатает dtype
каждого тензора (нужно для аудита q4tp, §7).

## 2. CPU-путь (по умолчанию; единственный на macOS)

```
CMF_GPU=0 cortiq run bounded-500-f32.cmf --prompt "…"
CMF_GPU=0 cortiq ppl bounded-500-f32.cmf --file heldout-en.txt --windows 8 --window-len 512
CMF_GPU=0 cortiq ppl bounded-500-f32.cmf --file heldout-en.txt --tokens 16384
```

- Оператор якоря — `bounded.rs` (`BoundedState::attend`, кольцо сырых k̂/v, поворот
  запроса на Δ по таблице `BoundedRope`); батчевый prefill — `bounded_attention_batch`
  (проекции GEMM, оператор по позициям, скоры только по кольцу ∪ чанку).
- `ppl` идёт штатным оператором: `--o1`/`CMF_O1*` на bounded-файле — **ошибка**
  («anchor is native bounded»), не warn. Метка результата: `PPL = … (bounded operator
  swa_sink_v1 W=128 S=4)`.
- Пул потоков: `CMF_THREADS=N`; после исправления гонки дескриптора
  (`pool.rs`, seqlock + эпоха в дескрипторе) ограниченные рассылки малых матриц
  Embryo больше не зависают/не падают (регрессионные тесты `pool.rs`
  `uninvited_straggler_*`, `tests/legacy_pool_ppl.rs`).
- Диагностика: `CMF_PPL_TRACE=1` — NLL каждого токена (`BTRACE pos … nll …`);
  `CMF_STATE_TRACE=1` — RMS/max рекуррентной записи каждого слоя каждые 256 позиций
  (`STATE pos=… layer=… kind=… S_rms=…`); `CMF_PREFILL_PROF=1` — строка
  `kv-reuse: R of N prompt positions already cached` на каждом ходе с переиспользованием.

## 3. Резидентный wgpu-граф (Linux/Windows, дискретная карта)

```
export CMF_GPU=wgpu CMF_GPU_PROBE=0 CMF_GPU_WGPU_GRAPH=1 CMF_EMBRYO_RESIDENT=parallel
cortiq bench bounded-500-f32.cmf --tokens 128 --ctx 32768 --core --json
```

- Весь токен — один submit (`wgpu_submits_per_token = 1.0`): веса, рекуррентное
  состояние, кольца якорей и иерархическая голова живут на устройстве
  (`gpu_wgpu.rs` `EMBRYO_CORE_SRC`, слои kind 0/1 = vmf_phase, 3 = bounded, 4 = GDN;
  legacy full-anchor kind 2 — только для старых файлов).
- Prefill — чанками по `CMF_EMBRYO_CHUNK` позиций (по умолчанию 64 = `EMBRYO_CHUNK_MAX`):
  проекции/FFN/роутер — чанковые GEMM с порядком редукции токен-пути, рекуррентные
  слои и якорь идут по чанку во времени на устройстве; логиты — только последней
  позиции. `CMF_EMBRYO_CHUNK=0` — потокенный prefill (референс). Чанковый и потокенный
  дают **одинаковые биты** (`tests/embryo_resident_parity.rs`, `CMF_EMBRYO_CHUNK_TOL`).
- Граф **f32-only**: q4tp/q8-файл → `eligible=false` → per-op путь (медленнее CPU, §7).
- Телеметрия: `bench --json` → `device_state_bytes`, `device_kv_bytes` (читаются из
  живых буферов), `wgpu_submits_per_token`; `CMF_EMBRYO_DBG=1 RUST_LOG=warn` печатает
  причину отказа от графа; `CMF_EMBRYO_PROFILE=1` — тайминги стадий (рвёт слитый pass,
  не для замеров).
- Паритет с CPU: `embryo_resident_parity` (двухпроцессный: `CMF_EMBRYO_PARITY_MODE=cpu`
  пишет референс, `=parallel` сравнивает; `CMF_EMBRYO_PARITY_IDS=synth:512|natural`,
  `CMF_EMBRYO_PARITY_TOKENIZER` + `_PROMPT_FILE` для натурального префикса).

# Engineering notes

## q2tp: encoder v2 and GPTQ into q2tp

Two changes to the q2tp tooling. The CMF format, the q2tp reader and the
kernels are unchanged: every file decodes as before.

1. **`encode_q2tp` v2** (`cortiq convert --quant q2tp`, requant, videopack,
   the DSpark sidecar — every caller). This is the zero-bit, data-free
   converter fix "Q0pd" from the q2tp study.
2. **`cortiq quantize-gptq --codec q2tp`**: GPTQ error feedback into the q2tp
   codec for the converter's q2tp profile. It ships with calibration
   plumbing that also serves `--codec q4tp`.

### What changed

**`crates/cortiq-cli/src/convert.rs`**

- `encode_q2tp` now picks an encoder. The default is `encode_q2tp_v2`.
  `CMF_Q2TP_ENCODER=v1` selects `encode_q2tp_v1`, the old code kept
  verbatim. `CMF_Q2TP_SEARCH=0` still selects the plain absmax rule.
- v2 encodes each row in three steps:
  1. `q2tp_place_row`: for each group, choose the scale
     `m·absmax/1.5` with `m ∈ {0.300, 0.325, …, 1.050}` that gives the
     lowest rounding error. The ladder spans those scales. Four ladder
     tops are tried as in v1, and the one whose full rung search gives the
     smallest row error wins.
  2. A full search over all 31 rungs, then round-to-nearest.
  3. `q2tp_unshrink_row`, a weight-space debias. The row slope is
     `b = ⟨W,Ŵ⟩/⟨W,W⟩`, clipped to 0.8…1.25. It is removed by shifting the
     row's f16 `lo` by `−log2 b`. Codes, rungs and steps are unchanged.
- `q2_level` replaces `round_ties_even().clamp(0,3)` by a magic-number
  rounding that gives the same value. It vectorizes on baseline x86-64.
  `q2tp_group_err` sums in eight fixed lanes. As a result, the bytes do not
  depend on the machine or the thread count.

**`crates/cortiq-cli/src/gptq.rs`**

- `run_quantize_gptq_tiled` replaces `run_quantize_gptq_q4tp` and handles
  both profiles. Each tensor gets the codec from `effective_quant(profile)`,
  with `--tensor-quant` overrides applied first.
  - q4tp and q2tp tensors that have a Hessian go through GPTQ in their own
    codec. A q4tp override on a q2tp profile is therefore an escort that
    stays GPTQ.
  - All other tensors get converter round-to-nearest.
  - A plain q4tp run writes the same header as before.
- `gptq_quantize_q2tp` has two rung rules (`Q2tpRule`):
  - `cortiq`: the v1 ladder. When the sweep reaches a group, its rung is the
    best of nominal−2…+1, with nominal taken from the corrected absmax/1.5
    and candidates ranked by `H_ii`-weighted error. This is the study's arm
    N1.
  - `placed`: the ladder is placed with `H_ii` weights, and each group gets
    a full 31-rung search when the sweep reaches it. This is the study's arm
    W0 and the default.
  - With `--act-order`, rungs are fixed up front: v1's rungs for the cortiq
    rule, the placed ladder's own rounding choice for the placed rule.
  - The sweep uses a 128-column lazy block. The update of the remaining
    columns is register-tiled (8 rows × 8 columns, with AVX2 dispatch), and
    work is split into 32-row items. Each row is computed by one thread in a
    fixed order, with multiplies and adds kept separate.
- `q2tp_debias_hessian` (`--q2tp-debias on|off`, default `on`) computes
  the row slope `(ŴHWᵀ)/(WHWᵀ)` on the calibration Hessian and removes it
  through `lo`.
  - Measured −11.5 % on the placed arm at zero bits (see below).
  - `off` reproduces the study's plain GPTQ arms (N1, W0). The N1c, W0c,
    N1c7, W0c7, W0ca and W128c rows below were run with it off.
- `--q4tp-debias` (opt-in) applies the same debias to q4tp tensors through
  `q4tp_debias_hessian`. It is off by default, so the q4tp output stays
  byte-identical to master.
- `--q2tp-rule-tensor PATTERN=RULE` sets the rule per tensor. Example: layer
  7 on the cortiq rule, as in the study's arm W128dh.
- Calibration changes:
  - `--calib` can be repeated as `PATH=SHARE`. Shares are rounded
    cumulatively, so they sum exactly to `--tokens`. Accepted inputs:
    `.txt`, `.jsonl` (`{"text":…}` or a string per line), and `.json`.
  - Text is read in budgeted prefixes (about 8 bytes per token, doubled as
    needed, with a 64-token margin), never the whole corpus.
  - A window never spans two sources.
- The capture keeps only the linears that GPTQ will quantize
  (`gptq_capture::begin_filtered`).
- `--calib-chunk-layers N` captures N layers per calibration pass, with one
  cache file per chunk: `PATH.L{a}-{b}`.
- Hessian groups are deduplicated by exact equality and freed as they are
  grouped.
- The cache is indexed (`index_hessian_cache`) and read one group at a time
  (`read_hessian_entry`). Previously every name got its own full copy.
- `gptq_fold_operator_par` runs both Cholesky factorizations, the
  triangular inverse and the `H⁻¹` product on several threads.
  - Each phase is cache-blocked in 32-column or 32-row blocks.
  - It is bit-identical to the original serial operator because every entry
    is the same `dot64` over the same slices, computed by a single worker.
  - Hessian groups are processed widest first, which shortens the tail.
  - The number of groups processed at once is capped by the RAM left after
    the chunk's Hessians and the tensors already written (85 % of the
    machine's RAM, the cgroup limit in a container); `CMF_GPTQ_MEM_GB`
    overrides it. A calibration pass whose Hessians exceed 90 % of RAM is
    refused up front with a `--calib-chunk-layers` value that fits.

**`crates/cortiq-engine/src/gptq_capture.rs`**: adds `begin_filtered`.

**`crates/cortiq-cli/src/main.rs`**: new flags `--codec q2tp`,
`--calib PATH[=SHARE]` (repeatable), `--calib-chunk-layers`, `--q2tp-rule`,
`--q2tp-rule-tensor`, `--q2tp-debias on|off`, `--q4tp-debias`.

### How to use

```sh
# data-free (v2 is the default; CMF_Q2TP_ENCODER=v1 for the old encoder)
cortiq convert --model HF_DIR --quant q2tp \
  --tensor-quant lm_head.weight=q8_2f --tensor-quant model.embed_tokens.weight=q8_2f --output q2tp.cmf

# GPTQ (f16 weights in, q8_2f sibling for the calibration forward; ≥ 32k tokens at 2 bits)
cortiq convert --model HF_DIR --quant f16 --output f16.cmf
cortiq convert --model HF_DIR --quant q8_2f --output q8_2f.cmf
cortiq quantize-gptq f16.cmf --codec q2tp --calib-model q8_2f.cmf \
  --calib wiki.train.raw=0.75 --calib c4.jsonl=0.25 --tokens 32768 --window 2048 \
  --tensor-quant lm_head.weight=q8_2f --tensor-quant model.embed_tokens.weight=q8_2f \
  --q2tp-rule placed --hessians H.hess --calib-chunk-layers 21 \
  --q2tp-rule-tensor 'model.layers.7.mlp.*=cortiq' --output q2tp-gptq.cmf
# (placed rule + debias are the defaults; the layer-7 rule is MiniCPM5's super-weight layer)
# escort: --tensor-quant model.layers.7.mlp.gate_proj.weight=q4tp (stays GPTQ, in q4tp)
# variants from the same cache: --q2tp-rule cortiq | --q2tp-debias off | --act-order
```

Measurement scripts (pod paths of the q2tp study) are in `tools/q2tp_eval/`:
- `gptq.sh`: one run with peak-RSS timing (`timerun.py`)
- `det.sh`: determinism and chunking checks
- `eval.sh`: raw dump and torch ppl with the study's evaluator
- `paired.py`: paired per-window comparison
- `hess2cmf.py`: the study's Hessians as a cortiq cache
- `par.sh` / `compare_q2.py`: payload parity against the torch arms
- `regress_q4tp.sh`: the q4tp byte-identity check

### Tests

`cargo test --release -p cortiq-cli -- q2tp q2_ gptq calib layer_chunks two_bit four_bit parallel requant fold tiled`
(36 tests) and `cargo test --release -p cortiq-engine --lib gptq_capture`.

Two integration tests in `tests/decision_cli.rs` fail on this pod

They fail the same way on master 5d6f1830 there, so the failure predates
this work.

- v2 encoder:
  - weight error below v1 on heavy-tailed matrices
  - debias brings each row slope back to 1 and leaves codes and rungs alone
  - `CMF_Q2TP_ENCODER` and `CMF_Q2TP_SEARCH` select the right encoder
  - bytes match between 1 and 8 threads
  - the reader validates the payload; dead rows and groups decode to zero
  - `q2_level` gives the same values as `round_ties_even`
- GPTQ-q2tp:
  - output error beats round-to-nearest with both rules, and `placed` beats
    `cortiq`
  - bytes match for 1, 5 and 7 threads, in natural and act order
  - act order keeps the static rungs
  - with an identity Hessian the result equals placed round-to-nearest
  - Hessian debias brings the slope back to 1
- Building blocks:
  - the trailing update matches a reference loop bit for bit
  - the threaded fold operator and Cholesky match the serial versions bit
    for bit
  - cache round trip through the lazy index
  - calibration share parsing and splitting, and budgeted `.txt` / `.jsonl`
    reading
  - filtered capture

The existing q2tp payload, round-trip, requant and parallel-encoding tests
pass unchanged.

- For Qwen3.8-27B q4tp, the lever is the calibration budget: 32k tokens
  gave −3.0 % over the shipped 2048 tokens here (20.23 → 19.62, bf16
  18.89), which closes 45 % of that recipe's gap to bf16. The debias adds
  nothing at 4 bits, because the q4tp cortiq rule's absmax scales are
  already unbiased. It stays opt-in.

  produced a file byte-identical to `Q0h_v2.cmf` (sha256 83d36e66…, torch

- **GPTQ-q2tp with the CLI defaults** from the 32k cache produced a file
  byte-identical to the evaluated `W0cd.cmf` (sha256 81f35e49…, ppl 27.756).

- **q4tp against master, with no cache.** Master's binary and this branch
  each calibrated from scratch on the same 2048 WikiText-2 train tokens
  (`--codec q4tp`, head and embeddings q8_2f) and wrote byte-identical files
  (sha256 c939b1fd…). This also checks that the budgeted calibration reader
  yields the same windows as master's whole-file read. Peak RSS was 23.2 GB
  on this branch and 23.4 GB on master.
- **Code review.** No correctness bug was found in the q2tp v2 writer
  against the unchanged reader and kernels, in the GPTQ sweep, the blocked
  trailing update, the threaded Cholesky and inverse, the Hessian cache
  reader and writer, or the calibration reader. Three fixes were committed:
  1. RAM guards for 27B-scale runs.
     - At the default `--calib-chunk-layers 0`, a Qwen3.8-27B capture needs
       about 230 GB and was not checked; it would have died with an OOM kill
       during its first CPU window. It is now refused before the forward
       runs, with a chunk size that fits.
     - The widest-first order starts all the widest folds together. Without
       `CMF_GPTQ_MEM_GB` nothing capped them; the RAM left now does.
     - The bytes do not change. The fixed binary rebuilt W0cd from the
       cache on 6 threads, byte-identical (sha256 81f35e49…).
  2. `env_guard` now also clears `CMF_Q2TP_ENCODER`, so a panicking test

  3. `par.sh` now passes `--q2tp-debias off`. The study's N1 and W0 arms
     have no debias, and the CLI default is now on.
- **Behaviour change outside quantization.** The DSpark draft requantizes its
  gate/up experts from q4tp to q2tp at upload, through `encode_q2tp`. It now
  runs v2, which does about 6× the search work of v1. The draft may encode
  better, but GPU upload of the draft takes longer. `CMF_Q2TP_ENCODER=v1`

### Open issues

- **The calibration forward is CPU-only, and this is the bottleneck for
  Qwen3.8-27B.** The Hessian hook lives in the CPU `QTensor::matmat`.
  - MiniCPM5-2B (q8_2f model, 13 threads): about 155 s per 2048-token
    window, roughly 13 tok/s. 32k tokens take about 40 min per pass; 131k
    tokens take about 2.8 h. For that reason the MiniCPM5 131k arm was not
    run; the long budget was shown on Qwen3-0.6B instead (52 s per window).
  - At 27B the same path costs about 13× more per token.
  - The tools below are ready for that scale; the forward is not. The next
    step is GPU-side capture: accumulate `XᵀX` for the four distinct
    inputs of each layer from the resident graph (f32 tiles on the device,
    f64 reduction on the host).
- **Hessian RAM** is dense f64 per tensor (8·cols² bytes). q/k/v and
  gate/up are captured separately even though their inputs are identical
  (the cache deduplicates them afterwards).
  - Qwen3.8-27B: about 3.6 GB per layer, so on 128 GB use
    `--calib-chunk-layers 8–16`, at one forward per pass.
  - Two improvements would bring this down to one pass: deduplicating
    identical inputs during capture, and storing a packed upper triangle in
    f32.
- **Fold operator.** In flight, one group holds 3n² f64 + n² f32 (8 GB at
  n = 17408). It is O(n³), about 3.5 T multiply-adds per 27B `down_proj`.
  - The threaded version and the RAM cap on concurrent groups handle this.
  - On MiniCPM5 one GPTQ-only arm took 14–20 min on the shared pod, about
    7 min per 21-layer chunk, mostly the 6144-wide folds.
  - The cache blocking made no measurable difference there (W0c_blocked
    879 s against W0c 829 s, same bytes, both under contention). At this
    size the folds are compute-bound in `dot64`. A faster `dot64` with more
    accumulators would change the summation order, and with it the q4tp
    bytes, so it was not done.
- **Mixed calibration** has only been checked functionally (detM, and the
  Qwen3-0.6B run). Its effect on quality against WikiText-only calibration
  was not isolated.
- **Not ported from the q2tp study:**
  - the H-metric refit and the code/scale alternation (with layer 7 fixed:
    −12 % on the cortiq line, −9 % on the placed line; they need held-out
    Hessians for selection);
  - the automatic super-weight guard (the study chose layer 7 with a
    model-level sensitivity pass);
  - end-to-end metric genesis (R1/R2, 25.6 → 21.9).

  `--q2tp-rule-tensor` and q4tp escorts handle the layer-7 case by hand.
- **Encoder cost.** The v2 encoder evaluates 155 group errors per group
  against 24 in v1. On MiniCPM5 (1.06 G q2tp weights, 13 threads) a
  `convert` takes 33 s instead of 27 s. A bracketed rung search around the
  placed scale would remove most of that cost, but it would need a parity
  check against the full search.
- **Act order with q2tp** uses static rungs, so there is no rung choice at
  sweep time. Measured +35 % ppl against natural order (W0ca vs W0c), so
  the runner warns. Act order would need sweep-time rungs, which a permuted
  sweep cannot pick group by group.

## Pipeline "genesis + tooling" (2026-10-17): metric genesis, escort, exact ppl as tools

Goal: turn the q2tp / q4tp studies' Python scripts (MiniCPM5-2B, `cmf-lb-local-runs/
{q4tp_genesis_minicpm5_20261017, q2tp_nvg_minicpm5_20261016T1800Z, q4tp_nvg_minicpm5_20261016T1215Z}`)
into production tools that scale to Qwen3.8-27B (hybrid GDN, `qwen3_5`) on one 32 GB GPU with
≥ 128 GB host RAM, without touching the CMF format or the kernels.

### What changed

- **cortiq CLI** (`crates/cortiq-cli/src/main.rs`): `cortiq dequant --dtype raw` writes a tensor's
  encoded payload verbatim; `cortiq patch-tensor --raw` stores an already encoded payload verbatim
  (the entry's dtype, or `--dtype` as the encoder would emit it for that shape), length-checked by
  the reader's own `validate_payload`, hashes recomputed; in place when the slot fits, else
  `--output`. Unit test `dequant_raw_and_patch_raw_round_trip_payloads_verbatim`.
- **tools/quant/** (new, see its README): `cmfio.py` (read-only CMF reader over mmap + write-back
  via `patch-tensor --raw` + `verify`), `cmfcodec.py` (byte-exact q4tp / q2tp / q8_2f / float
  payloads, field splicing), `qmodel.py` (torch model over a real CMF: llama family + `qwen3_5`
  hybrid; compact weights decoded on the device inside a memory-light custom autograd matmul;
  chunked KL head with an analytic backward; `resident` / `stream` residency with side-stream
  prefetch, bit-identical), `calib.py` (corpus specs, the studies' window placement, the cached
  teacher top-K), `metric_refit.py` (metric genesis), `escort.py` (sensitivity + water-filling,
  greedy re-measure, `--tensor-quant` output, escorted file), `ppl.py` (exact perplexity with
  paired SE), `tests/`.

See `tools/quant/README.md` (commands, memory model, 27B sizing, recipes q4tp-v2 / q2tp-v2).
