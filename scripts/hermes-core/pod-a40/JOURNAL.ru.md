# Тренер Embryo на CUDA: под A40, 14.11.2026

Задача владельца: «оптимизируй на CUDA по максимуму, потом посчитай, сколько
времени займёт обучение». Модель — выращенный из Embryo-56M ствол 340M
(16 слоёв × 768, 12 GDN-смесителей + 4 якоря, 4 эксперта на слой), корпус —
исходники Hermes, документация по командам ОС, Stack Exchange.

## Стенд

RunPod, NVIDIA A40 (46 ГБ), 7,65 ядра CPU, предел памяти контейнера 50 ГБ,
CUDA 12.8. Рабочий каталог `/root/hc`: `cmf/` — репозиторий (master e406e00d
+ изменения этой ветки), `data/` — `grown340.ckpt` (sha256 c7925739…) и шарды
`se.u16`, `docs.u16`, `hermes_code.u16`, `val.u16`, `run/` — логи.
Сборка: `cargo build --release -p cortiq-embryo --features cuda`,
перед запуском `export LD_LIBRARY_PATH=/usr/local/cuda/lib64:$LD_LIBRARY_PATH`.

Файлы рядом: `birth.sh` (короткий `birth` с пиком памяти и sha256
чекпойнта), `ab.sh` (TF32 против fp32), `prof.py` (разбор профиля
`CMF_VULKAN_OP_TS=1`), `cfg340.json` (форма для `step-bench`),
`verify-hook.patch` (временная сверка двух форм ядра, см. ниже).

## Что изменено в тренере

Всё в `crates/cortiq-embryo/src/cuda_dev.rs` и `wgsl_cuda.rs`; WGSL и путь
wgpu не тронуты.

1. **cuBLAS для больших GEMM** (одна матрица, от 2²⁶ умножений), на
   тензорных ядрах в режиме TF32. Мелкие пакетные GEMM остаются на своих
   ядрах: через cuBLAS они идут 0,1–0,3 TFLOPS.
2. **Динамические GEMM экспертов через cuBLAS.** Число строк эксперта
   лежит на карте; `commit` один раз читает счётчик и вызывает cuBLAS по
   фактическому размеру. Строки за счётчиком — по контракту ядер
   (C = beta·C).
3. **`emb_main` отдельной копией на каждую операцию** — без цепочки из ~50
   ветвлений в каждом потоке. Арифметика та же.
4. **Девять ядер только для CUDA** (`NATIVE_CUDA`). В форме WGSL эти
   операции простаивали: один последовательный поток (`ROUTE_GROUP`), один
   поток на строку или столбец с чтением через 3 КБ (`RMS_FWD`, dW у
   `RMS_BWD`, dW у `CONV_BWD`), несколько тысяч потоков, каждый со своим
   куском (`SUMSQ`, `WY_DU`, `WY_DGEND`, `WY_DLG_DOT`, `WY_DSCAL`). Новая
   форма: слитная загрузка в разделяемую память, суммы — в том же порядке
   одним потоком.

Выключатели: `CMF_CUDA_TF32=0` (cuBLAS в полном fp32), `CMF_CUDA_CUBLAS=0`,
`CMF_CUDA_CUBLAS_DYN=0`, `CMF_CUDA_MAIN_SPEC=0`, `CMF_CUDA_NATIVE=0`,
`CMF_CUDA_NATIVE_SKIP=70,76` (перечисленные коды операций — на форме WGSL).

## Точность

- **Ядра только для CUDA и копии `emb_main` — те же биты.** Проверка:
  8 шагов `birth` на настоящем рецепте с одним зерном, sha256 чекпойнта
  (веса и моменты). С ядрами и без: один хеш f0423782…; повтор с ядрами
  даёт тот же хеш (тренер на CUDA детерминирован).
- **cuBLAS в fp32** — не те же биты, что у своих ядер (другой порядок
  сумм), класс точности fp32. Набор тестов крейта с
  `CMF_CUDA_CUBLAS=all CMF_CUDA_TF32=0` (cuBLAS на каждом простом GEMM,
  включая динамические): проходят все сравнения с эталоном f64 и конечными
  разностями; падают только два теста на побитовую идентичность и тест,
  которому нужны переменные окружения.
- **TF32** — относительная ошибка GEMM 1e-4…4e-4 (мантисса множителей
  10 бит). На обучении: 300 шагов с одной точки и одним зерном, B8×1024 —
  валидационная потеря 3,2638 (TF32) против 3,2637 (fp32), перплексия 26,15
  у обоих; потери на шагах расходятся в 3–4-м знаке.
- Набор тестов в конфигурации по умолчанию: 40 файлов тестов проходят,
  падает один ручной (`terminal_sft_final_holdout_eval`, нужен
  `CMF_SFT_FINAL_CKPT`). Тест тайловых ядер `vulkan_gemm64` закреплён на
  своих ядрах (`CMF_CUDA_CUBLAS=0`): большой GEMM в нём иначе уходит в
  cuBLAS с TF32 и не укладывается в допуск 1e-5.

### Контракт

Один формат для всех диалогов и вызовов (`datasets/convert.py`): кадр
cmf-im-v1 (`<|im_start|>роль`, `<|im_end|>`), рассуждение в `<think>`,
вызов в `<tool_call>{"name", "arguments"}</tool_call>`, результат в
`<tool_response>` у роли `tool`, описания инструментов в `<tools>` в
системном сообщении — формат Hermes function calling. Теги — обычный текст:
в токенизаторе gen1 отдельных id для них нет (свободных спецтокенов четыре),
менять токенизатор у выращенной модели не стал. Спецтокены кадра в шардах —
id (`shard --specials`).

Обращение к справочнику — инструмент `lookup` того же контракта: на сервере
на него отвечает роутер по записям. Трассы (`stage0/lookup_gen.py`,
86 088 диалогов из задач `train_gen.py`, непересекающихся с набором R):

| Режим | Диалогов | Что происходит |
|---|---|---|
| lookup | 35 037 | карточки в запросе нет: рассуждение → `lookup` → карточка (одна или с 1–2 соседними) → рассуждение по шаблону → `terminal` |
| retry | 9 541 | первый `lookup` возвращает чужие карточки → «не то» → второй запрос → ответ |
| context | 19 119 | карточка уже в запросе (режим `context` движка): без `lookup` |
| two | 2 591 | конвейер из двух команд: два `lookup` или один на обе |
| none | 4 050 | подходящей карточки нет: после 1–2 запросов ответ NONE |
| direct | 15 750 | задачи без карточки (реакция на вывод, счёт): прямой ответ |

Рассуждение строит программа: какая карточка, какой шаблон, какое значение
куда. Проверка: подстановка значений из рассуждения в шаблон даёт команду —
61 433 трассы, расхождений 0. Первая версия брала первый шаблон, подошедший
как регулярное выражение (`base64 {{file}}` «съедал» `-d /x`): теперь берётся
шаблон с наибольшей буквальной частью, значение с ведущим дефисом — отказ.

## Ловушки

- `cargo build … | grep | head` обрывает сборку по SIGPIPE, замер идёт на
  старом бинаре. Сборку — в файл, искать `Finished`.
- `pkill -f` и `pgrep -f` по тексту команды убивают собственный ssh: шаблон
  есть в argv удалённого bash. Фоновые циклы — с конечным счётчиком и
  `kill $!`.
- `cargo test` без `--no-fail-fast` останавливается на первом упавшем
  файле. `growth_record_e2e` ищет бинарь `cortiq` рядом с тестом и не
  находит его в новой раскладке каталогов cargo: задать `CORTIQ_BIN`.
  `terminal_sft_final_holdout_eval` — ручной, требует `CMF_SFT_FINAL_CKPT`.
- Совпадение потерь до 4-го знака — не побитовая идентичность. Ядро
  `WY_DSCAL` давало те же потери и `|g|`, но другой sha256.
- Свёртка в FMA не выводится из исходника. NVRTC сворачивает произведение
  в следующую за ним сумму; затем ассемблер PTX ещё раз сворачивает пару
  `mul` + `sub`, если у произведения нет других потребителей. В `WY_DSCAL`
  так свернулась сумма `pa`, а `pd` — нет (её произведение ещё и
  записывается как `da`). Смотреть PTX в `~/.cache/cortiq/cuda/` и сверять
  выходы на карте.
- `verify-hook.patch` запускает обе формы операции на одних входах и
  печатает первое расхождение (`CMF_CUDA_NATIVE_VERIFY=<код>`). Годится
  только для операций, которые не читают свои выходы: для `WY_DU` (пишет
  на месте) и накопительных dW он показывает ложные расхождения.
- Прямой ssh к поду на несколько минут пропадал (тайм-аут соединения);
  фоновые задания на поде при этом живут.

## Что осталось

- Компактная раскладка dropless: буферы экспертов на m строк вместо 4·m с
  динамическими смещениями. Освобождает 9,7 ГБ при B8, вчетверо сокращает
  обмен SwiGLU по пустым строкам. Затрагивает WGSL, запись операций и путь
  cuBLAS.
- Прямой GEMM экспертов идёт через cuBLAS в форме (T,N): 34–73 TFLOPS
  номинальных против 54–99 у (N,N).
- Мелкие пакетные GEMM кусков WY: ~40 мкс на запуск, упираются в задержку
  запуска, а не в счёт.
- `WY_MASK_BWD_RED`: строчная часть читает вразнобой.
