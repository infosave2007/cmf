# Cortiq Decision на Vulkan

Нативный Rust/WGSL-путь для **того же CMF-файла**, без CUDA и переупаковки весов.
Доступно начиная с Cortiq 0.8.0; CPU остаётся режимом по умолчанию.
Нужен Rust 1.88 или новее.

## Сборка и запуск

На Linux с установленным Vulkan-драйвером GPU:

```bash
cargo install cortiq-cli --locked
export CORTIQ_DECISION_DEVICE=vulkan
export CORTIQ_DECISION_VULKAN_ADAPTER="RTX PRO 4000"
cortiq decide /path/to/cortiq-decision.cmf \
  --skill banking77 -p "I still have not received my new card" --json
```

Название в `CORTIQ_DECISION_VULKAN_ADAPTER` — уникальная часть имени GPU.
Если подходящих карт несколько, выбор обязателен. Программные адаптеры
вроде llvmpipe не принимаются; ошибки GPU не скрываются переходом на CPU.

Для API используются те же переменные:

```bash
cortiq serve /path/to/cortiq-decision.cmf \
  --host 127.0.0.1 --port 8091 --state ./decision-vulkan-state
```

`GET /healthz` показывает имя настоящего адаптера и счётчики
`vulkan_encoder_submissions` / `vulkan_resonance_submissions`.
Тайминг `gpu` включает весь совместный проход, а не только арифметику одного ядра.

## Что оптимизировано

- Резидентные веса и промежуточные тензоры; одна отправка вычислительного графа
  и одно итоговое чтение на CPU. Нет копирования промежуточных слоёв по PCIe.
- Параметры графа для длин входа подготовлены заранее. На запрос передаются
  только токены и хеш-признаки, а не веса и вся таблица команд.
- Для последовательностей до 128 токенов и небольших матриц на NVIDIA — скалярные FP32 произведения
  с subgroup-редукциями. Они дают больше независимых рабочих групп, чем
  крупные матричные плитки на маленьком запросе.
- Длинные последовательности используют плиточную матрицу. Её общая память
  транспонирована с дополнением, чтобы не создавать конфликт банков памяти.
- Attention с головой до 32 координат на NVIDIA объединён с online-softmax:
  без записи промежуточной матрицы attention и двух лишних запусков на слой.
- Реконструкция держит остаток и коэффициенты в регистрах. Каждый следующий
  базисный вектор применяется к уже обновлённому остатку; ортогональность
  базиса не предполагается.

Вычисления FP32, без FP16 и TF32. Порядок сложения отличается от CPU;
точность контролируется неизменным допуском эмбеддингов и независимым
сравнением решений, отказов и ошибок реконструкции.

## Проверка

```bash
cargo test --release -p cortiq-decision --features vulkan \
  --test vulkan_gpu -- --ignored
cargo run --release -p cortiq-decision --features vulkan \
  --example metal_compare -- /path/to/cortiq-decision.cmf \
  /path/to/test.jsonl banking77 999999 vulkan
```

Имя `metal_compare` сохранено для совместимости с первой серией измерений;
последний аргумент выбирает `vulkan`, JSON явно показывает фактическое устройство.
Набор JSONL содержит `{"text":"...","label":"..."}`. Benchmark не вызывает оракул.

Для диагностики можно **перед первым созданием GPU-модели** задать
`CORTIQ_DECISION_VULKAN_PROFILE=1`: stderr получит длительности подготовки,
отправки, ожидания и аппаратные GPU timestamps. В итоговом сравнении
профилирование выключено. Драйверные частоты и лимиты мощности не меняются.

## Границы проверки

Текущий целевой стенд — RTX PRO 4000 Blackwell. Другие Vulkan GPU требуют
собственной проверки. Нужны subgroup-операции и достаточные лимиты буферов;
при несовместимости загрузка завершается ошибкой. CPU и Metal доступны отдельно.
Загрузка модели, компиляция шейдеров, сеть и внешний оракул не входят в прогретую
локальную задержку. GPU не гарантирует одинаковую скорость на каждом запросе.

Benchmark поддерживает последний аргумент `separate`: сначала весь CPU-набор,
потом весь GPU-набор с теми же проверками. Это задержка непрерывной серии.
Режим по умолчанию `paired` вставляет CPU-вычисление между GPU-запросами.
При таком простое RTX автоматически снижает частоту памяти; результаты двух
режимов нельзя смешивать. Частоты и питание тестовые скрипты не меняют.
