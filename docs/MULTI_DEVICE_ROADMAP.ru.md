# N GPU/CPU в CMF: план развития (multi-device и multi-node)

Статус: проект-план, не начат. Состояние кода — 0.5.65.
Связанные документы: `PERFORMANCE_ROADMAP.ru.md` (§12.1 фиксирует multi-GPU как
«после single-GPU graph — layer/tensor split, peer transfer и admission control»),
`CMF_V2_SPEC.md`, `OPTIMIZATION_ROADMAP.md`.

---

## 0. Резюме

**Формат не меняется.** `.cmf` остаётся девайс-агностичным: один файл — одна
единица дистрибуции, читаемая любым сегодняшним ридером. Параллелизм — свойство
исполнения, а не файла; план размещения — производный, удаляемый артефакт
(правило трёх уровней из `PERFORMANCE_ROADMAP.ru.md` §4.1: семантика / переносимое
хранение / нативный кэш).

Три несущих решения:

1. **Устройство становится значением, а не глобалом.** Сегодня контекст GPU —
   процесс-глобальный `OnceLock` без выбора карты (`gpu_wgpu.rs:10072`,
   `gpu_metal.rs:3851`, `vulkan.rs:74`). Вводим `DeviceId` + реестр устройств;
   CPU — полноправное устройство наравне с GPU. Это фундамент всего остального,
   и он даёт немедленную пользу ещё до всякого параллелизма: выбор карты
   (`--device gpu:1`) сегодня невозможен в принципе.
2. **План размещения (placement plan) — явный, измеренный, воспроизводимый.**
   JSON-описание «слой/эксперт/диапазон строк → устройство», построенное
   автоматически из измеренных бюджетов или заданное вручную, сохраняемое в
   `.cmfplan`. Ключуется `dir_hash` файла + набором устройств. Не поле формата:
   «метафора не становится полем формата, пока не измерена».
3. **Сеть — поверх серверного слоя, не внутри движка.** `cortiq worker` держит
   диапазон слоёв того же файла (идентичность — по `dir_hash`, как у standalone
   skill: `base_dir_hash`), координатор гоняет активации. Никаких NCCL/MPI/CUDA:
   ядро остаётся no-framework (`CONTRIBUTING.md:75-77`), tokio уже есть в
   workspace у server/cli.

Лестница ценности для пользователя (в порядке реализации):

| Ступень | Что получает пользователь | Требование к железу |
|---|---|---|
| Выбор устройства — **СДЕЛАНО 2026-08-10** | `CMF_GPU_ADAPTER=индекс|имя`, `cortiq gpu` нумерует | 1+ GPU |
| Data-parallel на хосте | слоты `serve` закреплены за разными GPU → throughput ×N | модель влезает в каждую |
| Layer split на хосте — **СДЕЛАНО 2026-08-10** | `run/serve --gpus 2`: локальный воркер на второй карте через путь --peer, парити побайтное (bonsai, 2×5090) | 2+ GPU / GPU+CPU |
| Реплики по сети | роутер перед N узлами → throughput ×N | модель влезает в узел |
| Layer split по сети — **СДЕЛАНО 2026-08-10** (cortiq-net, wire v4) | **модель больше одного узла запускается** | 2+ узла |
| Мобильный расширитель — **ИЗМЕРЕНО 2026-08-12, роль перевёрнута** | телефон не добавляет мощности десктопу (это минус), а БЕРЁТ её: 34.7B на аппарате с 2 ГБ свободных, 16.3 tok/s | любой Android на кабеле |
| Tensor/expert split | ниже латентность на токен | быстрый interconnect, только по измерению |

## 1. Инвентаризация: где живёт однодевайсность

Полный список — 18 позиций; несущие:

| # | Допущение | Где |
|---|---|---|
| 1 | Один глобальный adapter/device/queue на бэкенд | `gpu_wgpu.rs:10072`, `gpu_metal.rs:3851`, `vulkan.rs:74` |
| 2 | Карта выбирается `PowerPreference::HighPerformance`, индекса нет | `gpu_wgpu.rs:10170-10176`; `enumerate_adapters` — только диагностика (`adapter_report`, `gpu_wgpu.rs:32047`) |
| 3 | Фасад `gpu.rs`: `enum Backend {None, Metal, Wgpu}` — вид, не handle; ~60 функций без параметра устройства | `gpu.rs:513`, `gpu.rs:527`, `gpu.rs:613-1560` |
| 4 | Кэш весов ключуется `(model_uid, tensor_idx)` — без устройства | `gpu_wgpu.rs:9800`, `weight_buffer` `gpu_wgpu.rs:10998` |
| 5 | KV/GDN/DSV4-зеркала ключуются `(kv_id, layer)` — без устройства | `gpu_wgpu.rs:9814-9845`, `gpu_metal.rs:3824` |
| 6 | Единый VRAM-бюджет и probe-вердикты — процесс-глобальные | `gpu_wgpu.rs:9780,10299`; `PROBES` `gpu.rs:208` |
| 7 | Гейтинг через thread-local (`CUR_LAYER`, `cpu_scope`) | `gpu.rs:18-33` |
| 8 | Раскладка слоёв — только CPU-vs-GPU (`CMF_GPU_LAYERS`) | `gpu.rs:72-106`, применяется в `pipeline.rs:5246` |
| 9 | `dsv4.rs` минует фасад: 141 прямой вызов `gpu_wgpu::` | `dsv4.rs` повсеместно |
| 10 | GPU-путь адресует только primary shard | `format.rs:823-825` + ~10 bail-out'ов в `gpu_wgpu.rs`/`gpu_metal.rs` |
| 11 | Ни одного CLI-флага устройства/потоков; всё — env-переменные, читаемые однажды | вся clap-поверхность `cortiq-cli/src/main.rs` |
| 12 | Сети нет нигде; сериализации активаций/KV через границу не существует | — |

Два готовых зародыша, на которых строим:

- **`CMF_GPU_LAYERS`** — уже раскладка «слой → исполнитель», просто исполнителей
  два и они захардкожены. Обобщение до «слой → устройство» и есть
  pipeline-parallel.
- **Гибридный сплит `qtensor.rs:1112-1173`** — буквально tensor-parallel matvec
  на двух исполнителях (CPU-половина + GPU-половина, непересекающиеся диапазоны
  строк, честный фолбэк). Обобщение до N исполнителей и есть tensor-parallel.

## 2. Принципы решения

1. **Контейнер неприкосновенен.** Ни новой секции (шесть слотов конверта
   позиционны, резервных байтов нет), ни feature-бита, ни бампа версии.
   Файл, записанный сегодня, читается всеми будущими бинарями; файл, записанный
   будущими — всеми сегодняшними. `python/cmf_reader.py` не требует правок.
2. **Разделение труда:** семантика — в `.cmf`; размещение — в `.cmfplan`
   (производный, удаляемый, ключёванный); транспорт — в протоколе воркеров
   (своя версия, независимая от версии формата).
3. **CPU — устройство.** Один исполнительский интерфейс для CPU-пула, каждой
   GPU и удалённого узла. Отсюда бесплатно: «несколько CPU по сети» — тот же
   путь, что «несколько GPU в корпусе»; CI-тесты мультидевайса без второй карты
   (cpu+gpu = уже два устройства).
4. **Fail loudly, никаких тихих деградаций.** Воркер недоступен → ошибка с
   именем узла, не молчаливый переезд на CPU. Несовпадение `dir_hash` между
   узлами → отказ («химеру не собираем» — тот же контракт, что у
   `skill apply`).
5. **Измерено, не задекларировано.** Авто-план строится из измеренных бюджетов
   (`vram_budget` уже вычисляется из реального heap); tensor-parallel включается
   только там, где probe показал выигрыш; каждый этап сдаётся с числами
   in-process таймеров, по методике `OPTIMIZATION_ROADMAP.md` §Benchmark rules.
6. **Последовательность из роадмапа соблюдается** (§12.1): single-GPU graph уже
   в master; дальше — раскладка слоёв, peer transfer, admission control. Этот
   план не перепрыгивает очередь — Phase 0/1 и есть её следующие пункты.

## 3. Целевая архитектура

### 3.1 DeviceId и реестр устройств

```rust
// cortiq-engine/src/device.rs (новый)
pub enum DeviceId { Cpu, Gpu(u32), Remote(u32) }   // Remote — с Phase 4

pub struct DeviceInfo {
    pub id: DeviceId,
    pub name: String,          // "Apple M4", "RTX 4090"
    pub backend: &'static str, // "metal" | "wgpu/vulkan" | "cpu" | "remote"
    pub stable_key: String,    // vendor:device:driver — для ключевания планов
    pub mem_budget: u64,       // измеренный, не заявленный
}
```

Индекс `gpu:N` — порядок `enumerate_adapters` — удобен в CLI, но нестабилен
между перезагрузками; в `.cmfplan` устройство записывается по `stable_key`,
индекс — только представление. `cortiq devices` печатает соответствие.

Сингلтоны превращаются в реестр: `ctx()` (`gpu_wgpu.rs:10092`) остаётся и
возвращает устройство по умолчанию — ни один существующий вызов не ломается;
добавляется `ctx_for(DeviceId)`. Metal и wgpu могут сосуществовать в одном
реестре (сегодня — взаимоисключающие через `backend()`).

Ключи всех кэшей получают измерение устройства:
`(uid, idx)` → `(dev, uid, idx)` для весов (`gpu_wgpu.rs:9800`),
`(kv_id, layer)` → `(dev, kv_id, layer)` для зеркал KV/GDN/DSV4.
Probe-вердикты (`PROBES`, `gpu.rs:208`) и VRAM-бюджет становятся per-device.

Thread-local гейтинг (`CUR_LAYER`, `CPU_ONLY`) заменяется явным контекстом
исполнения, передаваемым по цепочке вызовов (иначе декод, управляемый более чем
одним потоком, теряет гейты — сегодняшний пункт 11 инвентаризации).

### 3.2 План размещения `.cmfplan`

JSON рядом с моделью или во внутреннем кэше; удаляем — всё пересчитается.

```json
{
  "cmfplan": 1,
  "model": { "dir_hash": "9f3a…", "arch": "qwen3", "num_layers": 40 },
  "devices": [
    { "ref": "gpu:0", "key": "10de:2684:545.29", "budget_mb": 22800 },
    { "ref": "gpu:1", "key": "10de:2504:545.29", "budget_mb": 11600 },
    { "ref": "cpu",   "threads": 12 }
  ],
  "layers":  { "0-27": "gpu:0", "28-37": "gpu:1", "38-39": "cpu" },
  "embed": "gpu:0", "head": "gpu:1",
  "experts": null,
  "measured": { "tok_s": 31.2, "at": "0.5.66" }
}
```

- `dir_hash` (`CmfModel::dir_hash`, `format.rs:813-815`) связывает план с точным
  содержимым модели — план от другого файла отвергается, как `skill apply`
  отвергает чужую базу.
- Планировщик v1 — жадный: байты слоёв из директории (`layer_tensors`,
  `format.rs:886-893`) раскладываются по устройствам в порядке убывания
  измеренной пропускной способности до исчерпания бюджета; хвост — CPU.
  Никакого ILP-солвера, пока измерения не потребуют.
- Поле `measured` — числа последней проверки плана; расходится с реальностью →
  runtime предупреждает (контракт как у `quality: null` в skill-записях).
- `CMF_GPU_LAYERS` остаётся работать (алиас частного случая плана: одна GPU +
  CPU); при явном `--plan`/`--split` — предупреждение и приоритет флага.

### 3.3 Режимы исполнения

**A. Data-parallel (реплики).** Ноль работы в графе: слоты `PipelinePool`
(`cortiq-server/src/lib.rs:23-76`) закрепляются за устройствами
(`slot i → devices[i % n]`), веса грузятся в каждую карту независимо, KV и так
per-slot. Требование: модель влезает в каждое устройство. Масштабирует
пропускную способность сервера, не латентность одного потока.

**B. Pipeline-parallel (раскладка слоёв).** Обобщение сегодняшнего
`CMF_GPU_LAYERS`: каждый девайс держит непрерывный диапазон слоёв и **KV этих
слоёв** (KV уже пер-слойный — `KvCache.layers`, `kv_cache.rs:1083` — граница
режется бесплатно). На границе сегмента через устройство едет один hidden-вектор
(при decode — `hidden_size` f32/f16, единицы КБ). Однопоточному decode
перекрытие не нужно — устройства работают по очереди, это честно и просто;
prefill гоняется чанками (`CMF_PREFILL_CHUNK` уже есть) с перекрытием стадий.
Whole-token-graph путь (`try_token_graph_wgpu_steps`, `pipeline.rs:4094`)
строит не один граф, а по графу на сегмент: один submit на устройство на токен.

**C. Tensor-parallel (строки).** Обобщение `qtensor.rs:1112-1173` до N
исполнителей с непересекающимися диапазонами строк и конкатенацией результата.
Включается точечно и только по probe-выигрышу: на PCIe-картах синхронизация на
каждом matvec легко съедает всё. Не раньше Phase 5.

**D. Expert-parallel (MoE).** Банки экспертов уже выкладываются
роль-непрерывно (`CMF_V2_SPEC.md:222-231`) и грузятся пер-слойными планами
(`moe_expert_bufs`, `gpu_wgpu.rs:11174`) — раскладка экспертов по устройствам
ложится на существующий код загрузки; горячие эксперты — на быстрое устройство
(статистика уже есть у MoE-pin). Тоже по измерению.

### 3.4 Сетевой слой

Новый крейт `cortiq-net` (зависимости: core, engine, tokio, postcard/bincode —
всё уже в workspace; в core/engine ничего не добавляется).

```
cortiq worker model.cmf --listen 0.0.0.0:9911 [--device gpu:0] [--token T]
cortiq serve  model.cmf --peer gpu-box:9911 --peer cpu-box:9911 ...
cortiq run    model.cmf --peer gpu-box:9911 ...
```

Протокол — length-prefixed бинарные кадры по TCP, свой номер версии,
рукопожатие первым кадром:

| Кадр | Содержимое |
|---|---|
| `Hello` | версия протокола, версия бинаря, `dir_hash`, arch, список устройств узла |
| `Assign` | диапазон слоёв, dtype активаций на проводе (f32/f16/q8), параметры KV |
| `Prefill` | chunk hidden-состояний → hidden после диапазона |
| `Step` | hidden одного токена (или батча K токенов при спекуляции) → hidden |
| `KvOp` | reset / truncate_last(n) — ровно те операции, что нужны спекулятивному откату (`kv_cache.rs:883`) |
| `Logits` | только для узла с `head` |
| `Ping/Stats` | health, занятость, измеренная пропускная способность |

- **Идентичность:** координатор отвергает воркера с чужим `dir_hash` — у всех
  узлов буквально тот же файл (доставка файла — забота пользователя: scp/NFS;
  автоскачивание не в первой версии).
- **Реплики по сети (режим A)** не требуют протокола вовсе: воркер в этом
  режиме — обычный `cortiq serve`, координатор — роутер OpenAI-запросов по
  `/healthz` + свободным слотам. Это первая сетевая ступень.
- **Латентность честно:** при layer-split decode каждый токен платит RTT за
  границу сегмента. LAN ~0.2–0.5 мс × 2 границы ≈ ~1 мс/токен — на фоне
  25 мс/токен терпимо, но **спекулятивный батч радикально важнее по сети, чем
  локально**: DSpark уже драфтит 5 позиций и верифицирует батчем
  (`forward_batch_graph` + `SpecTail`) — K токенов за один RTT. Wi-Fi/WAN не
  обещаем и не оптимизируем.
- Безопасность: соединение только с `--token` (общий секрет в `Hello`), иначе
  слушаем только loopback. TLS — не в первой версии, честно сказано в доках.

### 3.5 Мобильные расширители (iPhone / Android)

Телефон — тот же воркер, что и любой узел, потому что кабель — это сеть:
USB-tethering у Android (RNDIS/NCM) и iPhone (NCM), USB3/Thunderbolt у
iPhone Pro (до 10 Гбит/с) — всё представляется хосту обычным сетевым
интерфейсом. **Транспортный код протокола §3.4 не меняется ни на байт**;
новое — упаковка воркера и планирование под асимметричное железо.

Пропускной способности хватает с запасом: при layer-split decode через границу
едет один hidden-вектор (единицы КБ на токен) — узкое место не полоса, а RTT,
и по кабелю он ниже, чем по Wi-Fi. Спекулятивный батч (K токенов за RTT)
обязателен, как и для любого сетевого сплита.

**Android — почти бесплатно.** Бинарь `aarch64-linux-android` уже собирается и
работает в Termux; пул уже учитывает big.LITTLE-топологию; NEON/SDOT-путь —
основной CPU-путь. `cortiq worker` в Termux + USB-tethering = готовый
расширитель. GPU на Android (Vulkan через wgpu) — отдельная проверка, но CPU
флагманов (16–24 ГБ RAM) ценен и сам по себе.

**iOS — воркер как библиотека.** Фоновые бинари на iOS невозможны, значит
воркер обязан быть библиотечным API, а не только CLI: ядро `cortiq-net`
оформляется как lib (`worker_serve(config)`), CLI — тонкая обёртка, FFI
получает аддитивный `cortiq_worker_start(json)`. Это правильная архитектура
независимо от iOS — но iOS делает её обязательной. Приложение-воркер
(TestFlight/dev-сборка для начала) встраивает staticlib `cortiq-ffi`;
GPU-путь — родной `gpu_metal.rs`, чей контракт UMA (`has_unified_memory`)
iPhone проходит по построению. Ограничения платформы фиксируются честно:
extended-memory entitlement для больших диапазонов слоёв, приложение живёт на
переднем плане (или в разрешённом фоновом режиме), троттлинг неизбежен.

**Планировщик и телефоны.** Бюджет телефона — измеренная *устойчивая*
производительность после прогрева, не пиковая (принцип «измерено, не
задекларировано» здесь буквально спасает план от развала через две минуты
декода). Кадр `Stats` расширяется полями thermal state и powered/battery;
при троттлинге координатор громко перепланирует — не тихо замедляется.
Лучшие роли телефона по измерению, в порядке ожидаемой пользы:

1. хвост слоёв при layer-split — чистое расширение памяти хоста;
2. реплика маленькой модели (data-parallel, Phase 3) — телефон обслуживает
   часть запросов целиком;
3. держатель холодных MoE-экспертов (expert-parallel, Phase 5) — редкие
   обращения прощают RTT.

### 3.6 UX-инварианты

- **Ноль конфигурации остаётся нулём конфигурации.** `cortiq run model.cmf`
  без флагов ведёт себя ровно как сегодня (одно лучшее устройство). Если модель
  не влезает — печатается измеренный план и запускается layer-split, вместо
  сегодняшнего OOM.
- Один новый флаг для 90% случаев: `--device auto | cpu | gpu:1 | gpu:0,gpu:1`.
- Тонкая настройка: `--split "gpu:0=22g,gpu:1=11g,cpu"` либо `--plan file.cmfplan`;
  `cortiq plan model.cmf --save` — построить и зафиксировать план отдельно.
- `cortiq devices` — инвентарь: имя, бэкенд, память, измеренная пропускная
  способность, стабильный ключ.
- Env-переменные продолжают работать; явный флаг всегда старше env (сегодня
  `cmd_serve` сам пишет `CMF_THREADS` — `main.rs:1726` — это учесть).
- FFI: только аддитивно — `cortiq_set_device_spec(json)` рядом с существующим
  `cortiq_set_gpu`; старый ABI не трогаем.

## 4. Гарантии совместимости

| Поверхность | Гарантия |
|---|---|
| Контейнер `.cmf` | Не меняется. Ни бита, ни секции, ни версии. Старые файлы ↔ новые бинари и наоборот — без оговорок |
| `python/cmf_reader.py` | Не требует правок |
| Однодевайсное поведение | `--device` не задан, устройств одно — идентичный сегодняшнему путь; CPU-путь бит-в-бит |
| `CMF_GPU`, `CMF_GPU_LAYERS`, `CMF_THREADS` и весь env-зоопарк | Работают; новые флаги — старше |
| C ABI | Только новые функции; существующие сигнатуры и семантика неизменны |
| `.cmfplan` | Удаляемый; без него всё пересчитывается; чужой — отвергается по `dir_hash` |
| Протокол воркеров | Своя версия в `Hello`; несовместимость — громкий отказ при рукопожатии |

Единственная правка формата — **аддитивная и опциональная**: в header-JSON
шардов ключ `shard.family` = hex `hash64` директории шарда 1, чтобы
`open_sharded` (а позже — координатор) мог проверить, что сиблинги от одного
семейства (сегодня сиблинги не проверяются ни по arch, ни по идентичности —
пробел, зафиксированный при инвентаризации). Старые ридеры ключ игнорируют
(serde без `deny_unknown_fields`), feature-бит не нужен.

## 5. Фазы

Каждая фаза самостоятельно полезна, сдаётся с числами и не блокирует релизы.

### Phase 0 — фундамент: устройство как значение (без нового поведения)

Самая большая по объёму и самая важная. Пользовательская фича на выходе одна,
но давно назревшая: выбор карты.

1. `DeviceId`/`DeviceInfo`/реестр; `ctx_for(dev)`, `ctx()` = устройство по
   умолчанию (`gpu_wgpu.rs:10072,10092,10149`; `gpu_metal.rs:3851`).
2. Ключи кэшей + probe + бюджеты получают измерение устройства
   (`gpu_wgpu.rs:9780,9800,9814-9845,9862`; `gpu.rs:208`).
3. Явный контекст исполнения вместо thread-local `CUR_LAYER`/`CPU_ONLY`
   (`gpu.rs:18-33`) — протягивается через фасад `gpu.rs` (у job-структур
   `GraphLayer`/`MoeJob`/`BatchJob` появляется поле устройства — сигнатуры
   ~60 функций фасада меняются механически).
4. `dsv4.rs`: 141 прямой вызов `gpu_wgpu::` получает параметр контекста
   (механика; поведение — бит-в-бит).
5. **GPU-адресация вторичных шардов**: `entry_abs_offset` → `(shard, off)` и
   ~10 bail-out'ов в `gpu_wgpu.rs`/`gpu_metal.rs` учатся брать буферы соседнего
   маппинга (`format.rs:823-825`; известный пробел из
   `PERFORMANCE_ROADMAP.ru.md` §4.9). Без этого любой большой (шардированный)
   файл молча падает на CPU — а именно большие модели и есть целевая аудитория
   мультидевайса.
6. CLI: `--device` у `run/serve/bench/ppl`, `cortiq devices` (расширение
   `Commands::Gpu`, `main.rs:1627`); флаги старше env.
7. Аддитивный `shard.family` в header-JSON + проверка в `open_sharded`
   (`format.rs:546-608`).

Приёмка: парити-тесты бит-в-бит со старым путём на одной карте; `--device gpu:1`
реально исполняет на второй карте (проверка по `adapter_report`); шардированная
модель держит веса на GPU. Perf-регрессий нет (in-process таймеры, A/B по
методике `OPTIMIZATION_ROADMAP.md`).

### Phase 1 — data-parallel на одном хосте

Слоты `serve` закрепляются за устройствами (`PipelinePool`,
`cortiq-server/src/lib.rs:23-76`): `CMF_SERVE_SLOTS=4 --device gpu:0,gpu:1` →
слоты 0,2 на первой карте, 1,3 на второй. Плюс наведение порядка в пулах
потоков (сегодня N пайплайнов × (cores−1) воркеров — oversubscription,
`pipeline.rs:1196`).

Приёмка: throughput сервера на 2×GPU ≥ 1.8× от 1×GPU на батче параллельных
запросов; изоляция состояния слотов (существующие маск/семплер-гарантии).

### Phase 2 — layer split на одном хосте (главная ступень)

1. `PlacementPlan` + жадный планировщик из байтов директории и измеренных
   бюджетов; `.cmfplan`, `--split`, `--plan`, `cortiq plan`.
2. Обобщение `layer_ranges` (`gpu.rs:72`) и цикла слоёв
   (`pipeline.rs:5245`, prefill `pipeline.rs:3393`) до сегментов по устройствам;
   передача hidden через host staging (peer-to-peer — потом, если измерение
   попросит).
3. Граф на сегмент: `try_token_graph_wgpu_steps` (`pipeline.rs:4094`) режется по
   границам плана — один submit на устройство на токен.
4. KV сегмента живёт на его устройстве (ключи уже пер-слойные).
5. `CMF_GPU_LAYERS` объявляется алиасом частного случая плана.

Приёмка: модель, не влезающая в одну карту, работает на 2×GPU (+CPU-хвост) с
tok/s ≥ уровня «одна GPU + CPU-оффлоад» сегодняшнего пути; парити логитов с
однодевайсным исполнением; спекулятивные пути (MTP/DSpark) работают поверх
сплита (откат KV — на каждом устройстве свой `truncate_last`).

### Phase 3 — реплики по сети

Роутер: `cortiq serve --peer host:port...` без загрузки модели локально —
прокси OpenAI-запросов по свободным слотам узлов (`/healthz` уже отдаёт
capabilities; добавить занятость слотов — `PipelinePool::n_slots()` написан и
не используется). `--token` для не-loopback. SSE-стриминг сквозной.

Приёмка: 2 узла ≥ 1.9× throughput; отказ узла → громкая ошибка запроса и вывод
узла из ротации, не тихий даунгрейд.

### Phase 4 — layer split по сети

Крейт `cortiq-net`: протокол из §3.4, `cortiq worker`, координатор считает
удалённые узлы устройствами `Remote(n)` в том же `PlacementPlan`. Спекулятивный
батч (K токенов за RTT) — обязательная часть приёмки, не опция.

Измерено (`spec-probe`, 2026-08): дешёвый вариант спекуляции — черновик
ранним выходом (норм+голова на hidden после L слоёв) — **мёртв на моделях,
не обученных под ранний выход**: nanbeige 0% приёмки всюду, кроме ровно
границы петли (9.4%), bonsai ≤1.6% до глубины 82% (там 32.8%, экономии
нет). Сетевой спекулятивный батч строится только на MTP-архитектурах либо
на компаньоне-черновике с тем же токенизатором.

Приёмка: модель, не влезающая в один узел, работает на двух по LAN; измеренная
цена RTT на токен опубликована в доках с числами; несовпадение `dir_hash` /
версии протокола — отказ при рукопожатии.

Архитектурное требование внутри фазы: воркер — библиотека (`worker_serve` в
`cortiq-net`), CLI `cortiq worker` — обёртка над ней. Это условие Phase 4b.

### Phase 4b — мобильные расширители (ИЗМЕРЕНО 2026-08-12)

Стенд: Xiaomi 12 Lite (SD778G, 4×A78 + 4×A55, 7.3 ГБ RAM, свободно ~2) на USB-C
и на Wi-Fi 5 ГГц ax рядом с MacBook M4 24 ГБ; настоящий `cortiq worker` в обе
стороны. Полный разбор для приложения — `MOBILE_SPLIT.ru.md`.

**Приёмка провалена ровно так, как была написана — и это результат.** Телефон по
кабелю НЕ добавляет хосту полезного диапазона слоёв: bonsai 1.7B идёт 28.6 tok/s
на Mac, 14.3 на телефоне, 14.0 пополам по USB. Роль честно понижена, но не до
реплики, а до **противоположной**: ценность телефона не в том, что он отдаёт
мощность десктопу, а в том, что он её берёт.

1. **Android — сделано, кода не понадобилось.** `aarch64-linux-android` +
   `cortiq worker`; `adb forward`/`reverse` заменяет USB-tethering на время
   отладки. 34.7B q2tp (12.9 ГБ) с координатором на телефоне: **16.3 tok/s** при
   2 ГБ свободной памяти — модель, которой на аппарате быть не может.
2. **Голова на воркере (wire v5) — сделано.** Голова не уменьшается со сплитом и
   стоила 29 мс из 73 мс токена; с `--peer-head` она уезжает к пиру, обратно едет
   id токена: bonsai 12.6 → **27.3 tok/s**, 34.7B 9.1 → **16.3**. Провод на токен
   16 байт. Парити побайтное при одинаковом бэкенде сторон.
3. **`cortiq_worker_start(json)` / `cortiq_set_peer(json)` / `cortiq_peer_stats()`
   — сделано.** Условие фазы «воркер — библиотека» выполнено; iOS-приложение
   больше ничем не блокировано, кроме своей сборки.
4. **`Stats` — сделано** (`nodestat.rs`): термозона, питание, текущая и пиковая
   частота быстрейшего ядра, свободная память. Каждое поле `Option`: «неизвестно»
   и «ноль» — разные значения для планировщика (проверено на живом устройстве:
   `/sys/class/power_supply` шеллу закрыт, и поле честно пустое).

**Главный незапланированный вывод — DVFS, а не термика.** При 36 °C и без
троттлинга один и тот же воркер отдавал свой диапазон то за 22.6 мс, то за
42.4 мс: `schedutil` не разгоняет большие ядра под задачу, которая считает
единицы миллисекунд и блокируется на сокете (cpu4 держался на 691 из 2400 МГц).
Планировщик обязан читать `cpu_khz_cur/max`, а не температуру. Лечение — ADPF
(`APerformanceHint_createSession` + `reportActualWorkDuration`), для чего в ABI
уже есть `cortiq_worker_tids()`.

Побочно закрыт вопрос про раскладку потоков: пул уже размеряется по большим
ядрам, явный пиннинг даёт +0.3% (шум), а отпустить его на все 8 ядер — −28%
(14.3 → 10.3 tok/s). Числа `run` для этого сравнения непригодны: холодный старт и
холодный губернатор дали ложные +16%, видимые только в `bench --json`.

Осталось в фазе: спекулятивный батч (нужен драфт — модель с MTP-головой, на
стенде их нет), передача KV между сторонами (цена посчитана: ~114 КБ на позицию,
1800 токенов ≈ 200 МБ = 5.7 с по кабелю против 14 с по Wi-Fi), термотест на
10 минут, и громкая ошибка на отключение кабеля.

### Phase 5 — tensor/expert-parallel (только по измерению)

Обобщение сплита `qtensor.rs:1112-1173` до N устройств; раскладка MoE-экспертов
по устройствам. Каждый включатель — за probe-гейтом; на интерконнектах, где
синхронизация дороже выигрыша, режим не включается сам.

Приёмка: измеренное снижение латентности на токен на конкретной паре карт;
нулевая регрессия там, где режим не включился.

### Сквозное (во всех фазах)

- Спека: `CMFPLAN_SPEC.md` и `CORTIQ_WIRE_SPEC.md` пишутся вместе с кодом —
  «один канон», реализуемый из спеки без чтения Rust (тот же контракт, что
  `cmf_reader.py` для контейнера).
- CI-мультидевайс без второй карты: cpu+gpu как два устройства; два логических
  wgpu-device на одном адаптере; loopback-воркер на localhost.
- Каждая фаза — отдельное обсуждение дизайна до кода (`CONTRIBUTING.md:17-19`)
  и запись в `CHANGELOG.md`.

## 6. Анти-скоуп

- **Никаких изменений конверта/секций/версии формата.** Раскладка под конкретное
  число устройств в `.cmf` не пишется никогда (урок GGUF с target-specific
  layout — `PERFORMANCE_ROADMAP.ru.md` §4.1).
- **Никаких NCCL/MPI/CUDA-зависимостей** в core/engine.
- **Никакого тихого фолбэка** при недоступном устройстве/узле.
- **Никакого «поддерживаем кластеры»** в README до того, как admission control
  и continuous batching (этапы 5.x перф-роадмапа) не сделают серверный слой
  честным перед такой формулировкой. Сравнения с upstream multi-GPU — только
  после собственного scheduler'а (§12.1).
- WAN/Wi-Fi-оптимизации, автодоставка файла на узлы, TLS, гетерогенные версии
  бинарей в одном кластере — не в этой итерации; всё перечисленное отклоняется
  громко, а не работает плохо.
- **Мобильное — без обещаний платформе.** App Store-дистрибуция iOS-воркера,
  работа от батареи без кабеля, фоновая работа в обход правил iOS — вне скоупа.
  Телефон-расширитель — это устройство на кабеле и питании; всё остальное —
  когда (и если) измерения покажут смысл.
