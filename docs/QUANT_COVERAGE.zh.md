*语言：[English](QUANT_COVERAGE.md) · [Русский](QUANT_COVERAGE.ru.md) · **中文***

状态：基于 0.5.65+wip 的代码审计，2026-08-10。以文中的 file:line 引用为准；

动机："优化不能只针对一种格式"。下面是一张实测得出的图：哪种 dtype 实际在

## "内核已有——调用处挡掉了"的缺口（按修复成本排序）

1. ~~`q1_parts` 中的 Q2TiledP 在 `proj_abs` 中没有内核~~——已修复。
2. ~~Q4Tiled 解码 matvec 没有分派器~~——已修复：`gpu::q4t_matvec`
   + 探测分支（Metal；wgpu——在出现独立显卡的 q4t 测试平台之前如实拒绝）。
3. Q4Block 的 Metal 逐算子：`gpu.rs:1001 Metal=>false`，而
   `encode_q4b_matvec` 是可用的——q4b 模型独立的 lm_head 得不到加速。
4. wgpu `matvec_batch` 中的 Q4t/Q4tp：`BatchLayout` 已建模，Metal 能执行，
   wgpu 却拒绝整个批次（gpu_wgpu.rs:20134）。
5. ~~`gpu_batch_job` 只认识 Q8/Q1~~——已修复：增加 Q4t/Q4tp 分支（原始
   激活，缩放放在负载中）；以 OpClass::Batch 进行的探测仲裁如实保留胜者
   （在 M4 和 M1 上探测选择了 CPU——这条路由面向 Metal 批处理能摊薄开销的
   配置）。
6. ~~批处理/预填充图中的 q2tp-MoE~~——已修复（2026-08-10），使用
   Qwen3.6-35B-A3B-Escha-W2 一致性预言机（parity oracle）：构建器获得了
   token 图的 q2tp 阶梯（gu_q2 贯通），逐位置通道分支为
   gu_q2 → `moe_gate_up_q2tp` + 精确的 `moe_down_q4tp`（与链式路径成对），
   整块 q4tp 通道**显式**排除 gu_q2（混合配置的 q4tp=true——没有 `!gu_q2`

   `expected_nbytes(Q2TiledP)` 计算。CPU⇔wgpu 输出逐字节一致，没有 bgraph
   拒绝，151/151 个测试通过。有意**没有**接入：
   `bt_moe_gate_up_q2tp(_r4)`——整块 2 位变体仍是一项优化，有自己的 mg 布局
   （逐位置通道位于同一次提交中）；以及草稿级的 `moe_down_q2tp_b`
   （DSpark 级别，"不要求逐位一致"）——按精度契约不适合主路径。
7. `moe_parts` 不接受 Q2TiledP/Q1T/Q4Block；`MoeJob` 没有 q2tp 标志——
   常规 MoE 路径绕过了现有的 wgpu 内核。
8. `matvec_silu_mul`：~~Q1~~ 已修复（使用共享组和的融合分支；M1 worker 上
   bonsai 9.0→7.5-7.9 ms/token，−14%）；~~Q8Row~~ 已修复（可移植的

   检查点）。Q8_2f 是**有意**排除的：它的列字段按张量预缩放激活，破坏了共享

   内核"一节）。
9. `matvec_many` 不支持 Q4Tiled/Q2TiledP；`matvec2_many` 支持的更少。
10. `moe_gate_up_many`/`moe_down_many`——只支持 Q4TiledP。
11. Metal `q8_matvec`/`q8_2f_matvec`——只用于测试；解码只能通过混合切分的
    `q8_matvec_range` 用到 Metal q8。
12. Q1-MoE：wgpu 拒绝（19951），Metal 执行；注释"q2tp down 不存在"
    （11341）已过时——`moe_down_q2tp_b` 是存在的。
13. `GraphW` 的文档注释把 kind 码写错了（gpu.rs:723 写着"2=q4_tiled"，实际上

## 在测试平台上获得的实践经验（27B q4tp，M4 24GB + M1 16GB）

- Metal 块图会**完整执行** q4tp/GDN（计划 32 项，层 0..64）——"图只用于
  q1"是 `q1_parts` 这个名字造成的误解。
- `hd=256` 默认关闭设备端注意力 → 每个 token 16 次夹层（sandwich）同步；

- 换页（paging）会掩盖一切：只有当层段能完全驻留时，测量才有效（见测试
  平台笔记）。

## 共享命令缓冲区中的 Metal-MoE——已实现（2026-08-10）

下面的规格已经落实：`moe_topk_select`（MSL，单元预言机
device==`moe_route`，含 tie-break 和两种 norm 模式）、token 图各层中的
`MetalFfn::{Dense,Moe}`、`encode_post_moe_ffn`（addnorm → f32 路由器 →
select → gate/up 作业（按配置为 q4tp/q2tp） → moe_silu → down 作业 → 加权
归约 → axpy——全部在共享命令缓冲区中）、构建器 `metal_moe_graph_parts`，并
如实拒绝不支持的情形（sigmoid/bias/τ 路由器、掩码、逐专家缩放、
router_input_norm、非 Silu——走 CPU）。

设备端注意力策略被移到计划扫描**之后**：hd>128 开关是在稠密模型上测得的，
而 MoE 计划会把结论反过来——每个 CPU 注意力夹层都要付出 commit+wait。实测
（W2 q2tp-MoE 34.7B，M4，稳态解码，bench --json）：夹层 14.7 tok/s，设备端
注意力 **24.8–27.1 tok/s**，纯 CPU 18.8。每 token 提交次数 39.8 → 27.4（计入
预填充摊薄）。稠密模型的策略不变。

回归矩阵：bonsai q1（文本 ==，95.8 tok/s）、nanbeige q4t（文本 ==，17.7）、
W2 q2tp-MoE（图 + CPU 注意力：与精确 CPU 的文本 48/48 ==，confidence 漂移
0.098，处于其自身 CPU 包络 i8↔exact 0.11 之内；设备端注意力在第 32 个 token
出现分歧——属于先前已有旋钮的漂移类别，而不是 MoE 分支的），引擎测试
253/253。

未解决：**35B q4tp（17.8 GB）超过 M4 的 Metal maxBufferLength（13.6 GB）**——
无法为该文件创建 no-copy 缓冲区，这个文件上的整个 Metal 路径（逐算子和图）
都不可用；W2（12.9 GB）放得下。后续工作：用按层段划分的缓冲区窗口代替整个
文件——网络切分同样需要它（每一端只映射自己的层段）。

## 设计：共享命令缓冲区中的 Metal-MoE（已执行的规格）

动机，在 35B-A3B q4tp（M4）上实测：CPU 11.6-12.1 tok/s，Metal 9.8-11.0——
而总线上限约为 30-60 tok/s（每 token 约 1.9 GB 活跃权重）。差距在于编排：
逐算子 MoE 在**每一层**都执行 commit+wait_until_completed（约 30 × 约
1.3 ms），因为该层的路由由主机上的 CPU 计算。解决办法是把整个 token 放进一个
命令缓冲区：

1. **MSL `f32_matvec`**（路由器：n_exp × hidden，f32 kind-4）——如果还没有；
   先检查现有的简单内核。
2. **MSL `moe_topk_select`**——由 logits[n_exp] 得到：top-k 索引 + softmax
   权重 + 共享门的 sigmoid（wgsl `moe_select` 的对应实现，
   gpu_wgpu.rs:~15864）；k ≤ 16，n_exp ≤ 256，一个 threadgroup。
3. **TokenGraph：`q1_graph_gpu` 计划中的 `Item::MoeFfn`**（去掉扫描中的
   `FfnKind::Dense` 闸门）：norm → router → select → 作业内核
   （`q4tp_matvec_jobs`/`q2tp_matvec_jobs`——已有） → `moe_silu_jobs` →
   down 作业 → `moe_reduce`（已有）——全部只编码而不提交；只在原本就有同步
   的地方同步（CPU 注意力夹层/最终回读）。缓冲区使用：sel/act/eo——通过
   io_bufs，与 `moe_block_jobs_q4tp` 相同。
4. 一致性预言机已就绪：W2（q2tp）和 35B-q4tp，CPU⇔Metal 文本。
5. 预期：省掉每 token 30-40 ms 的同步 → Metal ≥ CPU；此后只有内核才能推高
   共同上限（设备上的 scales_into 缓存已经存在——位于 threadgroup 内存中的
   阶梯）。

风险：q1 旗舰（35B Qwen3.5 q1）走的是同一个计划——不允许出现回归；MoE 分支
不得触碰 Dense 路径。需作为单独一轮工作，并跑完整的回归矩阵（bonsai q1、
nanbeige q4t、27B q4tp-dense、W2 q2tp-MoE、35B q4tp-MoE）。

## 独立显卡上的解码剖析（2×RTX 5090，2026-08-11）

使用 `CMF_GPU_TS=1`（逐帧 GPU 剖析器）在 W2 34.7B 上测量，hidden 2048，
40 层，top_k 8 + shared：

| 阶段 | µs/token | 每层 |
|---|---|---|
| GDN 混合（30 层） | 1949 | 65 |
| MoE-FFN（40 层） | 2717 | 68 |
| 注意力混合（10 层） | 767 | 77 |
| 尾部（norm+lm_head） | 189 | — |
| **GPU 合计** | **5630** | |

完整 token 为 8.3 ms，对应 121 tok/s——即约 2.7 ms 花在设备之外。

**解码并不受限于权重。** `CMF_TOPK_PROBE` 从 8 改为 4（专家运算量减半，分派
次数不变）只让时间变化 3%。1.9 GB 活跃权重的总线上限约为 1.1 ms——我们离它
还差 5 倍，差距被启动延迟吃掉：hidden 为 2048 的一层只有 30-70 µs 的工作量，
而这张卡需要成千上万个工作组才能填满。

**逐分派分解（`CMF_GPU_TS=2`，每种层各取一层）：**
GDN——proj 39 µs、outp 16、step 11、conv 6、snorm 5；注意力——attend 24、
qkv 17、wo 14、rope 13、kv 4、gate 4；MoE——router 16、select 13、down 14、
gate/up 13、pre 9。**最便宜**的分派也要 4-6 µs——这是启动开销的下限，每层约
15 次分派 × 40 层，它吃掉大约三分之一的 token 时间。

**旋钮都已检查——默认值已是最优，不必重新研究：**

| 旋钮 | 值 | 实测（W2，5090） |
|---|---|---|
| `CMF_MV4` | 1（默认） | 124.0，设为 0 时为 77.7 tok/s |
| `CMF_MOE_FOLDSEL` | 0（默认） | 120.7，设为 1 时为 100.4（此时输出逐字节相同——路径正确，只是更慢） |
| `CMF_SLOTS_PER_GPU` | 1（默认） | 210，设为 2 时为 185 tok/s |
| `CMF_BATCH_K` | 0（默认） | 129.9，设为 128 时为 128.2——批处理图对该模型没有帮助 |
| `CMF_COOP` | 1（默认） | GEMM 51.9，设为 0 时为 25.0 TFLOP/s |

由此得出下一步的杠杆，按实测价值从高到低：

1. **序列批处理（continuous batching）。** 填满 SM 的唯一办法：一次提交计算
   B 条独立序列。需要图中有逐序列的 KV 镜像（目前的键是 `(kv_id, layer)`——
   已经接近所需）。作为替代方案**已检查并否决**：每张卡两个槽位得到
   185 tok/s，而一个槽位为 210（`CMF_SLOTS_PER_GPU`）——槽位在争抢队列，而
   不是相互重叠。
2. **图的 bind group 缓存。** 每个 token 12,617 次分配，而 CPU 路径只有 363
   次——这些是每个 token 都重新创建的 wgpu 对象（uniform 已经按内容缓存，
   bind group 还没有）。设计：在 `forward_token_graph` 内部辅助函数
   `bg(...)` 的 35 个调用点上使用键 `(site_id, layer)`，再加一个代数计数器，
   由 `Scratch::ensure` 在重新创建缓冲区时递增。出错的代价是悄无声息的错误
   字节，因此必须在每个模型上配合一致性闸门来做。
3. **切分模式下的预填充**：每个位置两次提交，而不是一次（67.8 对
   156.6 tok/s）。解决办法是按位置对分段做流水线——分段 1 计算位置 p 时，
   分段 0 处理 p+1。

## 为什么探测可能把扩散模型留在 CPU 上（2026-08-11 实测）

症状：在 MiniMax-DiT 中，`out` 投影（5376×7168）每步耗时 9.8 s，而同一个
内核在相同形状上只需 8.4 ms（内核测试 `wgpu_q4tp_mm_throughput`，
53 TFLOP/s）。它**没有**到达设备。

机制是探测的两个特性叠加在一起：

1. **冷的 GPU 样本被丢弃。** 在扩散模型中，每一层每步只被访问一次，因此在
   **第一**步，每个 GPU 测量都被标记为冷（正在上传权重）而不计入。探测始终
   收集不到 GPU 分支的数据，于是继续在各分支之间交替。
2. **交替计数器按类别共享，并按调用顺序递增。** 一个块中恰好有两个参与
   仲裁的 GEMM（qkv、out）：qkv 总是偶数，out 总是奇数——于是整个第一步中
   `out` 都落在 CPU 分支上。

实测结果：第 1 步——9.8 s，第 2 步——2.8 s（权重已热，裁决已作出）。也就是
说，这是每次渲染约 7 s 的一次性代价，而不是系统性的。

提前裁决的阈值从 3× 降到 2×（这里的差距是 2.8×）——这**没有**修复该情形
（第 1 点在起作用），但在胜者明显时消除了不必要的交替。真正的解决办法：
探测期间如果权重尚未驻留，优先选择 GPU 分支（反正后续步骤也需要上传）——
为此已经有 `probe_resident_or_upload`。

## 视频的下一个杠杆：张量核心上的注意力（估算）

在迁移 FFN 并修复探测之后，MiniMax-DiT 的单步剖析（512×288，RTX 5090，
`CMF_MMH3_PROF`）如下：**注意力 7.5 s（40%）**，qkv 3.0，out 3.0，fc1（融合
FFN）约 5。

每个块的注意力运算量：n=1859，nh=42，hd=128 →
QK = 2·nh·n²·hd ≈ 37 GFLOP，PV 相同。50 个块每步约 3.7 TFLOP，耗时 7.5 s——
即 **0.5 TFLOP/s**，而同一张卡上的 q4tp-GEMM 内核测试能达到
**51.9 TFLOP/s**。差距不在总线（q/k/v 每块约 120 MB，整个渲染约 1.6 s），也不
在启动次数（每块 126 次分派 ≈ 每步 31 ms）——而在于 `dit_qk`/`dit_pv` 是标量
f32 内核，不是矩阵内核。

设计：后端**已经有**协作式 f32 GEMM（`gemm_nt_coop`，`gemm_nt_f32` 使用
它）。需要为它增加一个基于设备缓冲区的入口：

1. QK：q_h [n×hd] × k_h [n×hd]ᵀ → scores——正好是 NT 形式，无需转置。
2. 按行 softmax——保持原样（`dit_softmax`）。
3. PV：scores [n×n] × v_hᵀ [hd×n]——需要 vᵀ；要么在主机上准备（那里本来就把
   v 收集成 head-major，是同一遍处理），要么增加一个转置内核。
4. 闸门：与当前路径做帧一致性对比（阈值 3.4%——CPU↔GPU 包络），外加针对
   注意力形状的内核测试。

按运算量估计：每步 7.5 s → 1-2 s，即渲染 127.8 → 约 100 s。

**2026-08-11 已验证——前提被证明是错误的。** 内核已写好
（`DIT_COOP_SRC`/`dit_gemm_coop`，由 `CMF_DIT_ATTN_COOP=1` 开启），通过矩阵
核心计算的 QK **正确**（帧一致，差值 0.000），但单步时间没有变化：注意力
7.5 s 对 7.6。也就是说，注意力**并不**受限于 QK 运算，"0.5 TFLOP/s"的估计测的
并不是实际耗时的部分。仍然可疑的部分，按可能性从高到低：

1. **Softmax**：每块 nh·n² = 1.45 亿个元素，每行一个工作组——每块 7.8 万个
   组，每步 390 万个。
2. **上传 q/k/v 并回读面板**：每块 160 MB，每步 8 GB。
3. **分派**：42 个头 × 3 遍 × 50 个块 = 每步 6300 遍（按 4-6 µs 的下限约为
   30 ms——不多，但不是零）。

**已拆分（2026-08-11）。** 分别为主机端重排（repack）和设备调用设置了
计时器：注意力阶段的 7.3 s 中，**4.4 s 是主机上的重排**（从交错的 qkv 组装
head-major 的 q/k/v），只有约 2.9 s 是设备本身。也就是说，瓶颈**不在**内核，
也不在运算，而在 CPU 上的数据准备——这恰恰是前一次尝试（coop-QK）从原理上
就无法加速的部分。

已写好内核 `dit_qkv_split` 和入口 `dit_attention_packed`：qkv 作为一整块传到
显卡，并在**那里**按头拆开。已在 64×32 上验证（渲染正确），尚未在完整尺寸上
测完——因此需要显式开启：`CMF_MMH3_ATTN=split`。待完成：512×288 的测量 +
帧一致性，如果成立就设为默认。

先前的可疑项清单（softmax、流量、分派）保留，用于剩下的约 2.9 s：在
dit_attention 内部使用 `CMF_GPU_TS=2`，或做一个关掉 softmax 的简单 A/B（输出
必然错误，但时间是真实的）。该内核保留在开关之后——它是正确的，等瓶颈真的
出现在我原先设想的地方时会派上用场。

## 迁移重排之后注意力中还剩什么（2026-08-11）

现在默认在**显卡上**按头拆分 qkv（`dit_qkv_split`）：重排 4.4 → 1.5 s，渲染
130.0 → 111.8 s，帧逐位一致。

剩下的设备端部分是**每步 5.2 s**（占单步的 29%）。在**去掉**重排之后重新
测量 coop-QK，结果仍然持平（5.2 对 5.3）——也就是说，无论怎样安排，QK-GEMM
都不是瓶颈。因此剩余部分在 softmax（nh·n² 个元素，每行一个工作组 → 每块
7.8 万个组）和/或 PV 中。

**已拆分（`CMF_DIT_ATTN_PROF=1`，512×288）：**

| 遍 | 秒/步 | 占比 |
|---|---|---|
| QK | 1.65 | 22% |
| softmax | 0.97 | 13% |
| **PV** | **4.76** | **64%** |

在**相同** FLOP（都是 n²·hd）下，PV 比 QK 贵三倍——所以问题不在运算，而在
访存：它的右操作数 `v` 按 [n][hd] 存放，而 GEMM 按列、零散地读取它。QK 没有
这个问题，因为 k 的存放方式正好符合 NT 乘积的需要。

解决办法（按成本排序）：每个块在设备上把 v 转置一次（n·hd 个元素——与
n²·hd 相比微不足道）为 [hd][n]，之后 PV 就和 QK 一样成为普通的 NT 乘积，而且
还能直接使用已经写好的 coop 内核 `dit_gemm_coop`。预期：4.76 → 约 1.5 s，即
单步 18.9 → 约 15.6，渲染 111.8 → 约 95 s。

**PV 改用 NT：更快，但暂时不正确（2026-08-11）。** 转置被移到单独的模块中
（自动布局**按入口点**构建，并会重新编号绑定——只用到部分绑定的内核无法
绑定）。之后该路径开始工作，带来 **PV 4.76 → 2.82 s（1.7×）**，但帧出现了
59% 的偏差：NT 形式把归约宽度取为 `cols4 * 4`，而 PV 沿 n = 1859 归约，被
截断为 1856，悄悄丢掉了每行得分的三列。已加上闸门（`n % 4`），该路径仍在
`CMF_DIT_PV_COOP=1` 之后。要启用它：在 `cols4` 之外把真实的 k 传给内核（步长
仍按 cols4，循环边界按 k），然后核对帧并移除开关。收益已由测量确认，这是
正确性问题，而不是思路问题。

这正是"先拆分，再写代码"这条规则的例子：在拆分之前写的两个内核都正确却
无用，而拆分只花了一个开关和一次运行。

## 所有迁移完成后的 DiT 单步剖析（2026-08-11，最终）

统计已修正（槽位 2 和 3 测的是同一份工作——14.1 s 的单步被读成了 26.1；各
槽位之和现在与外部计时器一致）：

| 阶段 | 秒/步 | 占比 |
|---|---|---|
| fc1（融合 FFN） | 5.1 | 36% |
| qkv | 3.2 | 23% |
| out | 2.8 | 20% |
| 注意力（QK+softmax+PV） | 2.2 | 16% |
| 其余 | 0.8 | 5% |

**注意力已不再是主要开销**——主要开销是投影。而且它们与内核之间存在差距：
qkv 每块 430 GFLOP，每步 21.5 TFLOP，耗时 3.2 s = **6.7 TFLOP/s**，而同形状的
内核测试能达到 51-61。差距不在内核，而在**每次**调用的外围开销：

- 回读 y：1859×21504×4 = **每块 160 MB**，每步 8 GB；
- 上传 x：每块 40 MB；
- 解包平面：每块 1.15 亿个元素（明显，但是次要的——在 b=1859 时它只占 GEMM
  工作量的 1/1859）。

也就是说，代价来自粒度：每个 GEMM 都是一次单独的总线往返。缓存解包后的平面
没有用（这个模型的平面共有 38 GB），也没有必要——问题不在它们。

**设计修正（已对照代码核实）。** 不能"只是把缓冲区直接传下去"来去掉 qkv 的
回读：在 GEMM 和注意力之间，主机会对 q 和 k 施加归一化和 RoPE
（`norm_rope_w`，mmh3.rs:866）——只要这一步还在 CPU 上做，数据就必须回到
主机。所以工作顺序与直觉相反：先在设备上实现 qk-norm+RoPE 内核（它同时省掉
qknorm 槽位的 0.4 s），之后不回读 qkv 缓冲区才有意义。第二步所需的机制已经
存在——`q4tp_matmat_dev`（带可选回读的 tp_matmat）。

**内核 `dit_qknorm_rope` 已写好并被设备接受**（2026-08-11）。草案中的陷阱
不是在着色器内部解决的，而是在外部：WGSL 不能把 storage 绑定作为参数传入，
因此同一个内核被调用**两次**——q 和 k 的区别在于输出平面、权重和 `src_off`
的绑定。剩下的工作：从 mmh3 向它提供角度和权重，把 `norm_rope_w` 从主机上
去掉，并让 qkv 留在显卡上（机制是 `q4tp_matmat_dev`）。下面是它所依据的
形式：每个（token，头）对一个工作组，64 个线程；归一化需要沿 hd 归约，因此
不能每个线程处理一个元素。把该头的切片加载到工作组内存中，用树形归约求平方
和，乘以 1/sqrt(ss/hd + eps) 和归一化权重，把前 `pairs` 个元素与其配对元素
一起旋转，写入平面。v 是不做归一化的普通分散写入。主机语义
（`mmh3::norm_rope_w`）：求和用 f64，旋转 `x[j], x[j+pairs]`，角度按 token
计算；设备上用 f32 就够了（归一化用的是比值，hd = 128 个值）。**重要**：q 和
k 经过同样的变换，但使用**不同**的权重、写入**不同**的平面——辅助函数必须
同时接收输入和输出，否则 k 会悄无声息地保持未处理状态。

**下一轮的设计：整个 DiT 块驻留在设备上。** x 只进入块一次，qkv → 注意力 →
out → FFN 都在设备缓冲区中计算，只有块的结果被输出。这样每块可省掉约
200 MB 流量（每步 10 GB），并把四次往返变为一次。按运算量估计：投影 11.1 s →
3-4 s，单步 14.1 → 约 7，渲染 106.9 → 约 70。闸门相同：与当前路径做帧一致性
对比（包络 3.4%）。

## 视频的下一步：VAE 解码器中的驻留链

将主机循环并行化之后的 VAE 剖析（`CMF_VAE3D_PROF=1`，2 步，512×288，
RTX 5090）：共 26.1 s——ffn 7.1 · qkv gemm 5.3 · 注意力 5.3 · out gemm 4.4 ·
repack+rope 3.2 · 归一化 0.5。

这正是 DiT 中通过融合 `dit_qkv_attn_out` 消除掉的那种结构（链条每步
13.8 → 7.5 s，−46%）。这里可比的部分是 qkv + repack + 注意力 + out = 26.1 中
的 18.2 s。

妨碍直接复用 `dit_qkv_attn_out` 的是三处差异，每一处都可以检验：

1. **面板布局。** DiT 中每个 token 是 `[q(inner) | k | v]`，VAE 中则按头
   交错：`p*3*dim + h*3*hd` 得到 `[q_h | k_h | v_h]`。`dit_qkv_split` 内核
   需要的是 uniform 中的布局标志，而不是新内核。
2. **qkv 的偏置。** DiT 没有，VAE 在 GEMM 之后加上。最便宜的做法是在同一个
   `dit_qkv_split` 中加，反正只有它读取整个面板。
3. **不带权重的归一化。** `rms_norm_plain`，而 DiT 是带权重的。
   `dit_qknorm_rope` 内核计算 `x*inv*w`，因此一个全 1 缓冲区就能给出相同的
   结果——不需要新内核，只需要一个缓冲区。

顺序与在 DiT 中奏效的相同：先把该阶段拆分为主机端和设备端（已完成——见上面
的剖析器），然后再写内核。而且两个分支都只在 `CMF_GPU_PROBE=0` 下测量，否则
比较的是仲裁的随机结果，而不是改动本身。

## Qwen3.6 27B：token 的时间花在哪里（2×RTX 5090，`CMF_GPU_TS=1` 实测）

固定分支（`CMF_GPU_PROBE=0`）的基线：预填充 53.6 tok/s，解码 43.9——波动
±1%。整 token 图处于**激活**状态，在自动显存预算下模型完全驻留（强制设为
8 GB 会让它慢六倍——7.0 tok/s，这只是一项检查，不是工作模式）。

设备上一个 token 耗时 17.6 ms，层栈是混合的（48 个 GDN 层 + 16 个全注意力
层）：

| 阶段 | 时间 | 层数 | 每层 | 占比 |
|---|---|---|---|---|
| GDN 层的 FFN | 6.69 ms | 48 | 139 µs | 38% |
| GDN 混合 | 5.93 ms | 48 | 123 µs | 34% |
| 注意力 | 2.40 ms | 16 | 150 µs | 14% |
| 注意力层的 FFN | 2.20 ms | 16 | 138 µs | 12% |
| 尾部 | 0.42 ms | 1 | | 2% |

**matvec 不是杠杆，这是对我自己先前估计的更正。** 起初我根据猜测的维度计算
带宽，得到"543 GB/s，上限的三分之一"。真实维度——hidden 5120，64 层，文件
14.26 GB——意味着每层约 148 MB 的 FFN 权重，因此 139 µs 对应 **约 1.07 TB/s**，
而标称值约为 1.7。对一个实时解包的真实内核来说，达到峰值带宽的百分之六十三
已经是不错的水平，而不是余量。

旋钮的结果也证实了这一点：`CMF_MV4=0`（单行内核）只有 14.1 tok/s，而四行
内核为 44.2；十六行的 `q4tp_matvec16w` 对这些权重**已经会被**自动选中。这一
部分已经调优到位。

**杠杆在于主机开销：每个 token 20,134 次分配**（bind group），以及设备
（17.6 ms）与墙钟（20.3）之间 2.7 ms 的差距——token 时间的 13% 花在显卡之外，
而且是在一个已经整体提交的图之上。这正是 bind group 缓存那项任务，现在它的
代价可以用 token 来衡量，而不只是分配次数。
