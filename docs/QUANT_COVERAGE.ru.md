Статус: аудит кода на 0.5.65+wip, 2026-08-10. Единица правды — ссылки
file:line в тексте; при расхождении с кодом прав код, документ чинится.

Мотив: «оптимизация не для одного формата». Ниже — измеренная карта того,
какой dtype на каком пути реально исполняется, и полный список щелей
двух сортов: «кернел есть, вызов отсекает» (дёшево чинить) и «кернела

## Щели «кернел есть — вызов отсекает» (по цене починки)

1. ~~Q2TiledP в `q1_parts` без кернела в `proj_abs`~~ — починено.
2. ~~Q4Tiled decode-matvec без диспатчера~~ — починено: `gpu::q4t_matvec`
   + probe-арм (Metal; wgpu — честный отказ до появления дискретного
   q4t-стенда).
3. Q4Block Metal per-op: `gpu.rs:1001 Metal=>false` при живом
   `encode_q4b_matvec` — standalone lm_head q4b-модели не ускоряется.
4. Q4t/Q4tp в `matvec_batch` wgpu: `BatchLayout` смоделирован, Metal
   исполняет, wgpu отклоняет весь батч (gpu_wgpu.rs:20134).
5. ~~`gpu_batch_job` знает лишь Q8/Q1~~ — починено: армы Q4t/Q4tp
   (сырые активации, скейлы в payload); арбитраж пробой OpClass::Batch
   держит победителя честно (на M4 и M1 проба оставила CPU — маршрут
   для конфигураций, где Metal-батч амортизируется).
6. ~~q2tp-MoE в батч/префилл-графе~~ — починено (2026-08-10) с
   парити-оракулом Qwen3.6-35B-A3B-Escha-W2: билдер получил
   q2tp-лестницу токен-графа (gu_q2 сквозной), пер-позиционная полоса
   ветвится gu_q2 → `moe_gate_up_q2tp` + точный `moe_down_q4tp`
   (пара chain-пути), полно-чанковая q4tp-полоса ЯВНО исключает
   gu_q2 (у смешанного профиля q4tp=true — без `!gu_q2` она молола
   бы q2tp-байты q4tp-кернелом), GU-страйд юниформа по
   `expected_nbytes(Q2TiledP)`. Вывод CPU⇔wgpu побайтно совпал,
   отказов bgraph нет, 151/151 тестов. Заведомо НЕ подключены
   `bt_moe_gate_up_q2tp(_r4)` — полно-чанковый 2-битный вариант
   остаётся оптимизацией со своим mg-лейаутом (пер-позиционная
   полоса живёт в том же submit), и черновой `moe_down_q2tp_b`
   (DSpark-грейд, «не обязан совпадать бит-в-бит») — в основной
   путь не годится по контракту точности.
7. `moe_parts` не принимает Q2TiledP/Q1T/Q4Block; у `MoeJob` нет
   флага q2tp — обычный MoE-путь мимо существующих wgpu-кернелов.
8. `matvec_silu_mul`: ~~Q1~~ починено (fused-арм с общими групповыми
   суммами; M1-воркер bonsai 9.0→7.5-7.9 мс/ток, −14%); ~~Q8Row~~
   починено (портируемый `q8_row_dot` c оракул-тестом fast==scalar;
   бенч ждёт q8-чекпойнта на стенде). Q8_2f исключён ОСОЗНАННО: его
   колоночное поле прескейлит активации по-тензорно и ломает контракт
   общего split_act — остаётся двухпроходным. Q2TiledP — без CPU-i8
   кернела вовсе (см. «бескернельные»).
9. `matvec_many` без Q4Tiled/Q2TiledP; `matvec2_many` ещё уже.
10. `moe_gate_up_many`/`moe_down_many` — только Q4TiledP.
11. Metal `q8_matvec`/`q8_2f_matvec` — только тесты; декод достигает
    Metal-q8 лишь через `q8_matvec_range` гибридного сплита.
12. Q1-MoE: wgpu отклоняет (19951), Metal исполняет; комментарий
    «q2tp down не существует» (11341) устарел — `moe_down_q2tp_b` есть.
13. Док `GraphW` врёт про kind-коды (gpu.rs:723 «2=q4_tiled», на деле
    2=Q4Block, 5=Q4Tiled, 6=Q4TiledP) — та самая путаница, что уже
    приводила к мусорному выводу (qtensor.rs:568).

## Пробелы «кернела нет» (честные, до измеренной потребности)

- Q1S: движок не знает вовсе — файлы бегают в 4 байта/вес.
- ~~Q2TiledP: нет i8-варианта CPU-matvec и нет GPU-matvec на обоих~~ —
  закрыто (2026-08-10): i8-CPU (NEON shift+mask+vld4 + группсуммы,
  fused-арм, q2tp в moe_gate_up_many) и Metal `q2tp_matvec_jobs`
  (смешанное трио сквозь MoeJob; на M4 пробы честно держат CPU — 5.9
  против 2.8 форс-GPU; кернел для GPU-сильных устройств). Follow-up:
  device-vs-dequant юнит-оракул и MoE-блок в общий командный буфер.
- Vbit/VbitRo: CPU-only по построению.
- Q1/Q1T/Q4Block в Metal chunk-префилле (`kind_of` знает Q4t/Q4tp/Q8).
- Q8_2f col-field в wgpu-графе.

## Практика, добытая на стенде (27B q4tp, M4 24GB + M1 16GB)

- Metal block-граф ИСПОЛНЯЕТ q4tp/GDN целиком (план 32 итема, слои
  0..64) — «граф только для q1» — миф от имени `q1_parts`.
- `hd=256` выключает device-attend по умолчанию → 16 сэндвич-sync на
  токен; `CMF_GPU_ATTEND=256` включает широкий кернел: локальная
  сторона сплита 159→108 мс/токен (−35%).
- Пейджинг маскирует всё: любые замеры валидны только когда спан
  влезает в резидент (см. память стенда).

## Metal-MoE в общем командном буфере — РЕАЛИЗОВАНО (2026-08-10)

Спека ниже исполнена: `moe_topk_select` (MSL, юнит-оракул device==
`moe_route` с tie-break и обоими norm-режимами), `MetalFfn::{Dense,Moe}`
в слоях токен-графа, `encode_post_moe_ffn` (addnorm → f32-роутер →
select → gate/up-jobs (q4tp/q2tp по профилю) → moe_silu → down-jobs →
weighted reduce → axpy — всё в общем командном буфере), билдер
`metal_moe_graph_parts` с честными отказами (sigmoid/bias/τ-роутеры,
маски, per-expert scale, router_input_norm, не-Silu — CPU).

Политика device-attend перенесена ЗА скан плана: hd>128-выключатель
мерялся на dense-моделях, а MoE-план его инвертирует — каждый
CPU-attend-сэндвич стоит commit+wait. Замер (W2 q2tp-MoE 34.7B, M4,
steady decode, bench --json): сэндвич 14.7 tok/s, device-attend
**24.8–27.1 tok/s**, чистый CPU 18.8. Сабмиты/токен 39.8 → 27.4
(с префилл-амортизацией). Dense-модели политику не меняют.

Матрица регрессий: bonsai q1 (тексты ==, 95.8 tok/s), nanbeige q4t
(тексты ==, 17.7), W2 q2tp-MoE (граф+CPU-attend: тексты 48/48 == с
точным CPU, дрейф confidence 0.098 внутри собственного CPU-конверта
i8↔exact 0.11; device-attend расходится на 32-м токене — класс дрейфа
преджившей ручки, не MoE-ветки), 253/253 тестов движка.

Открытое: **35B q4tp (17.8 ГБ) больше Metal maxBufferLength M4
(13.6 ГБ)** — no-copy буфер файла не создаётся, весь Metal-путь
(и per-op, и граф) на этом файле недоступен; W2 (12.9 ГБ) влезает.
Follow-up: окно буфера по спану слоёв вместо целого файла — оно же
нужно сетевому сплиту (каждая сторона маппит только свой спан).

## Дизайн: Metal-MoE в общем командном буфере (исполненная спека)

Мотив, измеренный на 35B-A3B q4tp (M4): CPU 11.6-12.1 tok/s, Metal
9.8-11.0 — при потолке шины ~30-60 tok/s (активных ~1.9 ГБ/ток).
Разрыв — оркестровка: per-op MoE делает commit+wait_until_completed на
КАЖДОМ слое (~30 × ~1.3 мс), потому что роутинг слоя считает CPU на
хосте. Лечение — весь токен в одном командном буфере:

1. **MSL `f32_matvec`** (router: n_exp × hidden, f32 kind-4) — если
   отсутствует; проверить существующие простые кернелы.
2. **MSL `moe_topk_select`** — из logits[n_exp]: top-k индексы + softmax
   веса + shared-gate sigmoid (двойник wgsl `moe_select`,
   gpu_wgpu.rs:~15864); k ≤ 16, n_exp ≤ 256, один threadgroup.
3. **TokenGraph: `Item::MoeFfn`** в плане `q1_graph_gpu` (снять
   `FfnKind::Dense`-гейт скана): норм → router → select → jobs-кернел
   (`q4tp_matvec_jobs`/`q2tp_matvec_jobs` — есть) → `moe_silu_jobs` →
   down-jobs → `moe_reduce` (есть) — всё encode без commit; sync только
   там, где он уже есть (CPU-attend сэндвич / финальный readback).
   Расход буферов: sel/act/eo — через io_bufs, как в
   `moe_block_jobs_q4tp`.
4. Парити-оракулы готовы: W2 (q2tp) и 35B-q4tp, CPU⇔Metal тексты.
5. Ожидание: −30-40 мс/ток синхронизаций → Metal ≥ CPU; дальше общий
   потолок двигают только кернелы (scales_into-кэш на устройстве уже
   есть — лестница в threadgroup-памяти).

Риск: q1-флагман (35B Qwen3.5 q1) ходит этим же планом — регрессия
недопустима; ветка MoE не должна трогать Dense-путь. Делать отдельным
заходом с полной матрицей регрессий (bonsai q1, nanbeige q4t, 27B
q4tp-dense, W2 q2tp-MoE, 35B q4tp-MoE).

## Профиль декода на дискретной карте (2×RTX 5090, 2026-08-11)

Измерено `CMF_GPU_TS=1` (покадровый GPU-профилировщик) на W2 34.7B,
2048 hidden, 40 слоёв, top_k 8 + shared:

| фаза | мкс/токен | на слой |
|---|---|---|
| GDN-микс (30 слоёв) | 1949 | 65 |
| MoE-FFN (40 слоёв) | 2717 | 68 |
| attn-микс (10 слоёв) | 767 | 77 |
| хвост (norm+lm_head) | 189 | — |
| **итого GPU** | **5630** | |

Полный токен 8.3 мс при 121 tok/s — то есть ~2.7 мс вне устройства.

**Декод НЕ упирается в веса.** `CMF_TOPK_PROBE` 8→4 (вдвое меньше
экспертной арифметики при том же числе диспатчей) меняет время на 3%.
Потолок шины для 1.9 ГБ активных весов ≈ 1.1 мс — мы в 5× от него, и
разрыв съедает латентность запуска: 2048-hidden слой это 30-70 мкс
работы на карте, которая хочет тысячи рабочих групп.

**Пер-диспатчная разбивка (`CMF_GPU_TS=2`, один слой каждого рода):**
GDN — proj 39 мкс, outp 16, step 11, conv 6, snorm 5; attention — attend
24, qkv 17, wo 14, rope 13, kv 4, gate 4; MoE — router 16, select 13,
down 14, gate/up 13, pre 9. Самые ДЕШЁВЫЕ диспатчи стоят 4-6 мкс — это
пол накладных расходов на запуск, и при ~15 диспатчах на слой × 40 слоёв
он съедает около трети токена.

**Ручки проверены — дефолты уже оптимальны, не переоткрывать:**

| ручка | значение | измерено (W2, 5090) |
|---|---|---|
| `CMF_MV4` | 1 (дефолт) | 124.0 против 77.7 tok/s при 0 |
| `CMF_MOE_FOLDSEL` | 0 (дефолт) | 120.7 против 100.4 при 1 (вывод при этом побайтно тот же — путь верный, но медленнее) |
| `CMF_SLOTS_PER_GPU` | 1 (дефолт) | 210 против 185 tok/s при 2 |
| `CMF_BATCH_K` | 0 (дефолт) | 129.9 против 128.2 при 128 — батч-граф этой модели не помогает |
| `CMF_COOP` | 1 (дефолт) | GEMM 51.9 против 25.0 TFLOP/s при 0 |

Отсюда следующие рычаги, по убыванию измеренной цены:

1. **Батчинг последовательностей (continuous batching).** Единственный
   способ заполнить SM: один сабмит считает B независимых
   последовательностей. Требует пер-последовательностных KV-зеркал в
   графе (сейчас ключ `(kv_id, layer)` — уже почти то, что нужно).
   ПРОВЕРЕНО И ОТВЕРГНУТО как замена: два слота на карту дают 185 tok/s
   против 210 у одного (`CMF_SLOTS_PER_GPU`) — слоты дерутся за очередь,
   а не перекрываются.
2. **Кэш bind-групп графа.** 12 617 аллокаций на токен против 363 на
   CPU-пути — это объекты wgpu, пересоздаваемые каждый токен (uniform'ы
   уже кэшируются по содержимому, bind-группы нет). Дизайн: ключ
   `(site_id, layer)` на 35 точках вызова хелпера `bg(...)` внутри
   `forward_token_graph` + счётчик поколения, который бампает
   `Scratch::ensure` при пересоздании буфера. Цена ошибки — тихо
   неверные байты, поэтому делать с парити-гейтом на каждой модели.
3. **Префилл в сплит-режиме**: два сабмита на позицию против одного
   (67.8 против 156.6 tok/s). Лечится конвейеризацией сегментов по
   позициям — сегмент 1 считает позицию p, пока сегмент 0 берёт p+1.

## Почему проба может оставить диффузию на CPU (измерено 2026-08-11)

Симптом: в MiniMax-DiT проекция `out` (5376×7168) стоила 9.8 с на шаг,
хотя тот же кернел на той же форме делает её за 8.4 мс (кернел-тест
`wgpu_q4tp_mm_throughput`, 53 TFLOP/s). Она НЕ доходила до устройства.

Механизм — два наложившихся свойства пробы:

1. **Холодные GPU-сэмплы отбрасываются.** В диффузии каждый слой
   трогается один раз за шаг, поэтому на ПЕРВОМ шаге каждый GPU-замер
   помечен cold (заливка весов) и не считается. Проба не набирает
   GPU-плечо и продолжает чередовать армы.
2. **Счётчик чередования общий на класс и идёт по порядку вызовов.**
   В блоке ровно два арбитрируемых GEMM (qkv, out): qkv всегда чётный,
   out всегда нечётный — и весь первый шаг `out` попадает на CPU-плечо.

Итог измерен: шаг 1 — 9.8 с, шаг 2 — 2.8 с (веса тёплые, вердикт
принят). То есть это разовая цена ~7 с на рендер, а не системная.

Порог раннего вердикта опущен с 3× до 2× (разрыв тут 2.8×) — это НЕ
починило случай (мешает пункт 1), но убирает лишнее чередование там,
где победитель очевиден. Настоящее лечение: во время пробы, если веса
ещё не резидентны, предпочитать GPU-плечо (заливка всё равно нужна для
следующих шагов) — `probe_resident_or_upload` для этого уже есть.

## Следующий рычаг видео: attention на тензорных ядрах (посчитано)

После переноса FFN и починки пробы профиль шага MiniMax-DiT (512×288,
RTX 5090, `CMF_MMH3_PROF`) выглядит так: **attention 7.5 с (40%)**,
qkv 3.0, out 3.0, fc1 (слитый FFN) ~5.

Арифметика attention на блок: n=1859, nh=42, hd=128 →
QK = 2·nh·n²·hd ≈ 37 GFLOP, PV столько же. На 50 блоков это ~3.7 TFLOP
за шаг, и они идут 7.5 с — то есть **0.5 TFLOP/s**, при том что
кернел-тест q4tp-GEMM на этой же карте держит **51.9 TFLOP/s**.
Разница не в шине (q/k/v это ~120 МБ на блок, ~1.6 с на весь рендер) и
не в запусках (126 диспатчей на блок ≈ 31 мс на шаг) — она в том, что
`dit_qk`/`dit_pv` скалярные f32-кернелы, а не матричные.

Дизайн: у бэкенда УЖЕ есть кооперативный f32-GEMM (`gemm_nt_coop`,
которым пользуется `gemm_nt_f32`). Нужен его вход по device-буферам:

1. QK: q_h [n×hd] × k_h [n×hd]ᵀ → scores — ровно форма NT, ложится
   без транспонирования.
2. Softmax по строкам — как есть (`dit_softmax`).
3. PV: scores [n×n] × v_hᵀ [hd×n] — нужен vᵀ; либо готовить его на
   хосте (там v уже собирается в head-major, это тот же проход), либо
   добавить транспонирующий кернел.
4. Гейт: парити кадров против текущего пути (порог 3.4% — конверт
   CPU↔GPU) плюс кернел-тест на форму attention.

Ожидание по арифметике: 7.5 с → 1-2 с на шаг, то есть рендер 127.8 →
~100 с.

**ПРОВЕРЕНО 2026-08-11 — ПОСЫЛКА ОКАЗАЛАСЬ НЕВЕРНОЙ.** Кернел написан
(`DIT_COOP_SRC`/`dit_gemm_coop`, за `CMF_DIT_ATTN_COOP=1`), QK через
матричные ядра считает ПРАВИЛЬНО (кадры совпадают, дельта 0.000), но
шаг не изменился: attention 7.5 с против 7.6. То есть attention НЕ
упирается в арифметику QK, и оценка «0.5 TFLOP/s» мерила не то, что
тратит время. Что осталось подозреваемым, по убыванию:

1. **Софтмакс**: nh·n² = 145 М элементов на блок, одна рабочая группа
   на строку — 78 тыс. групп на блок, 3.9 млн на шаг.
2. **Заливка q/k/v и вычитка панели**: 160 МБ на блок, 8 ГБ на шаг.
3. **Диспатчи**: 42 головы × 3 прохода × 50 блоков = 6300 проходов на
   шаг (при полу в 4-6 мкс это ~30 мс — мало, но не ноль).

**РАЗДЕЛЕНО (2026-08-11).** Таймер поставлен отдельно на хостовый репак
и на устройственный вызов: из 7.3 с фазы attention **4.4 с — это репак
на хосте** (сборка head-major q/k/v из чересстрочного qkv), и только
~2.9 с — само устройство. То есть узкое место было НЕ в кернелах и не в
арифметике, а в подготовке данных на CPU — ровно то, что предыдущая
попытка (coop-QK) не могла ускорить в принципе.

Написан кернел `dit_qkv_split` + вход `dit_attention_packed`: qkv едет
на карту одним куском и раскладывается по головам ТАМ. Проверен на
64×32 (рендер корректен), на полном размере не домерен — поэтому
включается явно, `CMF_MMH3_ATTN=split`. Довести: замер 512×288 + парити
кадров, и если держит — сделать дефолтом.

Прежний список подозреваемых (софтмакс, трафик, диспатчи) остаётся для
оставшихся ~2.9 с: `CMF_GPU_TS=2` внутри dit_attention, или простой A/B с
выключенным софтмаксом (заведомо неверный вывод, но честное время).
Кернел оставлен за флагом — он корректен и пригодится, когда узкое
место окажется там, где я предполагал.

## Что осталось в attention после переноса репака (2026-08-11)

Дефолт теперь раскладывает qkv по головам НА КАРТЕ (`dit_qkv_split`):
репак 4.4 → 1.5 с, рендер 130.0 → 111.8 с, кадры бит-в-бит.

Оставшаяся устройственная часть — **5.2 с на шаг** (29% шага). Coop-QK
перемерен уже БЕЗ репака и снова нейтрален (5.2 против 5.3) — то есть
QK-GEMM не узкое место ни при каком раскладе. Значит остаток сидит в
софтмаксе (nh·n² элементов, одна рабочая группа на строку → 78 тыс.
групп на блок) и/или в PV.

**РАЗВЕДЕНО (`CMF_DIT_ATTN_PROF=1`, 512×288):**

| проход | секунд/шаг | доля |
|---|---|---|
| QK | 1.65 | 22% |
| softmax | 0.97 | 13% |
| **PV** | **4.76** | **64%** |

PV втрое дороже QK при ТЕХ ЖЕ FLOPs (оба n²·hd) — значит дело не в
арифметике, а в доступе: его правый операнд `v` лежит [n][hd], а GEMM
читает его по колонкам, вразнобой. QK такой проблемы не имеет, потому
что k лежит ровно так, как нужен NT-произведению.

Лечение (в порядке цены): транспонировать v на устройстве один раз на
блок (n·hd элементов — копейки рядом с n²·hd) в [hd][n], после чего PV
становится обычным NT-произведением, как QK, и вдобавок ложится на уже
написанный coop-кернел `dit_gemm_coop`. Ожидание: 4.76 → ~1.5 с, то
есть шаг 18.9 → ~15.6 и рендер 111.8 → ~95 с.

**PV-как-NT: быстрее и пока неверно (2026-08-11).** Транспонирование
вынесено в свой модуль (авто-layout строится ПО ТОЧКЕ ВХОДА и
переиндексирует биндинги — кернел, трогающий подмножество, привязать
нельзя). После этого путь заработал и дал **PV 4.76 → 2.82 с (1.7×)**,
но кадры разошлись на 59%: NT-форма берёт ширину свёртки как
`cols4 * 4`, а PV сворачивает по n = 1859, что усекается до 1856 и
молча теряет три колонки каждой строки очков. Гейт добавлен (`n % 4`),
путь остаётся за `CMF_DIT_PV_COOP=1`. Чтобы включить: дать кернелу
истинное k рядом с `cols4` (страйд остаётся от cols4, границы цикла — от
k), затем сверить кадры и снять флаг. Выигрыш подтверждён замером, это
вопрос корректности, а не идеи.

Это и есть пример правила «сначала разведи, потом пиши»: два кернела,
написанные до разведения, оказались корректными и бесполезными, а
разведение стоило одного флага и одного прогона.

## Профиль шага DiT после всех переносов (2026-08-11, финальный)

Учёт выправлен (слоты 2 и 3 мерили одну работу — шаг 14.1 с читался как
26.1; сумма слотов теперь сходится с внешним таймером):

| фаза | с/шаг | доля |
|---|---|---|
| fc1 (слитый FFN) | 5.1 | 36% |
| qkv | 3.2 | 23% |
| out | 2.8 | 20% |
| attention (QK+softmax+PV) | 2.2 | 16% |
| остальное | 0.8 | 5% |

**Attention перестал быть главной статьёй** — им были проекции. И у них
разрыв с кернелом: qkv это 430 GFLOP на блок, 21.5 TFLOP на шаг, идёт
3.2 с = **6.7 TFLOP/s**, тогда как кернел-тест на той же форме держит
51-61. Разница — не в кернеле, а в обвязке КАЖДОГО вызова:

- вычитка y: 1859×21504×4 = **160 МБ на блок**, 8 ГБ на шаг;
- заливка x: 40 МБ на блок;
- распаковка плоскости: 115 М элементов на блок (заметно, но вторично —
  при b=1859 это 1/1859 работы GEMM).

То есть цену платит гранулярность: каждый GEMM — отдельный round trip
через шину. Кэшировать распакованные плоскости бесполезно (у этой модели
их на 38 ГБ) и не нужно — дело не в них.

**УТОЧНЕНИЕ ДИЗАЙНА (проверено по коду).** Убрать вычитку qkv «просто
прокинув буфер» НЕЛЬЗЯ: между GEMM и attention хост применяет к q и k
норму и RoPE (`norm_rope_w`, mmh3.rs:866) — данные обязаны прийти на
хост, пока это делает CPU. Значит порядок работ обратный тому, что
кажется: сперва кернел qk-norm+RoPE на устройстве (он же снимает 0.4 с
слота qknorm), и только потом qkv-буфер имеет смысл не вычитывать.
Механизм для второго шага уже есть — `q4tp_matmat_dev` (tp_matmat с
необязательной вычиткой).

**Дизайн следующего захода: блок DiT целиком резидентен.** x входит в
блок один раз, qkv → attention → out → FFN считаются в device-буферах,
наружу выходит только результат блока. Это убирает ~200 МБ трафика на
блок (10 ГБ на шаг) и превращает четыре round trip в один. Ожидание по
арифметике: 11.1 с проекций → 3-4 с, шаг 14.1 → ~7, рендер 106.9 → ~70.
Гейт тот же: парити кадров против текущего пути (конверт 3.4%).
