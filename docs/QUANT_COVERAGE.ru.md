# Покрытие квант-форматов путями исполнения

Статус: аудит кода на 0.5.65+wip, 2026-08-10. Единица правды — ссылки
file:line в тексте; при расхождении с кодом прав код, документ чинится.

Мотив: «оптимизация не для одного формата». Ниже — измеренная карта того,
какой dtype на каком пути реально исполняется, и полный список щелей
двух сортов: «кернел есть, вызов отсекает» (дёшево чинить) и «кернела
нет» (осознанные пробелы).

## Щели «кернел есть — вызов отсекает» (по цене починки)

1. ~~Q2TiledP в `q1_parts` без кернела в `proj_abs`~~ — починено.
2. ~~Q4Tiled decode-matvec без диспатчера~~ — починено: `gpu::q4t_matvec`
   + probe-арм (Metal; wgpu — честный отказ до появления дискретного
   q4t-стенда).
3. Q4Block Metal per-op: `gpu.rs:1001 Metal=>false` при живом
   `encode_q4b_matvec` — standalone lm_head q4b-модели не ускоряется.
4. Q4t/Q4tp в `matvec_batch` wgpu: `BatchLayout` смоделирован, Metal
   исполняет, wgpu отклоняет весь батч (gpu_wgpu.rs:20134).
5. ~~`gpu_batch_job` знает лишь Q8/Q1~~ — починено: армы Q4t/Q4tp
   (сырые активации, скейлы в payload); арбитраж пробой OpClass::Batch
   держит победителя честно (на M4 и M1 проба оставила CPU — маршрут
   для конфигураций, где Metal-батч амортизируется).
6. ~~q2tp-MoE в батч/префилл-графе~~ — починено (2026-08-10) с
   парити-оракулом Qwen3.6-35B-A3B-Escha-W2: билдер получил
   q2tp-лестницу токен-графа (gu_q2 сквозной), пер-позиционная полоса
   ветвится gu_q2 → `moe_gate_up_q2tp` + точный `moe_down_q4tp`
   (пара chain-пути), полно-чанковая q4tp-полоса ЯВНО исключает
   gu_q2 (у смешанного профиля q4tp=true — без `!gu_q2` она молола
   бы q2tp-байты q4tp-кернелом), GU-страйд юниформа по
   `expected_nbytes(Q2TiledP)`. Вывод CPU⇔wgpu побайтно совпал,
   отказов bgraph нет, 151/151 тестов. Заведомо НЕ подключены
   `bt_moe_gate_up_q2tp(_r4)` — полно-чанковый 2-битный вариант
   остаётся оптимизацией со своим mg-лейаутом (пер-позиционная
   полоса живёт в том же submit), и черновой `moe_down_q2tp_b`
   (DSpark-грейд, «не обязан совпадать бит-в-бит») — в основной
   путь не годится по контракту точности.
7. `moe_parts` не принимает Q2TiledP/Q1T/Q4Block; у `MoeJob` нет
   флага q2tp — обычный MoE-путь мимо существующих wgpu-кернелов.
8. `matvec_silu_mul`: ~~Q1~~ починено (fused-арм с общими групповыми
   суммами; M1-воркер bonsai 9.0→7.5-7.9 мс/ток, −14%); ~~Q8Row~~
   починено (портируемый `q8_row_dot` c оракул-тестом fast==scalar;
   бенч ждёт q8-чекпойнта на стенде). Q8_2f исключён ОСОЗНАННО: его
   колоночное поле прескейлит активации по-тензорно и ломает контракт
   общего split_act — остаётся двухпроходным. Q2TiledP — без CPU-i8
   кернела вовсе (см. «бескернельные»).
9. `matvec_many` без Q4Tiled/Q2TiledP; `matvec2_many` ещё уже.
10. `moe_gate_up_many`/`moe_down_many` — только Q4TiledP.
11. Metal `q8_matvec`/`q8_2f_matvec` — только тесты; декод достигает
    Metal-q8 лишь через `q8_matvec_range` гибридного сплита.
12. Q1-MoE: wgpu отклоняет (19951), Metal исполняет; комментарий
    «q2tp down не существует» (11341) устарел — `moe_down_q2tp_b` есть.
13. Док `GraphW` врёт про kind-коды (gpu.rs:723 «2=q4_tiled», на деле
    2=Q4Block, 5=Q4Tiled, 6=Q4TiledP) — та самая путаница, что уже
    приводила к мусорному выводу (qtensor.rs:568).

## Пробелы «кернела нет» (честные, до измеренной потребности)

- Q1S: движок не знает вовсе — файлы бегают в 4 байта/вес.
- ~~Q2TiledP: нет i8-варианта CPU-matvec и нет GPU-matvec на обоих~~ —
  закрыто (2026-08-10): i8-CPU (NEON shift+mask+vld4 + группсуммы,
  fused-арм, q2tp в moe_gate_up_many) и Metal `q2tp_matvec_jobs`
  (смешанное трио сквозь MoeJob; на M4 пробы честно держат CPU — 5.9
  против 2.8 форс-GPU; кернел для GPU-сильных устройств). Follow-up:
  device-vs-dequant юнит-оракул и MoE-блок в общий командный буфер.
- Vbit/VbitRo: CPU-only по построению.
- Q1/Q1T/Q4Block в Metal chunk-префилле (`kind_of` знает Q4t/Q4tp/Q8).
- Q8_2f col-field в wgpu-графе.

## Практика, добытая на стенде (27B q4tp, M4 24GB + M1 16GB)

- Metal block-граф ИСПОЛНЯЕТ q4tp/GDN целиком (план 32 итема, слои
  0..64) — «граф только для q1» — миф от имени `q1_parts`.
- `hd=256` выключает device-attend по умолчанию → 16 сэндвич-sync на
  токен; `CMF_GPU_ATTEND=256` включает широкий кернел: локальная
  сторона сплита 159→108 мс/токен (−35%).
- Пейджинг маскирует всё: любые замеры валидны только когда спан
  влезает в резидент (см. память стенда).

## Metal-MoE в общем командном буфере — РЕАЛИЗОВАНО (2026-08-10)

Спека ниже исполнена: `moe_topk_select` (MSL, юнит-оракул device==
`moe_route` с tie-break и обоими norm-режимами), `MetalFfn::{Dense,Moe}`
в слоях токен-графа, `encode_post_moe_ffn` (addnorm → f32-роутер →
select → gate/up-jobs (q4tp/q2tp по профилю) → moe_silu → down-jobs →
weighted reduce → axpy — всё в общем командном буфере), билдер
`metal_moe_graph_parts` с честными отказами (sigmoid/bias/τ-роутеры,
маски, per-expert scale, router_input_norm, не-Silu — CPU).

Политика device-attend перенесена ЗА скан плана: hd>128-выключатель
мерялся на dense-моделях, а MoE-план его инвертирует — каждый
CPU-attend-сэндвич стоит commit+wait. Замер (W2 q2tp-MoE 34.7B, M4,
steady decode, bench --json): сэндвич 14.7 tok/s, device-attend
**24.8–27.1 tok/s**, чистый CPU 18.8. Сабмиты/токен 39.8 → 27.4
(с префилл-амортизацией). Dense-модели политику не меняют.

Матрица регрессий: bonsai q1 (тексты ==, 95.8 tok/s), nanbeige q4t
(тексты ==, 17.7), W2 q2tp-MoE (граф+CPU-attend: тексты 48/48 == с
точным CPU, дрейф confidence 0.098 внутри собственного CPU-конверта
i8↔exact 0.11; device-attend расходится на 32-м токене — класс дрейфа
преджившей ручки, не MoE-ветки), 253/253 тестов движка.

Открытое: **35B q4tp (17.8 ГБ) больше Metal maxBufferLength M4
(13.6 ГБ)** — no-copy буфер файла не создаётся, весь Metal-путь
(и per-op, и граф) на этом файле недоступен; W2 (12.9 ГБ) влезает.
Follow-up: окно буфера по спану слоёв вместо целого файла — оно же
нужно сетевому сплиту (каждая сторона маппит только свой спан).

## Дизайн: Metal-MoE в общем командном буфере (исполненная спека)

Мотив, измеренный на 35B-A3B q4tp (M4): CPU 11.6-12.1 tok/s, Metal
9.8-11.0 — при потолке шины ~30-60 tok/s (активных ~1.9 ГБ/ток).
Разрыв — оркестровка: per-op MoE делает commit+wait_until_completed на
КАЖДОМ слое (~30 × ~1.3 мс), потому что роутинг слоя считает CPU на
хосте. Лечение — весь токен в одном командном буфере:

1. **MSL `f32_matvec`** (router: n_exp × hidden, f32 kind-4) — если
   отсутствует; проверить существующие простые кернелы.
2. **MSL `moe_topk_select`** — из logits[n_exp]: top-k индексы + softmax
   веса + shared-gate sigmoid (двойник wgsl `moe_select`,
   gpu_wgpu.rs:~15864); k ≤ 16, n_exp ≤ 256, один threadgroup.
3. **TokenGraph: `Item::MoeFfn`** в плане `q1_graph_gpu` (снять
   `FfnKind::Dense`-гейт скана): норм → router → select → jobs-кернел
   (`q4tp_matvec_jobs`/`q2tp_matvec_jobs` — есть) → `moe_silu_jobs` →
   down-jobs → `moe_reduce` (есть) — всё encode без commit; sync только
   там, где он уже есть (CPU-attend сэндвич / финальный readback).
   Расход буферов: sel/act/eo — через io_bufs, как в
   `moe_block_jobs_q4tp`.
4. Парити-оракулы готовы: W2 (q2tp) и 35B-q4tp, CPU⇔Metal тексты.
5. Ожидание: −30-40 мс/ток синхронизаций → Metal ≥ CPU; дальше общий
   потолок двигают только кернелы (scales_into-кэш на устройстве уже
   есть — лестница в threadgroup-памяти).

Риск: q1-флагман (35B Qwen3.5 q1) ходит этим же планом — регрессия
недопустима; ветка MoE не должна трогать Dense-путь. Делать отдельным
заходом с полной матрицей регрессий (bonsai q1, nanbeige q4t, 27B
q4tp-dense, W2 q2tp-MoE, 35B q4tp-MoE).
