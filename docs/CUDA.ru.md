# Бэкенд CUDA

*Языки: [English](CUDA.md) · **Русский** · [中文](CUDA.zh.md)*

cortiq работает на GPU через wgpu (Vulkan, DX12, Metal) и через собственный путь Metal. На карте NVIDIA
есть третий путь — нативный бэкенд CUDA. Он экспериментальный и по умолчанию выключен: его включает
feature сборки, а выбирает переменная окружения.

```bash
cargo install cortiq-cli --features cuda      # или в рабочей копии: cargo build --release -p cortiq-cli --features cuda
CMF_GPU=cuda cortiq run spark-x2.6-4b-q4tp-turbo.cmf --prompt "..." --greedy --no-think
CMF_GPU=cuda cortiq bench spark-x2.6-4b-q4tp-turbo.cmf --ctx 4000 --tokens 60 --core
cortiq gpu        # скажет, на месте ли карта и библиотеки
```

Для сборки toolkit CUDA не нужен: ничего не линкуется. При запуске бэкенд открывает `libcuda` драйвера и
две библиотеки toolkit — `libnvrtc` (компилирует ядра) и `libcublas`, версии 12.x. Если какой-то из них
нет, `CMF_GPU=cuda` работает на CPU и говорит почему (`cortiq gpu` или `RUST_LOG=warn`).

## Сервер

`cortiq serve` работает на этом бэкенде так же, как на любом другом: OpenAI-совместимый HTTP API и
веб-панель на том же порту.

```bash
CMF_GPU=cuda CMF_MAX_SEQ=131072 cortiq serve spark-x2.6-4b-q4tp-turbo.cmf --port 8080 --host 127.0.0.1
```

```bash
curl http://127.0.0.1:8080/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "spark",
  "messages": [{"role": "user", "content": "Explain how a hash map works."}],
  "max_tokens": 256,
  "temperature": 0,
  "enable_thinking": false,
  "stream": true
}'
```

| адрес | что делает |
|---|---|
| `POST /v1/chat/completions` | реплика чата; `stream: true` отдаёт ответ по мере генерации и заканчивает его строкой `data: [DONE]` |
| `POST /v1/completions` | продолжение текста `prompt` |
| `GET /v1/models` | обслуживаемая модель |
| `GET /healthz` | 200, пока сервер работает |
| `GET /` | веб-панель |
| `GET /v1/cortiq/status` | состояние движка |

- Поле `model` в запросе обязательно, имя может быть любым: сервер обслуживает один файл.
- По умолчанию `--host` равен `0.0.0.0`, то есть все интерфейсы, и сервер не проверяет ключи;
  `--host 127.0.0.1` оставляет его локальным.
- `CMF_MAX_SEQ` — потолок контекста каждого запроса, по умолчанию 32 768.
- Запрос, продолжающий предыдущий, читает только новое: строки K/V общего начала остаются на карте
  (20 новых токенов за 42 мс при 87 из кэша). После печати турбо-файла новая реплика читает диалог заново.
- `CMF_SERVE_SLOTS=N` держит N диалогов одновременно, у каждого свои строки на карте: по умолчанию один на
  каждые четыре ядра CPU, не больше четырёх. Их запросы идут по карте по очереди. Два запроса сразу дали
  те же тексты, что и по одному, на 38 и 64 tok/s там, где один запрос генерирует 117.
- После каждого запроса сервер печатает, сколько он занял, как llama-server. Документ в 20 283 токена на
  A40 — чтение, печать и ответ:

```
prompt eval time =    8334.96 ms / 20283 tokens (    0.41 ms per token,  2433.49 tokens per second)
       eval time =     710.31 ms /    63 tokens (   11.27 ms per token,    88.69 tokens per second)
      total time =    9045.26 ms / 20347 tokens
```

Всё это на карте проверяет `scripts/cuda/pod/serve_turbo_check.sh`.

## Что на нём работает

Плотные стеки с полным или скользящим вниманием, класс Spark-X2.x: веса q4tp, q8_2f или f32, RMS-нормы,
ротационные позиции по слоям, поголовный выходной гейт Spark, FFN с SiLU или GELU. Для них бэкенд
обслуживает те же два графовых контракта, что и wgpu:

- **декод**: все слои и голова на карте, скрытая строка резидентна, одно чтение на токен;
- **промпт**: куски по 1024 строки через все слои, строки K/V остаются в зеркалах, которые читает декод;
- **дальнее поле** турбо-файла: промпт длиннее печати файла читается целиком с точным вниманием и
  запечатывается один раз после него; дальше токен читает состояние дальнего поля на карте, и его цена
  и память карты перестают расти вместе с текстом. `CMF_O1=off` оставляет точное внимание на любой длине.

Гибриды семейства Qwen3.5 (`qwen3_5`: смесители GDN и полное внимание с гейтом и нормами Q/K, плотные
FFN, блок MTP; Qwen3.8-27B) идут по второй ветке бэкенда, черновики и их проверка тоже на карте, см.
[Гибриды](#гибриды-семейство-qwen35). У стека Fast Code (`qwen4_exp`) свой путь (`gpu_cuda/qwen4.rs`).
Nemotron Labs Dory (`dory`, зацикленный nGPT) идёт на ядрах гибридной ветки вместе с турбо-файлами, см.
[Dory](#dory-зацикленный-ngpt).
Всё остальное (другие MoE, сэндвич-нормы, выходные гейты кроме этих) отклоняется до изменения состояния,
и модель идёт по пути CPU; `CMF_CUDA_DEBUG=1` печатает причину.

## Как это устроено

Со стороны Rust — [cudarc](https://crates.io/crates/cudarc): driver API для контекста, памяти, загрузки
модулей и запуска ядер, NVRTC и cuBLAS. Ядра написаны на CUDA C в `crates/cortiq-engine/src/gpu_cuda/` и
компилируются при первом использовании под архитектуру карты; внимание декода — под геометрию голов
модели.

**Декод** держит веса в их кодеке и читает каждую матрицу один раз на токен. Одно ядро, `mv_multi`,
берёт за запуск несколько матриц против одной входной строки (q, k, v и гейт голов; gate и up). Варп
владеет строкой матрицы; входная строка раскладывается в разделяемой памяти один раз на блок, вместе с
RMS-нормой и полем столбцов q8_2f. Строка хранится «по элементам» с нечётным шагом, поэтому 32 линии
варпа читают 32 разных банка. 32 масштаба строки q4tp лежат в регистрах линий, масштаб группы — это
shuffle внутри варпа. Внимание — три небольших ядра над зеркалом K/V: скоры с варпом на строку ключей
(строка читается один раз на четыре головы запроса группы KV), экспоненты и суммы значений по блокам,
сумма по блокам с гейтом голов.

**Промпт** раз в кусок разворачивает каждый вес в плотную плоскость f16 и умножает через cuBLAS на
тензорных ядрах: операнды f16, накопление и результат f32. Внимание — два пакетных GEMM на слой (скоры
и значения, четыре группы KV одним вызовом) вокруг причинного softmax, отрезками строк, при которых
матрица скоров держится около 384 МБ.

**Дальнее поле** (`nystrom.rs`) держит для запечатанного слоя строки, которые он читает точно, — первые
строки, строки, выбранные точными, кольцо последних 1800 — в буфере с раскладкой зеркала K/V, и дальние
суммы каждой головы по 32 опорным точкам: 18 МБ на слой. Токен добавляет два запуска к трём запускам
точного внимания: строка кольца, которую он заменяет, уходит в дальние суммы, а дальняя часть внимания
строки выходит как ещё один блок частичных сумм, которые оставляют ядра ближних строк, под одним сдвигом
с ними. Печать делает хост: для неё с карты уходят строки K/V промпта и одна строка запросов из восьми,
и 248 точных строк выбираются среди всех строк промпта. Этот бэкенд читает весь промпт до печати, а путь
wgpu запечатывает на 8 192 строках и читает остальное через дальнее поле; `CMF_O1_WHOLE=1` ведёт путь
wgpu тем же порядком.

## Точность

Декод считается в f32 в любом режиме. Для промпта выбирает `CMF_CUDA_PREC`:

| значение | GEMM весов | GEMM внимания |
|---|---|---|
| `fast` (по умолчанию) | операнды f16, накопление f32 | TF32 |
| `tf32` | TF32 | TF32 |
| `exact` | f32 | f32 |

`fast` — класс ядер матричных блоков пути wgpu. Середина FFN, `act(gate) · up`, уходит в f16 делённой
на 16, и GEMM умножает обратно, так что половинная точность вмещает величины до миллиона.

## Совпадение

Эталон — хост с float-активациями (`CMF_GPU=0 CMF_SDOT=0`). Четыре промпта, по 96 токенов, все пути идут
по одним и тем же id; наибольшее расхождение логитов с эталоном:

| файл | путь | top-1 как у эталона | первый токен | остальные токены |
|---|---|---:|---:|---:|
| q4tp | CUDA, `exact` | 384/384 | 0,0001 | 0,0002 |
| q4tp | **CUDA** | 384/384 | 0,020 | 0,016 |
| q4tp | Vulkan | 384/384 | 0,020 | 0,017 |
| q8_2f | CUDA, `exact` | 384/384 | 0,0001 | 0,0002 |
| q8_2f | **CUDA** | 384/384 | 0,019 | 0,023 |
| q8_2f | Vulkan | 384/384 | 0,014 | 0,015 |

Свободные жадные прогоны с точным вниманием на шести промптах от 20 до 20 255 токенов (`CMF_O1=off` для
самого длинного), по 96 токенов: CUDA и Vulkan дают одни и те же 576 id на каждом файле. Чат из трёх реплик и два запроса к серверу с общим началом (строки K/V
переиспользуются) дают один и тот же текст на обоих путях. Строки Vulkan — версии 0.8.67: первый токен
после промпта идёт через голову графа токена, а cortiq 0.8.66 считал его для файла q8_2f гибридной головой
(0,29 на первом токене).

У дальнего поля три проверки. Его ядра токена против `NystromState::step_group` на случайных состояниях,
144 строки через полный оборот кольца: 3,5e-5 при значениях до 2,3 (юнит-тест на карте). От одной и той
же печати промпта в 20 255 токенов декод на карте против декода на хосте с float-активациями, 96 токенов:
тот же top-1 на каждом шаге, логиты в пределах 0,0002 (q4tp) и 0,0004 (q8_2f). Против пути wgpu в том же
порядке, оба промпта в f32: 96/96 и 0,025 (q4tp), 95/96 и 0,50 (q8_2f). При точностях по умолчанию дальние
поля двух путей расходятся раньше, как и две точности одного пути: на этом промпте путь wgpu по умолчанию
и с f32-промптом различаются на 0,04 в среднем по логитам (q4tp) и на 0,65 (q8_2f), путь CUDA — так же.
Печать усиливает округления промпта; точное внимание — нет. Факты, подложенные в 60 000, 120 000 и
240 000 символов текста Википедии, найдены 8 раз из 8 с дальним полем на CUDA
(`scripts/cuda/pod/chain_cuda_passkey.sh`).

## Гибриды: семейство Qwen3.5

Стек из смесителей GDN и полного внимания с гейтом и нормами Q/K (`qwen3_5`, среди них Qwen3.8-27B) идёт
по своей ветке, `gpu_cuda/hyb.rs` и `hyb.cu`, за теми же двумя графовыми контрактами. Раунды черновиков
пайплайна, prompt lookup и сервер работают на ней без изменений.

```bash
CMF_GPU=cuda cortiq run qwen38-27b-q4tp.cmf --prompt "..." --greedy --no-think
CMF_GPU=cuda cortiq serve qwen38-27b-q4tp.cmf --port 8080 --host 127.0.0.1
```

**Декод и проверка** идут через одно ядро на тензорных ядрах: `mma.sync` m16n8k16, операнды bf16, суммы
f32.
- При загрузке карта перепаковывает каждую матрицу q4tp, чтобы поток брал свои восемь байт плитки из 16
  строк за одну загрузку.
- Входная строка приходит в ядро двумя плоскостями bf16, около 17 значащих бит; их пишет ядро, которое
  эту строку посчитало.
- До шестнадцати строк стоят почти как одна: восемь строк — 1,05× одной на 3090, шестнадцать — около 1,6×.
- Арифметика строки не зависит от того, сколько строк в запуске. Поэтому окно проверки даёт биты
  обычного токена, и текст с черновиками совпадает с текстом без них.
- gate и up — одна матрица, в плитках которой по восемь строк каждой. Эпилог ядра пишет
  silu(gate) · up для проекции down.

**GDN и внимание.**
- Слой GDN — два запуска: свёртка, её кольцо, L2-нормы и гейты в одном, правило дельты в другом.
- В правиле дельты поток владеет столбцом состояния на 3 МБ, так что варп читает 32 соседних числа;
  копию состояния для шага назад при проверке пишет тот же запуск.
- Внимание читает зеркала K/V в f16.
- Токен или окно проверки — один граф CUDA, который проигрывается с записью своих позиций.
- Вызов на одну строку по длинному набору матриц берёт одну плитку на блок (gate/up 801 против 745 ГБ/с);
  арифметика от этого не зависит.

**Черновики.**
- Черновики MTP одного раунда — один граф CUDA: каждый шаг берёт строку эмбеддинга своего токена на
  карте (первые 65 536 строк эмбеддинга, перепакованные), прогоняет блок и голову по шортлисту и
  берёт argmax там же. Одна загрузка, один запуск, назад только id.
- Проверка выбирает argmax каждой строки на карте по правилу хоста для равных, логиты остаются там.
- Раунд, который приносит два токена и больше, спекулирует без замера обычных токенов: раунд стоит
  около 1,25 обычного токена на этой ветке.
- Prompt lookup продолжает черновик, повторяющий более ранний кусок текста. Его окно — 8 строк, и 16
  после раунда lookup, в котором устояли все черновики.
- После частичного принятия каждое состояние GDN возвращается к началу окна и проигрывает принятые
  строки: два запуска на все слои.

**Промпт** разворачивает перепакованные веса в f16 для cuBLAS, кусками по 1024 строки. Внимание идёт по
K/V в f16, склейка GDN — в ядрах f32.

**Загрузка.** PTX каждого ядра кешируется на диске (`~/.cache/cortiq/cuda`, `CMF_CUDA_CACHE`), а
перепаковка идёт на карте. План файла 27B строится меньше чем за 4 с.

**Следующая реплика чата.** Шаблон Qwen3.5 выводит прошлый ответ без блока размышлений, поэтому новая
реплика никогда не продолжает закешированные id. Откатить рекуррентные состояния тоже нельзя. Вместо
этого при чтении промпта карта копирует состояния GDN на последнем `<|im_start|>` промпта (заголовке
ассистента), около 150 МБ для файла 27B. Реплика, которая начинается с id до него, возвращается туда и
читает только то, что дальше. Строки внимания до этой точки — строки промпта, которые декод не писал,
поэтому копия точна после любого раунда черновиков. Строки головы черновиков до этой точки тоже
остаются. `CMF_KV_REUSE=0` читает каждую реплику с начала.

Три реплики о файле на 10 КБ (`scripts/q27cuda/serve_chat.sh`), каждая несёт собственные ответы модели:

| реплика | промпт, токенов | чтение заново | **от снимка** |
|---:|---:|---:|---:|
| 2 | 4 048 | 4 048 за 4,13 с | **338 за 0,50 с** |
| 3 | 4 119 | 4 119 за 4,29 с | **78 за 0,24 с** |

Тексты всех трёх реплик совпадают в обоих вариантах, скорость декода тоже (99 против 97 tok/s во второй
реплике).

### DFlash 2 рядом с файлом

Опубликованный драфтер DFlash 2 (`z-lab/Qwen3.8-27B-DFlash2`) пишет раунд из семи токенов за один проход. У
него пять слоёв, а контекст — строки ствола после слоёв 5, 19, 33, 47 и 61. На этой ветке блок идёт на
карте:
- четырёхбитные матрицы — через то же ядро на тензорных ядрах;
- fc, проекции ядер свёртки и селектор — в f16 на cuBLAS;
- свёртки по строкам, нормы голов и внимание по контексту — в своих ядрах.

Графы ствола по пути копируют строки отводов, и контекст драфтера строится из них на карте.

```bash
hf download z-lab/Qwen3.8-27B-DFlash2 --local-dir dflash2
cortiq convert --model dflash2 --output qwen38-27b-q4tp.cmf --dflash-sidecar --quant q4tp   # пишет qwen38-27b-q4tp.dflash.cmf
CMF_GPU=cuda CMF_DFLASH=1 cortiq run qwen38-27b-q4tp.cmf --prompt "..." --greedy --no-think
```

Каждый раунд получает драфтер, который приносит больше токенов по ценам этой карты. Блок стоит около 0,19
обычного токена, проверка восьми строк — 1,24.
- Роутер в заголовке сайдкара читает строку ствола на кончике. Его подгоняют по записанным раундам при этих
  ценах (`cortiq dflash-route-fit … --prices`).
- Без роутера решают измеренные доли принятия драфтеров.
- Копирование остаётся у цепочки MTP: хвост повторяет восемь токенов и больше, или lookup продолжает
  попадать. Как и текст из верхней части словаря.

## Dory: зацикленный nGPT

У Nemotron Labs Dory входной блок, рекуррентный блок, который несколько раз проходит по одним и тем же весам,
и выходной блок; подслой — это внимание или MLP SwiGLU, и каждая строка лежит на единичной сфере. Модель
идёт на ядрах гибридной ветки (`gpu_cuda/hyb/dory.rs`, `dory.cu`), только файлы q4tp.

```bash
CMF_GPU=cuda cortiq run dory-turbo.cmf --prompt "..." --no-think
CMF_GPU=cuda cortiq serve dory-turbo.cmf --port 8080 --host 127.0.0.1
```

- **Токен**: каждая матрица через тензорный матвек ветки, восемь варпов на тайл и тайл на блок (матрицы
  Dory шириной от 2560 до 7168 столбцов). Gate и up — одна пара, их шкалы внесены в лестницы q4tp, так что
  эпилог матвека пишет silu(g) · u. Между матвеками: поворот с единичными головами и шкалой запроса, один
  проход по ключам (flash decoding, каждый блок под своим максимумом), гейт, остаток nGPT со строкой в
  регистрах. K и V в f16: у скользящего слоя в кольце окна и отката реплики, у полного — по позиции.
  Каждая стадия токена — один CUDA-граф.
- **Роутер** турбо-файла решает после первого прохода: карта прогоняет входной блок и этот проход, хост
  оценивает состояние (10 КБ), и карта прогоняет выходной блок или сначала второй проход.
- **Промпт** идёт через GEMM по 512 строк: каждый вес разворачивается в f16 один раз на кусок, внимание
  полного слоя — два пакетных GEMM вокруг маскированного softmax, скользящего — то же по его окну,
  развёрнутому из кольца. В турбо-файле эти строки проходят один раз. Последние ((n − 1) mod 64) + 1 строк
  проходят все циклы на тензорном пути, как последний кусок пути wgpu, поэтому текст тот же.
- **Печать** турбо-файла в конце промпта: строки полных слоёв уходят на хост, строки, которые дальнее поле
  потеряло бы, выбираются и остаются точными (`pick_exact_rows`), опорные точки строятся (`far_states`,
  поток на слой) и поднимаются как дальние поля ветки. После печати токен читает свои точные строки
  (стоки, выбранные, окно) и 32 опорные точки на голову.

|---|---|

## Ограничения

- Покрыты четыре класса архитектур: плотные стеки класса Spark (измерены на A40), гибриды семейства
  Qwen3.5 и Dory (измерены на RTX 3090) и стек Fast Code. Файл Dory q8_2f идёт на CPU. Другие MoE и стеки вида Gemma под `CMF_GPU=cuda` идут
  на CPU, а не на wgpu.
- Промпт под дальнее поле читается целиком: его строки K/V лежат на карте до печати (8,2 ГБ на
  64 000 токенов, 4,5 ГБ на пути wgpu), и его время растёт быстрее текста. Новая реплика
  запечатанного диалога читает диалог заново, как и на пути wgpu.
- Черновики работают на гибридной ветке и на стеке Fast Code, но не на плотной ветке.
- Библиотеки toolkit должны быть на пути загрузчика; привязки — под CUDA 12.x.
- Декод упирается в собственную арифметику: около 350 ГБ/с весов на A40 против 500 у ядра, которое их
  только загружает (`scripts/cuda/bench/mv_bench.cu`).

Прогон, давший эти цифры: `scripts/cuda/` (скрипты пода, промпты, бенчмарки ядер).
