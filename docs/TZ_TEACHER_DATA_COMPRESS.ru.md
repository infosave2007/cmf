# ТЗ: сжатие модели под задачу по данным учителя

**`cortiq teacher-data` + `cortiq compress`** — проектный конвейер
«данные учителя → засветка нейронов → свёртка NVG → лечение → квантизация»
внутри движка CMF.

> **Статус для релиза 0.8.38.** В релиз вошли text-only E1 v1
> (`cortiq teacher-data generate` и `teacher-data inspect`) и безопасная
> compaction существующего dense MTP-draft через `cortiq mtp-compact` /
> короткую форму `cortiq compact SOURCE.cmf PROMPTS.jsonl OUTPUT.cmf`. Это ТЗ
> всё ещё описывает последующие исследовательские стадии, в том числе ещё не
> выпущенную общую команду `cortiq compress`; его нельзя читать как справку по
> доступным флагам.
> Практическая инструкция для выпущенного пути:
> [`TEACHER_DATA.ru.md`](TEACHER_DATA.ru.md).

## 1. Цель

Сегодня специализированное сжатие делается ноутбуком на PyTorch: HF-модель,
кэш ответов, скачанный с SFTP, ручные константы в ячейках, выход —
safetensors → GGUF. Шаги не возобновляются, оценка смешана с подбором,
результат не попадает в формат CMF.

Нужно, чтобы движок делал то же самое двумя командами:

```bash
# 1. Данные учителя: учитель (.cmf) отвечает на промпты задачи
cortiq teacher-data generate qwen38-27b-q8_2f.cmf calibration_prompts.jsonl coder.tdata

# 2. Сжатие: исходная модель + данные учителя → готовый .cmf в нужной квантизации
cortiq compress Qwen/Qwen3.8-27B coder.tdata cortiq-coder-12b.cmf q4tp --size 12B
```

Результат второй команды — один `.cmf`, который сразу запускается в
`cortiq run` / `cortiq serve`, плюс отчёт о качестве по стадиям и запись
происхождения в заголовке файла.

### 1.1 Требования верхнего уровня

| # | Требование |
|---|---|
| R1 | **Удобство.** Две команды. Четыре позиционных аргумента у `compress` (исходная модель, данные, выход, квант). Всё остальное берётся из пресета. `--plan-only` до тяжёлой работы показывает, что получится: архитектуру, размер файла, память, диск, объём токенов. |
| R2 | **Воспроизводимость.** У данных и у каждой стадии есть хэш входов. Повторный запуск на том же бэкенде даёт те же байты. |
| R3 | **Возобновляемость.** `kill -9` на любой стадии, повторный запуск той же командой продолжает с места остановки. |
| R4 | **Честная оценка.** Сплит train/val/test делается по промптам. Чекпойнты выбираются только по val, итоговые числа считаются только на test. |
| R5 | **Без молчаливых усечений.** Каждая стадия печатает, сколько записей и токенов она взяла из доступных. Если данных меньше, чем нужно методу, стадия отказывает или явно предупреждает. |
| R6 | **Нативно.** Rust, GPU там, где он есть (wgpu/Metal), CPU-путь служит эталоном. |
| R7 | **Переиспользование.** Существующие механизмы (GPTQ, FCD, defrag, пробы активаций, KD top-k из `nvg-train`) вызываются как библиотека, а не дублируются. |

### 1.2 Фактический начальный срез (26.10.2026)

Это **не** заявление о готовности всего конвейера: в релизе реализованы
`.tdata` v1, `inspect` и минимальный direct-answer `generate`; остальная E2
(top-k, online stop, import/merge/resplit, resume, shard/parallel) только
спланирована. `compress` ещё не готов и цифры ниже не являются quality-gate
сжатой модели. Часть чисел и JSON-фрагментов далее зафиксирована во время
pre-release эксперимента, где бинарь выводил `cortiq 0.6.8`; они сохранены как
историческая воспроизводимая запись, а не как утверждение о версии релиза.

Для первого настоящего прогона взят существующий набор
`/Users/oleg/Documents/cortiq-bot/benchmarks/calibration_prompts.jsonl`:
483 валидных JSONL-записи с полями `id`, `category`, `prompt`, 49 категорий,
без пустых промптов и повторов `id`. Рабочий ноутбук
`/Users/oleg/Documents/cortiq-bot/colab_nvg_compress.ipynb` разобран как
эталон методики: будущий `.tdata` хранит отдельные prompt/response/token
границы, а не его плоский калибровочный текстовый поток.

Локальный Apple M4 (10 GPU cores), нативный Metal (`CMF_GPU=1`; выбор
`Apple M4` подтверждается `cortiq gpu`). Ниже — медианы устойчивых
core-decode прогонов, а не скорость первого холодного токена:

| Модель для эксперимента | Кодек | Медианная скорость decode | Назначение |
|---|---:|---:|---|
| `infosave/MiniCPM5-2B-cmf` | файл `q4tp`, заголовок `Q4Block` | **47.589 tok/s** | целевая 2B-приёмка |
| `Qwen/Qwen3.5-0.8B` (локально конвертирована) | q4tp | **113.551 tok/s** | быстрый smoke/итерации |
| `Qwen/Qwen3.5-0.8B` (локально конвертирована) | q8_2f | **72.269 tok/s** | более точный малый учитель |

Для быстрых вариантов принудительное `CMF_GPU_PROBE=0` не улучшило
результат, поэтому текущий генератор оставляет штатный адаптивный путь.
Быстрый путь первого среза — один загруженный `Pipeline`, greedy-декод с
точными `GenerateResult.token_ids`, `reset_session()` между записями и без
фиктивного top-k; он не добавляет искусственный медленный путь повторного
открытия модели или обратной токенизации текста. Это не доказательство
включения либо выигрыша MTP. Полные сырые логи хранятся только в
игнорируемом `output/tz_teacher_data_compress/`, а не в каноническом
манифесте, чтобы не нарушать воспроизводимость данных.

### 1.3 Проверенный E1-проход (`teacher-data generate`)

Реализован и проверен первый исполнимый срез команды:

```bash
cortiq teacher-data generate <teacher.cmf> <prompts.jsonl> <out.tdata> \
    --no-think --topk 0 [--max-tokens N] [--samples N]
cortiq teacher-data inspect <out.tdata> --verify --json
```

Он хэширует и разбирает исходный JSONL через один открытый файловый
дескриптор (без второй полной копии source-байтов в RAM), сохраняет
`id/category/messages`, детерминированно распределяет
промпты по category-stratified split, создаёт по одному независимому seed на
запись и пишет атомарно финализируемый `.tdata`. В `tokens.bin` кладётся
**отрендеренный префикс + фактические `GenerateResult.token_ids`**; ответ не
токенизируется повторно. `records.jsonl` является commit marker, а
`inspect --verify` повторно проверяет поток, размеры и SHA-256 всех payload
файлов, а для E1 JSONL-ledger — также `pid`/split каждой записи против
`prompts.jsonl`.

Граница токенов физически точна: в E1 все фактические
`GenerateResult.token_ids` записываются в answer-span, `think=0`. Семантика
«только ответ» верна при условии, что carried template и учитель соблюдают
`enable_thinking=false`; E1 не пытается задним числом угадать или вырезать
`<think>` из декодированного текста.

Проверка на двух точных коротких строках, выделенных из предоставленного
`calibration_prompts.jsonl`, прошла на Metal для обоих учителей:

| Учитель | Результат | Целостность |
|---|---|---|
| Qwen3.5-0.8B `q8_2f` | `255`, `Canberra`; 2/2 `usable`, `finish=stop` | `inspect --verify`: OK |
| MiniCPM5-2B (файл `q4tp`, заголовок `Q4Block`) | `255`, `Canberra`; 2/2 `usable`, `finish=stop` | `inspect --verify`: OK |

На длинных первых code-prompts тот же smoke намеренно ограничен 256 токенами:
Qwen дал 2/2, MiniCPM — 1/1 записей с `finish=length`, `truncated=true` и
`usable=false`. Это корректная защита, а не тихая потеря данных. В этом
длинном режиме end-to-end скорость одной горячей pipeline составила
**67.78 tok/s** для Qwen `q8_2f` (512 ответных токенов) и **46.51 tok/s** для
MiniCPM (256 токенов); её нельзя сравнивать со скоростью коротких ответов,
где доминируют prefill и первый токен.

Ограничения E1 намеренные и fail-closed: обязательны `--no-think` и
`--topk 0`; positive top-k появится только после runtime-захвата сырых
логитов на фактических позициях (включая MTP verifier). Публичного `--resume`
пока нет: он будет добавлен лишь вместе с проверкой identity манифеста **до**
recovery и защитой от повторной записи prompt/rid. Полная команда `compress`,
импорт/merge/resplit и online loop-stop пока остаются пунктами этого ТЗ.

Во время Qwen-smoke Metal сообщил, что batched `metal rows graph` отказался
на preflight. Это отдельный производительный риск для MTP-ускорения, который
надо диагностировать до заявлений о MTP-выигрыше: результаты выше подтверждают
выбор `CMF_GPU=1`/Apple M4, но не выдают этот отказ за успешное MTP-ускорение.

### 1.4 Уточнение границ по первоисточникам

Перед дальнейшим расширением сверены локальные исходные документы: Patent 12
задаёт для будущего `compress` сохранение архитектурных групп и
activation-weighted selection; Patent 2 — frozen-base, маски/физический
defrag и завершающий FCD; Patent 4 — валидацию эпизода и численный reward.
Они являются **источниками проектных требований**, а не доказательством того,
что эти стадии уже реализованы или дали заявленный результат.

Отсюда следуют два ограничения плана. Во-первых, E1 не объявляет себя
реализацией NVG/FCD: он только создаёт проверяемый источник prompt/response
токенов для последующих S1--S5. Во-вторых, текст Patent 12 допускает
distillation-free CE healing, тогда как этот план предусматривает KD там, где
есть честно захваченные logits; выбор между ними должен проходить отдельный
val/test gate, а не подменяться названием патента. Для сложных задач будущий
E2 сохраняет `quality.check`/`meta` как место для machine-checkable reward,
но E1 не исполняет пользовательские проверки.

## 2. Термины

| Термин | Значение в этом ТЗ |
|---|---|
| Учитель | Модель `.cmf`, чьи ответы и распределения задают целевое поведение. Это может быть сама исходная модель (самодистилляция) или модель старше. |
| Исходная модель (source) | Модель, которую сжимаем. HF-чекпойнт или `.cmf` высокой точности. |
| Ученик (student) | Сжатая модель на любой стадии. |
| Данные учителя, `.tdata` | Каталог с промптами, ответами учителя, токенами и (опционально) top-k распределениями учителя (§8). Это «данные для засветки». |
| Засветка | Прогон исходной модели по данным учителя с датчиками: энергия каждого нейрона FFN, каждой головы внимания и GDN, грамианы входов считывающих проекций (§9.5). |
| Энергетический след `E` | Вектор энергии нейронов слоя, как `gather_energy_trace` в ноутбуке. |
| Свёртка Ĉ (fold) | Структурный разрез: сохраняем множество S, выброшенные P регрессируются на S через `Π = (Σ_SS+εI)⁻¹Σ_SP` (§9.7). |
| Лечение (heal) | Обучение после свёртки: Genesis Ť (все слои, прогрессивная разморозка) и FCD (хвостовые слои целиком). Цель — KD к учителю. |
| Escort | Тензоры, которые при низкобитной квантизации оставляются в `q8_2f` по измеренной чувствительности (k/v/o, lm_head). |
| Ворота (gates) | Автоматические проверки качества, которые решают, писать ли итоговый файл (§9.10). |

| Механизм | Где | Что даёт | Чего не хватает для задачи |
|---|---|---|---|
| Генерация собственных ответов | `examples/tube_gen.rs` | Ответы модели по `calibration_prompts.jsonl` (greedy, plain text) | Это пример, а не команда. Нет id/сплитов/resume, нет top-k, нет фильтра зацикливания, ручной разбор JSON, выход — сплошной текст без разметки промпт/ответ. |
| Логиты по промптам | `cortiq dump-logits --prompts-jsonl` | Полные логиты f32 по greedy-генерации | Полный словарь (248k × f32 на позицию) не годится как формат данных. Нужен top-k. |

| Проба массы FFN | `Pipeline::probe_ffn_mass(_batch)`, `CMF_FFN_PROBE_SQ/_TOPK/_SIGNED`, `CMF_FFN_ADUMP` | Σ\|a\|, Σa², счётчики top-k по нейронам FFN | Только FFN. Нет энергии голов внимания и GDN, нет грамианов на устройстве, нет раздельных train/val аккумуляторов и скользящего окна. |
| Захват гессианов | `gptq_capture.rs`, `quantize-gptq --calib-chunk-layers` | X·Xᵀ входов линейных слоёв на GPU упакованными треугольниками, порциями слоёв | Нужен тот же механизм для грамиана входа `down_proj`/`o_proj`/`out_proj` в засветке. |
| Физический дефраг FFN | `convert --defrag DIR` (`ffn_keep.npy` формы `[L, inter]`) | Выброшенные нейроны не хранятся и не считаются, ширина по слоям может быть разной | Нет refit `down_proj` (Π), нет голов внимания и GDN, keep-set приходит извне. |
| Свёртка в замкнутой форме | `tools/nvg_fold_qwen35.py`, `docs/NVG_FOLD_ATTN_GDN.ru.md` | FFN + q-головы + GDN v-головы, Π-регрессия, печать остатка | Python, только Qwen3.5/3.8, выход в safetensors. |
| KD-данные и KD-лечение | `tools/heal_data_teacher.py`, `tools/nvg_heal_kd.py` | top-k учителя, KD-LoRA 0.3·CE + 0.7·KL | Python, сырой текст без разметки ответа. |
| FCD-коррекция | `cortiq fcd --polish-only --teacher T --kl` | Дообучение FFN и норм выбранных слоёв против отдельного учителя | CPU f32. Нет обучения внимания, нет маски «только ответ», вход — плоский текст. |
| GPU-дистилляция | `cortiq nvg-train` (`nvg_train.rs`) | Проход учителя → top-k на хосте/диске → обучение ученика Adam на GPU | Обучаются только метрика BLR и нормы, только семейство Qwen3.5. |
| Запекание навыка | `cortiq skill bake` | DTG-MA маска + FCD (`--fcd-attn` — полный слой), `--answer-after/--answer-end` | Другая задача (маска навыка), но маскирование ответа и полнослойный FCD переиспользуются. |
| GPTQ-квантизация | `cortiq quantize-gptq --codec q4tp\|q2tp`, `quantize-moe` | GPU-калибровка, `--tensor-quant`, escort-списки | Данные — плоский текст. Escort подбирается вручную (`tools/quant/escort.py`). |
| Перепаковка float-тензоров | `cortiq requant --quant q4tp-quantize` | Тензоры, оставшиеся в f32 после FCD, переводятся в q4tp | Не вызывается автоматически. |
| MoE | `moe-defrag`, `moe-mask`, `awnp`, `CMF_MOE_STATS`, `CMF_ACT_DUMP` | Удаление невостребованных экспертов, отбор входных каналов экспертов | Не связаны с данными учителя. |

**Вывод.** Почти все кирпичи есть. Не хватает четырёх вещей: формата
данных учителя, генератора этих данных, свёртки на Rust с засветкой голов
и GPU-тренера для лечения полных слоёв. И оркестратора, который связывает
всё одной командой с планом, кэшем стадий, воротами и отчётом.

## 7. Команда `cortiq teacher-data`

**Статус этого раздела.** §7.1--7.8 описывают целевой интерфейс E2+.
Единственный исполнимый интерфейс E1 зафиксирован в §1.3 и §8.0: один
локальный JSONL, новый каталог `.tdata`, обязательные `--no-think --topk 0`,
без `import`, `merge`, `resplit`, `--parallel`, `--shard`, `--check-cmd` и
public resume. Это разделение не позволяет принять проектные флаги за уже
выпущенную функциональность.

### 7.1 Синтаксис

Ниже записан **целевой** интерфейс всего конвейера. На 26.10.2026 исполнимы
только `teacher-data generate` и `teacher-data inspect` из §1.3; у generate
пока только JSONL-вход, обязательные `--no-think --topk 0`, новый пустой
`<OUT>.tdata` и нет алиаса `gen`, `resume`, `import`, `merge` или `resplit`.
`--raw` также намеренно отклоняется: E1 не станет угадывать границу hidden
reasoning у base-completion модели.

```
cortiq teacher-data generate <TEACHER> <PROMPTS> <OUT> [опции]   (алиас: gen)
cortiq teacher-data import   <SOURCE>  <OUT> --tokenizer <CMF> [опции]
cortiq teacher-data inspect  <TDATA> [--verify] [--json]
cortiq teacher-data merge    <TDATA>... -o <OUT>
cortiq teacher-data resplit  <TDATA> --split 80/10/10 [--holdout-category GLOB]
```

`<TEACHER>` — локальный `.cmf`. `<PROMPTS>` — файл или каталог (§7.2).
`<OUT>` — каталог `.tdata` (§8). Это контракт целевой версии: если он
существует и его манифест совпадает с параметрами запуска, генерация
продолжается; если не совпадает — отказ с перечнем расхождений (`--fresh`
начинает заново). В E1 существующий путь всегда отклоняется, чтобы recovery
не мог случайно продублировать ledger.

### 7.2 Входные форматы промптов

| Формат | Распознаётся по | Поля |
|---|---|---|
| JSONL объектов | `.jsonl` | обязательно `prompt` или `messages` (`[{role, content}]`); необязательно `id`, `category`, `system`, `samples`, `max_tokens`, `meta` (переносится в запись как есть). Формат `calibration_prompts.jsonl` (`id`, `category`, `prompt`) поддерживается без изменений. |
| Текст | `.txt` | один промпт на строку, или блоки через пустую строку (`--txt-blocks`) |
| Каталог | директория | все `*.jsonl` / `*.txt` в алфавитном порядке, id получает префикс имени файла |
| Кэш DTG-MA | `.json` `[[prompt, rendered], …]` | только через `import` (там уже есть ответы) |

Для будущих наборов из `TRAINING_DATA_PROMPTS.md` поля вроде сложности и
машинной проверки следует передавать без потери через `meta`, например
`"meta":{"difficulty":"intermediate","verify_patterns":["…"]}`.
Текущий E1 переносит `meta` в запись как JSON, но не интерпретирует регулярные
выражения и не запускает проверяющий код; это задача будущих `check-cmd`/E2.

Правила:

- `id` отсутствует → `sha256(normalized prompt)[:12]`. Идентичная
  нормализованная беседа отбрасывается как duplicate до проверки id; один и
  тот же явный id у разных бесед — ошибка с номерами строк. Для id-less строк
  с одним prompt, но разными system-инструкциями следует указывать явный id.
- Почти-дубли (первые 256 символов совпадают) — только предупреждение.
- Системный промпт: поле `system` записи > `--system-map FILE` (`{"category-glob": "текст"}`) > `--system TEXT` > шаблон модели.
- Строки короче `--min-prompt-chars` (по умолчанию 8) пропускаются с подсчётом. В `tube_gen` порог был 20 символов, и он молча выкидывал короткие промпты.

### 7.3 Параметры `generate`

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--samples N` | 1 | ответов на промпт (разные сиды) |
| `--max-tokens N` | 8192 | лимит генерации на ответ, включая `<think>` |
| `--think on\|off\|auto` | auto | рендер шаблона с `enable_thinking`; auto — поведение шаблона файла |
| `--reasoning-effort V` | — | бюджет рассуждения для V4.1 (как в `run`) |
| `--sampling file\|greedy\|K=V,…` | file | семплирование: рекомендованное из файла (`convert --sampling`), иначе `temperature=0.6,top_p=0.95,top_k=20,repetition_penalty=1.0` |
| `--seed N` | 42 | базовый сид; сид записи = `hash(seed, id, sample)` |
| `--topk K` | 64 | top-k распределения учителя на каждом сгенерированном токене; 0 — не писать |
| `--topk-prompt` | выкл | top-k ещё и на позициях промпта (дорого: голова считается на каждой позиции префилла) |
| `--split A/B/C` | 90/5/5 | train/val/test по промптам, стратифицировано по `category` (§8.6) |
| `--holdout-category GLOB` | — | категории целиком в test (повторяемый) |
| `--exclude-category GLOB` | — | категории не генерируются (повторяемый) |
| `--loop-stop on\|off` | on | онлайн-останов при зацикливании (§7.5) |
| `--keep-truncated` | выкл | считать ответы, упёршиеся в `--max-tokens`, годными |
| `--check-cmd CMD` | — | внешний проверяльщик ответа (§7.5) |
| `--select all\|best\|first-pass` | all | при `--samples>1` с `--check-cmd`: что оставить |
| `--parallel N` | 1 | независимых слотов генерации на одном mmap |
| `--shard I/N` | — | генерировать только промпты с `hash(id) mod N == I` |
| `--limit N`, `--skip N` | — | пробный прогон на части промптов |
| `--fresh` | выкл | удалить содержимое `<OUT>` и начать заново |
| `--gpus`, `--peer`, `--peer-split`, `--net-token` | как в `run` | рантайм учителя |

### 7.4 Алгоритм

1. Прочитать и нормализовать промпты, присвоить id, исключить дубли, назначить сплит (§8.6). Записать `prompts.jsonl` и черновой `manifest.json` (`complete: false`).
2. Открыть учителя, проверить его `dir_hash` против манифеста (при продолжении). Зафиксировать бэкенд, версию cortiq, хэши токенизатора и шаблона.
3. Сформировать очередь `(prompt, sample)` без уже записанных `rid`. Порядок очереди детерминирован и не влияет на результат: сид каждой записи зависит только от `(seed, id, sample)`.
4. Для каждой задачи: отрендерить шаблон → префилл → генерация. На каждом сгенерированном токене взять top-k логитов (ids + logprob) до семплирования и после штрафов. Для токенов, принятых спекулятивно (MTP), top-k берутся с позиций проверки. Онлайн-детектор зацикливания работает на хвосте.
5. Разобрать ответ на `think` / `content` по маркерам шаблона. Посчитать метрики качества, запустить `--check-cmd`.
6. Дописать в `tokens.bin`, `topk.bin`, затем строку в `records.jsonl`. Строка JSON — признак завершённой записи: бинарные хвосты без строки при продолжении отрезаются. После каждой записи `fsync` (или раз в `--sync-every N`).
7. В конце пересчитать статистику, хэши файлов и выставить `complete: true`.

### 7.5 Фильтры качества

| Проверка | Как | Результат |
|---|---|---|
| Зацикливание (онлайн) | каждые 64 токена: доля различных 5-грамм в окне последних 512 токенов < `--loop-min-distinct` (0.05) | генерация останавливается, `finish: "loop"`, в обучение не идёт |
| Зацикливание (итог) | доля различных 5-грамм в хвосте ответа < 0.30 | флаг `quality.loop_suspect` |
| Обрезка | достигнут `--max-tokens` | `finish: "length"`, `truncated: true`; в обучение — только с `--keep-truncated` |
| Пустой ответ | `content` пуст после `</think>` | `finish: "empty"` |
| Внешняя проверка | `--check-cmd`: JSON записи в stdin, ответ `{"pass": bool, "score": float, "note": str}` в stdout, таймаут `--check-timeout` (60 с) | `quality.check`; используется `--select` |

Внешний проверяльщик запускается как команда пользователя без песочницы.
Это фиксируется в `--help`: компилировать и запускать сгенерированный код —
ответственность скрипта.

Отклонённые записи **сохраняются** в `records.jsonl` с флагом
`usable: false`. Статистика отказов видна в `inspect`, данные можно
пересмотреть без новой генерации.

### 7.6 Вывод в консоль

```

  промпты: calibration_prompts.jsonl — <n> строк, <d> дублей, <s> коротких → <N> промптов, <C> категорий
  сплит 90/5/5 по категориям: train <a> / val <b> / test <c> промптов
  задач: <N×samples>, уже готово <k> (продолжение)
[ 37/966] algo_graph_dijkstra#0  stop  think 1 204 + ответ 811 ток.  <x> ток/с  MTP <p>%  осталось ~<ETA>
[ 38/966] ds_trie#1              loop@3 072  (отклонено)
...
готово: <N> записей, годных <g> (loop <l>, length <t>, check <c>), токенов: промпт <P> / think <T> / ответ <A>
```

ETA считается по измеренной скорости последних записей.

### 7.7 `import`

`cortiq teacher-data import <SOURCE> <OUT> --tokenizer <CMF>`:

- `SOURCE`: кэш DTG-MA `[prompt, rendered]`, JSONL `{"prompt", "response"}` или `{"messages": […]}` с ответом ассистента.
- Отрендеренный ChatML (`<|im_start|>role … <|im_end|>`) разбирается в `messages`, `<think>…</think>` выделяется в `think`. Другие шаблоны — через `--template chatml|gemma|deepseek|raw`.
- Токены считаются токенизатором `--tokenizer`, top-k нет. В манифесте `teacher.kind: "imported"`, источник и его sha256.
- Предупреждение (F19): ответы написаны другой моделью. Для KD на логитах они не годятся, только как текст.

### 7.8 `inspect`, `merge`, `resplit`

- `inspect` печатает манифест, распределение по категориям и сплитам, гистограмму длин, причины отказов и N/\|S\| для типичных ширин. `--verify` сверяет sha256 бинарных файлов и согласованность смещений. `--json` — машиночитаемо.
- `merge` требует совпадения `teacher.dir_hash`, токенизатора, шаблона, семплирования, `seed`, правила сплита и списка промптов. Записи с одинаковым `rid` — ошибка.
- `resplit` перераздаёт сплиты без перегенерации и меняет `split.rule_version`. Потребители по хэшу манифеста видят, что данные другие.

## 8. Формат данных учителя `.tdata` (версия 1)

**Статус раздела.** §8.0 — фактически выдаваемый E1-формат. §8.1–8.7 ниже
описывают целевой расширенный формат E2+ (в частности `topk.bin`, import,
merge и потребители в остальных CLI ещё не подключены). Не следует
подставлять целевые поля в манифест текущего E1.

### 8.0 Фактически выдаваемый E1 v1

Финализированный E1-каталог содержит ровно пять payload-файлов:

```
out.tdata/
  manifest.json      # immutable после finalize; SHA-256 и размеры payload
  prompts.jsonl      # принятые structured prompts и назначенный split
  records.jsonl      # commit marker: одна завершённая запись на строку
  tokens.bin         # u32 LE: rendered prefix + точные generated ids
  tokens.idx         # 40-байтные индексы записей
```

`topk.bin` и `logs/generate.log` E1 не создаёт. `response.think` и `topk`
в записях равны `null`; `gen` содержит только детерминированный `seed`.
`quality` хранит только `truncated`, `loop_suspect`, `check`; timing, tok/s,
название GPU и MTP-счётчики намеренно остаются в stderr, а не в
канонических байтах набора.

Каждая строка обоих JSONL ограничена 16 MiB тем же лимитом, что у recovery
reader; prompt-ledger проверяется до загрузки учителя/создания каталога, а
record — до записи token payload. Поэтому writer не может выпустить набор,
который его bounded reader не сумеет прочитать или возобновить.

Ключевой фрагмент текущего `manifest.json` имеет вид:

```json
{
  "format": "cmf-tdata", "version": 1, "complete": true,
  "cortiq": {"version": "0.6.8"},
  "teacher": {"kind": "cmf", "file": "teacher.cmf",
              "directory_hash": "<16-hex>", "trunk_hash": "<16-hex>",
              "integrity": "verified-all-cmf-tensors-v1", "architecture": "<arch>",
              "quantization": "<codec>"},
  "tokenizer": {"vocab_size": 0, "eos_id": 0,
                "vocab_sha256": "<sha256>", "config_sha256": "<sha256>",
                "template_sha256": "<sha256>"},
  "template": {"mode": "carried", "thinking": "off"},
  "topk": {"k": 0, "positions": "none"}
}
```

Перед генерацией E1 перепроверяет хэши **всех** тензоров загруженного CMF,
включая sibling-шарды, и записывает merged `trunk_hash`; `directory_hash`
сохраняется для legacy/base-identity, но относится только к primary shard.
Это не дорогой криптографический SHA-256 каждого файла `.cmf`, а встроенный
контракт CMF после полной проверки payload. Вход должен быть одним JSONL-файлом;
учитель обязан нести chat template и embedded tokenizer. `<OUT>.tdata` не
должен существовать даже пустым. При аварии остаётся `complete:false`,
который `inspect`/reader не принимают; публичного `--resume` пока нет.
Итоговая проверка хвоста (`<30%` различных 5-грамм) только помечает запись
`loop_suspect=true`, `usable=false`: она не является online-stop и не меняет
`finish` в `loop`.

### 8.1 Целевая структура каталога E2+

```
coder27.tdata/
  manifest.json      # идентичность, параметры, статистика, хэши файлов
  prompts.jsonl      # нормализованные промпты с id, category, split
  records.jsonl      # одна строка на сгенерированный ответ (§8.3)
  tokens.bin         # u32 LE: полная отрендеренная последовательность каждой записи
  tokens.idx         # фиксированные записи по 40 байт для произвольного доступа (§8.4)
  topk.bin           # top-k учителя на сгенерированных позициях (§8.5), если --topk > 0
  logs/generate.log
```

Все бинарные файлы только дописываются. Каталог переносим: путей
к машине генерации внутри нет, кроме информационного `teacher.path`.


### 8.4 `tokens.bin` / `tokens.idx`

- `tokens.bin`: подряд u32 LE id токенов каждой записи: префикс шаблона + промпт + сгенерированное (think, ответ, EOS).
- `tokens.idx`: 40 байт на запись, в порядке `records.jsonl`:

| Поле | Тип | Смысл |
|---|---|---|
| `tok_offset` | u64 | смещение в `tokens.bin` (в токенах) |
| `total` | u32 | всего токенов |
| `prompt` | u32 | токенов до первого сгенерированного |
| `think` | u32 | сгенерированных токенов рассуждения (включая маркеры) |
| `answer` | u32 | сгенерированных токенов ответа (включая EOS) |
| `topk_offset` | u64 | смещение в `topk.bin` (в позициях); `u64::MAX`, если top-k нет |
| `flags` | u32 | бит 0 — usable, 1 — truncated, 2 — loop, 3 — check failed |
| `split` | u8 + 3 резерв | 0 — train, 1 — val, 2 — test |

### 8.5 `topk.bin`

На каждую сгенерированную позицию `t` (в порядке генерации):

```
ids:      k × u32 LE   — id в порядке убывания вероятности
logprob:  k × f16 LE   — log p учителя (после температуры 1, до отсечений семплера)
rest:     1 × f16 LE   — log(1 − Σ p_i), остаточная масса вне top-k
```

Размер позиции: `6k + 2` байт (k = 64 → 386 Б). При 5 млн
сгенерированных токенов это ≈ 1.9 ГБ, при k = 32 ≈ 0.97 ГБ.

Распределение берётся с температурой 1 по сырым логитам, а не по
распределению семплера: KD учит распределению модели, а не настройкам
семплирования.

### 8.6 Сплиты

- Единица сплита — **промпт**: все `samples` одного промпта лежат в одном сплите, утечки между сплитами нет.
- В каждой категории `c` промпты сортируются по `sha256("split-v1" ‖ split_seed ‖ id)`. Первые `round(n_c·r_test)` идут в test, следующие `round(n_c·r_val)` — в val, остальное — в train. Категория с `n_c < 3` целиком уходит в train и попадает в список предупреждений.
- `--holdout-category` отправляет категорию целиком в test (проверка обобщения на невиданный тип задач).
- Сплит записывается и в `prompts.jsonl`, и в каждую запись. Потребители не пересчитывают его сами.

### 8.7 Целевые потребители `.tdata` E2+

Селектор и потоковый reader уже существуют внутри CLI, но на дату этого
среза единственный подключённый пользовательский consumer —
`teacher-data inspect`. Интеграции в `quantize-gptq`, `fcd`, `skill bake` и
`nvg-train` ниже являются планом, а не обещанием работающих флагов.

Селектор: `PATH.tdata[:split][=SHARE]`, где `split` — `train` (по умолчанию),
`val`, `test` или `all`. Доли `=SHARE` работают как в нынешнем
`--calib PATH=SHARE`.

| Команда | Что берётся |
|---|---|
| `quantize-gptq`, `quantize-moe`, `convert --quant blr --calib`, `nvg-bench` | токены записей `usable` выбранного сплита, окнами `--window`, границы записей уважаются |
| `fcd --corpus/--val-corpus` | записи как последовательности; лосс по ответу (`--loss-on answer`, новое) |
| `skill bake --files/--held-files` | записи как chat-records (вместо разбора по `--record-start`) |
| `nvg-train --calib` | токены; при совпадении токенизатора — готовые top-k вместо прохода учителя |

Попутно исправляется чтение кэша DTG-MA `[prompt, rendered]`: если второй
элемент начинается маркером шаблона, берётся только он, без повторного
промпта.

## 9. Команда `cortiq compress`

### 9.1 Синтаксис

```
cortiq compress <SOURCE> <DATA> <OUTPUT> [QUANT] [опции]
```

| Аргумент | Смысл |
|---|---|
| `SOURCE` | HF repo id, локальный HF-каталог или `.cmf` (f16/bf16/q8/q8_2f) |
| `DATA` | `.tdata` (селектор §8.7 допустим). Дополнительные наборы — `--data PATH=SHARE` (повторяемый) |
| `OUTPUT` | итоговый `.cmf` |
| `QUANT` | кодек итогового файла, значения как у `convert --quant`; по умолчанию `q4tp`. Эквивалентно `--quant` |

Цель сжатия задаётся одним из вариантов:

| Флаг | Пример | Смысл |
|---|---|---|
| `--size` | `12B`, `900M` | целевое число параметров (без MTP), аллокатор подбирает ширины |
| `--ratio` | `0.45` | доля параметров исходной модели |
| `--ffn` | `12288` или `0.7` | ширина FFN (абсолютная или доля); с `--allocate curve` — средняя |
| `--heads` / `--gdn-v-heads` | `16` / `32` | q-головы на слой (внутри GQA-групп) / value-головы GDN (внутри k-групп) |
| `--layers` | `48` | глубина с сохранением рисунка гибрида (F9: предупреждение) |
| `--experts-cover` | `0.95` | MoE: доля массы маршрутизации, которую сохраняют эксперты |
| `--plan` | `plan.json` | готовый план (из `--plan-only` или правленный вручную) |
| ничего | — | только квантизация (`--recipe quant-only`) |

### 9.2 Пресеты

| Стадия | `fast` | `balanced` (умолч.) | `full` | `notebook` | `quant-only` |
|---|---|---|---|---|---|
| S1 засветка | ✓ | ✓ | ✓ | ✓, окно 10128/5120, энергия RMS + 0.3·σ | — |
| S2 раздача ширины | равномерно | по кривым остатка | по кривым остатка | вручную, как `MANUAL_INTERMEDIATE_SIZE` | — |
| S3 refit Π | по val | по val | по val | аналитический Σ, rescale, ρ_c, Born + осмос | — |
| S4 лечение | — | FCD хвоста, KD | Genesis + FCD, KD | Genesis 6 эпох + FCD 20 слоёв, CE по всему тексту | — |
| S5 квант | GPTQ 32k | GPTQ 64k + escort auto | GPTQ 64k + escort auto + FCD хвоста после кванта | GPTQ 64k | GPTQ 64k + escort auto |
| S6 оценка | базовая | полная | полная | полная | полная |

`notebook` воспроизводит ноутбук для сравнения, в том числе его известные
слабые места (CE по всему тексту, F1). Он нужен для A/B, а не как
рекомендация.

### 9.3 Параметры по группам

**Данные**

| `--lora-rank R` | 64 | ранг LoRA |
| `--kd-teacher auto\|source\|data\|FILE` | auto | откуда KL: auto — top-k из данных, если токенизатор совпал, иначе исходная модель |
| `--kd-alpha A` | 0.3 | вес CE; вес KL = 1 − A |
| `--kd-topk K` | 64 | top-k учителя для KL |
| `--genesis-epochs N` / `--genesis-lr X` | 2 / 2e-5 | фаза A |

| `--fcd-epochs N` / `--fcd-lr X` | 2 / 1e-5 | фаза B |
| `--seq N` | 4096 | длина обучающей последовательности; длинные записи режутся окнами, содержащими ответ |

### 9.5 S0 — подготовка источника

1. `SOURCE`: HF id или каталог → один потоковый проход `convert` в `src-f16.cmf` (структурные операции требуют высокой точности весов) и, если хукам засветки нужны mmap-квантованные тензоры, в `src-q8_2f.cmf` через `--also-output` (одна загрузка). `.cmf` f16/bf16 используется на месте. q8/q8_2f — с предупреждением. 4 бита и ниже — отказ (`--allow-lossy-source` снимает).
2. Совместимость с данными:
   - токенизатор (sha256) совпал → токены `.tdata` используются как есть, top-k доступны для KD;
   - не совпал → записи перерендериваются шаблоном исходной модели из `messages`/`response`, top-k отключаются, `--kd-teacher auto` переходит на `source`. Об этом печатается одна строка с причиной.
3. Проверки архитектуры по матрице §11. Неподдержанная операция — отказ с названием операции и архитектуры, а не молчаливый пропуск.

### 9.6 S1 — засветка

Прогон **исходной** модели (F19) префиллом, без генерации, по записям
`usable` сплитов train и val. Train и val копятся в раздельные
аккумуляторы. Длинные записи — скользящим окном `--window/--stride`
с добором хвоста ≥ 128 токенов, как в ноутбуке.

Датчики (для каждого слоя `l`):

| Где | Что копится | Зачем |
|---|---|---|
| вход `down_proj` (`a = act(gate)·up`) | Σa, Σa², Σ\|a\|, попадания в top-k токена; по окнам Σ_w RMS_w, Σ_w σ_w | энергия нейрона `E_j` |
| то же | грамиан `Σ = Σ_t w_t a_t a_tᵀ` (f32, упакованный треугольник, на устройстве) | Π-регрессия, кривые остатка |
| вход `o_proj` (уже с output-gate) | энергия по q-головам + грамиан | свёртка голов внимания |
| вход `out_proj` GDN (после gated-norm) | энергия по value-головам + грамиан | свёртка голов GDN |
| резидуальный поток | `‖h_out − h_in‖² / ‖h_in‖²` | чувствительность слоя для глубины и защиты |
| маршрутизатор MoE | счётчики и масса по экспертам (`CMF_MOE_STATS`) | `--experts-cover` |

`w_t` — вес записи по `--balance`.

Энергия:

```
rms:      E_j = sqrt( Σ_t w_t a_tj² / Σ_t w_t )
notebook: E_j = (1/W) Σ_w ( RMS_w(a_·j) + 0.3·σ_w(a_·j) )      # как gather_energy_trace
mass:     E_j = Σ_t w_t |a_tj| / Σ_t w_t
нормировка внутри слоя: Ē_j = E_j / mean_j(E_j);  энергия слоя = Σ_j E_j до нормировки
```

Из грамиана train сразу строится **кривая остатка** слоя для всех
префиксов keep-set (§9.7): одна факторизация Холецкого на слой даёт
остаток для любой ширины, поэтому аллокатору не нужен второй проход.

Память: грамиан FFN шириной n в f32-треугольнике занимает `2·n(n+1)` байт.
Для 27B (n = 17408) это 0.61 ГБ на слой и сплит, 77.6 ГБ на 64 слоя
train + val. Поэтому слои идут порциями `--chunk-layers`. Грамианы
пишутся на диск (`--keep-grams auto`, если хватает места), иначе
пересчитываются в S3 вторым проходом.

Выход: `energy.stats` (заголовок JSON + массивы LE f32/f64), `curves.json`,
печать top-5/bottom-5 слоёв по энергии (как в ноутбуке) и строка
«взято X записей / Y токенов из Z».

Обязательные инварианты (F12): ни у одного слоя нет нулевой энергии;
пока проба активна, слитые цепочки устройства открываются для хука.

### 9.7 S2 — план и S3 — свёртка Ĉ

**Важность и keep-set (слой l, FFN):**

```
energy (умолч.):  imp_j = ‖W_down[:, j]‖² · ⟨a_j²⟩
nvg-born:         W̃ = W ⊙ Ē (линзирование по выходной оси для gate/up, по входной для down),
                  U,S,Vᵀ = svd(W̃);  e_j = ‖(U·S)_j‖² (или ‖(S·Vᵀ)_·j‖²);
                  imp_j = e_j + 0.5·|Δ log(e_j + 1e-5)|;  imp = imp_gate + imp_up + imp_down
ρ_c (опция):      из нейронов с imp_j / max(imp) > 0.382 берутся top-k, если их хватает
```

Нейроны упорядочиваются по убыванию `imp`. Keep-set ширины k — префикс
этого порядка. Внутри тензора сохранённые индексы идут по возрастанию
(локальность, как `torch.sort(top_indices)` в ноутбуке).

**Кривая остатка (одна факторизация на слой).** Пусть `Σ` переставлен
в порядке важности, `Σ = L·Lᵀ`. Для префикса S = первые k:

```
условная ковариация выброшенных:  Σ_PP|S = L[k:, k:] · L[k:, k:]ᵀ
выходная ошибка без refit:        e0(k) = tr( W_P Σ_PP W_Pᵀ )
выходная ошибка с refit:          e1(k) = ‖ W_P · L[k:, k:] ‖_F²
относительная:                    c_l(k) = e1(k) / tr( W Σ Wᵀ )
```

Все k получаются из одной факторизации `O(n³/3)` (на GPU — с
уравновешиванием, как в GPTQ). Для голов внимания и GDN то же самое
по блокам голов внутри групп.

**Аллокатор (`--allocate curve`).** Минимизирует `Σ_l s_l·c_l(k_l)` при
`Σ_l bytes_l(k_l) ≤ бюджет`. Ограничения: `k_l` кратно `--align`,
`k_l ≥ min-width·n`, защищённые слои — полная ширина. Метод — жадное
снятие ширины с наименьшим приростом стоимости на байт (кривые монотонны).
`s_l` — чувствительность слоя: 1 по умолчанию, `--sens resid` берёт
резидуальную метрику S1. Рядом печатается спектральная рекомендация ρ_c
из ноутбука (`compute_spectral_target_vmf`) — для сравнения, на решение
она не влияет.

**План** (`plan.json`, Приложение B) фиксирует: ширины и головы по слоям,
параметры и размер файла по компонентам для выбранного кодека и всех
`--also-output`, N/\|S\| по слоям, предупреждения, ресурсы стадий.
`--plan-only` печатает его и выходит. `--until S2` строит его по данным.

**Свёртка (S3), слой l:**

```
Π = (Σ_SS + ε·mean(diag Σ_SS)·I)⁻¹ Σ_SP                  # |S|×|P|, f64 на CPU или f32 с уравновешиванием на GPU
W_down' = W_down[:, S] + W_down[:, P] · Πᵀ
W_gate' = W_gate[S, :],  W_up' = W_up[S, :]               # (+bias[S], если есть)
внимание: W_o' = W_o[:, S_h] + W_o[:, P_h] · Π_hᵀ;  W_q' = строки {q_h, gate_h : h ∈ S}; W_k, W_v, нормы — без изменений
GDN:      W_out' по value-головам; in_proj_qkvz' — v_h, z_h для h ∈ S; in_proj_ba', conv1d', A_log', dt_bias', norm' — элементы S
```

**Выбор риджа по val (`--refit auto`).** Для каждого ε из сетки считается
выходная ошибка на **val**-грамиане:

```
e_val(Π) = tr( W_P (Σᵛ_PP − Πᵀ Σᵛ_SP − Σᵛ_PS Π + Πᵀ Σᵛ_SS Π) W_Pᵀ )
```

Берётся ε с минимумом. Если `e_val(Π) ≥ e_val(0)` (refit на val не
помогает), слой режется без refit. Решение и обе ошибки пишутся в
`fold.json` и в журнал. Это прямая защита от F2.

**MTP:** `keep` — блок копируется байт в байт. `compress` — как в ноутбуке,
энергия последнего слоя в роли прокси. `drop` — блок не пишется.

**Тест тождества:** при keep = 100 % свёртка обязана дать на том же пути
исполнения логиты, побайтно равные исходным.

Выход: `fold-f16.cmf` с метаданными архитектуры по слоям (ширина FFN,
число голов), запись `provenance.compress.fold`, после чего сразу идёт
быстрая проба живости (как `test_liveness`).

### 9.8 S4 — лечение

**Данные:** записи train в шаблоне исходной модели. Лосс считается по
`--loss-on`, контекст промпта подаётся полностью. Записи длиннее `--seq`
режутся окнами, каждое из которых содержит токены лосса. `--general`
подмешивается по доле. Val — для выбора чекпойнта, test не трогается.

**Учитель KL (`--kd-teacher`):**

- `data` — top-k из `.tdata` (только при совпадении токенизатора; распределение настоящего учителя);
- `source` — проход исходной плотной модели по тем же окнам, top-k (`--kd-topk`) на хост/диск (`kd_topk.bin`), потом модель освобождается. Это механизм `nvg-train --topk-cache`;
- `FILE` — любой `.cmf` с тем же токенизатором.

**Лосс:**

```
L = α · CE(y_t)  +  (1 − α) · KL_k(p_T ‖ q_S),         α = --kd-alpha (0.3)
KL_k = Σ_{i∈topk} p_i log(p_i / q_i)  +  r_T log(r_T / r_S),
       r_T = 1 − Σ_{i∈topk} p_i,   r_S = 1 − Σ_{i∈topk} q_i       # остаточная масса — отдельная корзина
```

**Фаза A — Genesis Ť** (пресет `full`, перенос ячейки §7):

- обучаемые: все слои + финальная норма + lm_head (+ MTP при `keep`);
- прогрессивная разморозка по эпохам: последние [round(3L/16), round(3L/8), round(5L/8), все] слоёв (для L = 64 это ровно [12, 24, 40, all] ноутбука);
- LR слоя i: `lr · e^{−κ·d_i}`, `κ = 0.1/(epoch+1)`, `d_i` — расстояние от начала окна разморозки;
- VMF-буст: `s = W_t/W_0`; `ρ = s, если s ≤ 0.5, иначе 1 − s`; `H² = ρ(1 − ρ/ρ_c)`; буст 1.0 при H² > 0.05, 1.3 при H² > 0, иначе 1.5;
- расписание `lr(t) = lr₀ (1 − e^{−t/τ}) e^{−t/(2T)}`, `τ = T/3`; клиппинг нормы градиента 1.0.

**Фаза B — FCD** (Patent 2 §4.5, перенос ячейки §7.5): последние
`--fcd-layers` слоёв целиком (внимание/GDN, MLP, нормы, MTP), AdamW,
`lr 1e-5`, косинус до 0.1·lr, `--fcd-epochs` эпох.

**Выбор чекпойнта:** каждые `--eval-every` шагов считаются KL и NLL на val.
При `--gen-gate on` дополнительно генерируются до 8 промптов val и
проверяются воротами G1 (§9.10). Годный чекпойнт с минимальным val-KL
восстанавливается в конце. Нулевой шаг (до лечения) — тоже кандидат,
поэтому лечение не может ухудшить val.

**Режимы памяти:** `full` — обучаемые слои с f32-мастер-весами (или bf16
с компенсацией) и 8-битными моментами, остальные заморожены в f16/q8;
`lora` — LoRA ранга `--lora-rank` на всех проекциях обучаемых слоёв,
после обучения сливается в f16 (без двойной квантизации, как в
`nvg_heal_kd.py`). `auto` выбирает `full`, если планировщик укладывается
в память, иначе `lora` и сообщает об этом.

Выход: `healed-f16.cmf` (обученные тензоры в f16), `train.jsonl`
(шаг, лоссы, lr, val, ворота).

### 9.9 S5 — квантизация

1. `q4tp` / `q2tp`: GPTQ на вылеченной f16 (библиотечный вызов `quantize-gptq`), калибровка — токены train из данных (+ `--general` по доле), `--calib-tokens`, `--calib-window`, гессианы на GPU одним проходом или порциями.
2. `--escort auto`: чувствительность кандидатов (k/v/o каждого слоя, lm_head) измеряется на val как рост KL при кванте одного тензора (перенос `tools/quant/escort.py`). Набор с наибольшим выигрышем на бит берётся в пределах `--escort-budget`.
3. `q8_2f`, `q4t` и прочие кодеки без GPTQ — обычное кодирование конвертера.
4. `blr` — NVG-кодировщик (`convert --quant blr --blr-method nvg`) с калибровкой из данных. Для Qwen3.5 дальше `nvg-train` с теми же данными и учителем.
5. Все float-тензоры после лечения перекодируются в кодек профиля (F11).
6. `--post-fcd N`: короткий FCD последних N слоёв уже квантованной модели против учителя, эти слои пишутся в `q8_2f`.
7. `--also-output`: каждый дополнительный кодек из той же `healed-f16.cmf`.

### 9.10 S6 — оценка, ворота, отчёт

Измеряется на **test** (кроме отмеченного):

| Метрика | Как |
|---|---|
| NLL ответа | средний −log p ученика на токенах ответов учителя в test |
| KL к учителю | по top-k (если есть) на тех же позициях |
| Согласие top-1 | доля позиций, где argmax ученика = argmax учителя |
| Генерация | `--eval-prompts` промптов test, greedy и семплирование из файла: `finish`, длина ответа / длина у учителя, доля различных 5-грамм в хвосте, `--check-cmd` |
| Общий текст | ppl на `--general-eval` (если задан), протокол `cortiq ppl` |
| Размер и скорость | размер файла, `cortiq bench` декод/префилл на текущем устройстве, принятие MTP |

Строки отчёта:

| Вариант | Откуда |
|---|---|
| исходная (f16 или q8_2f) | S0 |
| `quant-only` — исходная в том же кодеке с GPTQ на тех же данных | `--baseline quant-only` (умолч.) |
| `naive` — равномерный разрез по ‖W‖ без засветки, refit и лечения | `--baseline naive` |
| свёртка | S3 |
| + лечение | S4 |
| + квант (итог) | S5 |

Ворота (пороги настраиваются `--gate-*`):

| Ворота | Условие | При провале |
|---|---|---|
| G0 загрузка | `cortiq verify` проходит, генерация идёт, нет NaN/Inf | код 5 |
| G1 генерация | ни одного зацикливания на test-промптах (distinct-5 хвоста ≥ 0.30); медиана длины ответа ≥ 0.7 от учителя; доля `stop` не ниже учительской более чем на 10 п.п. | код 5 |
| G2 качество | NLL ответа итога не хуже `naive` того же размера (если `naive` посчитан); каждая стадия не хуже предыдущей на val (обеспечено восстановлением лучшего) | код 5 |
| G3 общий текст | рост ppl на `--general-eval` ≤ `--gate-general-rise` (по умолчанию только печать) | предупреждение |

При провале ворот итоговый файл не пишется (кроме `--write-on-fail` →
`<OUTPUT>.rejected.cmf`), отчёт пишется всегда.

`report.md` / `report.json`: таблица стадий, план, решения S3 по слоям
(ширина, ε, остаток), кривая лечения, escort, ворота, примеры генераций
(`samples.jsonl`). В заголовок итогового `.cmf` пишется
`provenance.compress`: идентичность источника и данных (sha256 манифеста,
`teacher.dir_hash`), план, параметры стадий, метрики S6, версия cortiq.

### 9.11 Ресурсный планировщик

Перед стартом и в `--plan-only` для каждой стадии печатаются пиковые ОЗУ,
VRAM и диск. Лимиты берутся из cgroup (F18), `cortiq gpu` и `statfs`
рабочего каталога.

| Стадия | Основная статья расхода |
|---|---|
| S0 | диск: f16 = 2 Б/параметр (+ q8_2f ≈ 1.06 Б/параметр при необходимости) |
| S1 | грамианы `2·n(n+1)` Б на слой и сплит × `--chunk-layers`; диск при `--keep-grams` |
| S3 | один слой f64-факторизации `8·n²` Б (CPU) или f32 на устройстве; выход f16 |
| S4 | `full`: обучаемые параметры × (вес + градиент + моменты) + активации окна с чекпойнтингом по слоям; `lora`: замороженная база + адаптеры |
| S5 | гессианы GPTQ (27B на GPU: ≈ 50 ГБ за один проход, измерено) |

Если стадия не помещается, планировщик предлагает конкретную замену
(`--chunk-layers 8`, `--heal-mode lora`, `--keep-grams off`,
`--work-dir /local/disk`) или отказывает с кодом 4 до начала работы.
Рабочий каталог на сетевой ФС — предупреждение.

### 9.13 Коды выхода и типичные отказы

| Код | Когда |

## 12. Тестирование и приёмка

**Модульные (CI):**

- `.tdata`: round-trip, детерминизм сплита, селекторы, `merge` с несовпадающими манифестами (отказ), обрезка недописанного хвоста при продолжении.
- Детектор зацикливания, включая случай одной гигантской строки (F14).
- KL с остаточной корзиной: совпадение с полным KL, когда k = vocab.
- Решатель Π и кривые Холецкого против явных решений (f64-эталон).
- Аллокатор: бюджет, кратность, защита, монотонность.
- Расписания Genesis (LR, разморозка, VMF-буст) против формул ноутбука.

**Интеграционные (CI, крошечная синтетическая модель, как в `crates/cortiq-engine/tests/fcd_train.rs`):**

- `teacher-data generate` на 8 промптах → `compress --ffn 0.5 --recipe full` → файл грузится, генерирует, отчёт полный.
- Тождество свёртки при keep 100 %.
- Прерывание после каждой стадии (`CMF_COMPRESS_ABORT_AFTER`) → тот же sha256 итога.
- top-k генерации ≡ teacher-forced top-k.

**Сверка с эталонами (данные в `tests/data`, Python в CI не запускается):**

- энергия `--energy notebook` против `gather_energy_trace` ноутбука;
- свёртка против `tools/nvg_fold_qwen35.py` (Π, остатки, итоговые веса одного слоя).

**Приёмочный прогон (вручную, на стенде владельца):**

- Этап 1: MiniCPM5-2B или Qwen3.5-2B, `calibration_prompts.jsonl`, `--ffn 0.75`, q4tp. В отчёте строка «+ лечение» лучше строки «свёртка», итог лучше `naive` того же размера, ворота G0–G2 пройдены, файл работает в `run` и `serve`.
- Этап 2: Qwen3.8-27B → цель по решению владельца (D1), `--recipe full`.

Кросс-модельный регрессионный прогон для этой работы не нужен: новые пути
не меняют существующие ядра. Хватает тестов и CI.
