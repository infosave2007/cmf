# CMF v2 — Спецификация формата

*Языки: [English](CMF_V2_SPEC.md) · **Русский** · [中文](CMF_V2_SPEC.zh.md)*

**Cortiq Model Format** — единый файл, несущий всё необходимое для
разреженного, маршрутизируемого по задачам инференса: квантованные веса,
токенизатор, маски по задачам, предвычисленный разреженный
индекс — и, что уникально, **рой скиллов**, разделяющих одну базовую модель
(Patent 15).

> Нормативный источник: этот документ. Референсные
> реализации: Rust-ридер/рантайм (`crates/cortiq-core`,
> `crates/cortiq-engine`), Python-райтер (`converter/`) и
> ридер на Python без зависимостей (`python/cmf_reader.py`, только numpy).

Три требования, в порядке приоритета:

1. **Корректность.** Никаких режимов тихого повреждения: строгий magic,
   версия, `required_features`, границы на каждую секцию, 64-битный хэш на
   каждый тензор. Файл либо валиден, либо open() возвращает ошибку — третьего
   состояния нет.
2. **Скорость.** Секция весов выровнена по странице для mmap, каждый тензор
   выровнен по 64 байтам (SIMD без копирования), каталог тензоров бинарный —
   читается без разбора. Холодные (замаскированные) веса не стоят RSS.
3. **Компактность.** Маски упакованы побитово (1 бит на нейрон), веса —
   q4/q8/переменной битности, весь файл адресуется одним 128-байтовым
   конвертом.

Гармония достигается не количеством фич, а **единым каноном**: одна
раскладка на уровень (конверт, каталог, квант-блок, маска), байт-в-байт
совместимая с валидированным форматом `.vmfc` v2 там, где домены
пересекаются (каталог тензоров, раскладки квантования, `hash64`). Никогда
двух определений одного и того же.

CMF — инженерный контейнер: общая основа сочетается с масками и накладками
задач без копирования и изменения самой основы. Формат хранит измеренные
метрики качества и явно описывает детали реализации, включая масштабы строк
и входных каналов, чтобы читатель мог проверить каждый раздел.

---

## 1. Конверт (фиксированные 128 байт)

Все целые числа — little-endian.

```
[0x00 : 0x04]  magic              = b"CMF\x01"  (4 bytes)
[0x04 : 0x08]  version            : u32 = 2
[0x08 : 0x0C]  flags              : u32 (reserved, 0)
[0x0C : 0x10]  required_features  : u32 (bitmask, §1.1)
[0x10 : 0x18]  header_off         : u64 (= 128)
[0x18 : 0x20]  header_len         : u64   — JSON header (§2)
[0x20 : 0x28]  dir_off            : u64   — tensor directory (§3)
[0x28 : 0x30]  dir_len            : u64
[0x30 : 0x38]  data_off           : u64   — weight blob; multiple of 4096 (§4)
[0x38 : 0x40]  data_len           : u64
[0x40 : 0x48]  masks_off          : u64   — masks section (§5); 0 = absent
[0x48 : 0x50]  masks_len          : u64
[0x50 : 0x58]  vocab_off          : u64   — tokenizer (§6); 0 = absent
[0x58 : 0x60]  vocab_len          : u64
[0x60 : 0x68]  index_off          : u64   — sparse index (§7); 0 = absent
[0x68 : 0x70]  index_len          : u64
[0x70 : 0x80]  reserved           : 16 bytes (§8.1: header/dir hashes)
```

Порядок секций на диске: конверт → JSON-заголовок → каталог → **блоб
весов (выровнен по 4096)** → маски → словарь → разреженный индекс. Ридер
ОБЯЗАН адресовать секции ТОЛЬКО через конверт, никогда не предполагая
порядка. Это не только правило стиля: после дописывания в хвост (§9.3)
заголовок и каталог лежат ПОСЛЕ данных, а маски, словарь и индекс — ВНУТРИ
расширенного диапазона `[data_off, data_off + data_len)`. Проверки
непересечения секций нет и быть не должно.

### 1.1 `required_features`

Бит, которого ридер не знает → ошибка `UnsupportedFeature` (fail-fast;
никакого «читаем как можем»).

| bit | name           | значение |
|-----|----------------|---------|
| 0   | `TENSOR_DIR`   | бинарный каталог тензоров (всегда установлен в v2) |
| 1   | `BINARY_MASKS` | секция масок (§5) присутствует |
| 2   | `QUANT_2F`     | каталог содержит тензоры `q8_2f`/`vbit` (многомасштабное квантование) |
| 3   | `DELTA_MASKS`  | reserved: XOR-дельты масок от родителя |
| 4   | `HOT_PACKS`    | reserved: материализованные плотные срезы |
| 5   | `LOOP_MASKS`   | ряды масок хранятся ПО ВИЗИТАМ (физические слои × циклы, проход-мажорно) — у зацикленного трансформера каждый проход несёт независимую маску (§5.1) |
| 6   | `SKILL_FILE`   | файл — САМОСТОЯТЕЛЬНЫЙ СКИЛЛ: частичный набор тензоров, вырезанный против конкретной базы и привязанный ключом `SkillRecord.base_dir_hash` (§9.1). Не запускается — прикладывается через `cortiq skill apply` |
| 7   | `PRISM_HADAMARD` | матрицы Prism/Bonsai в знаковом базисе FWHT и контракт границы активаций (`arch.prism_hadamard`, `arch_name = prism_hadamard_qwen35`). Бит ⇔ запись в обе стороны: ридер отвергает файл, где они расходятся |
| 8   | `PRISM_AFFINE` | явная аффинная поправка q2tp `(c − 1.0)·s` для перечисленных Prism-матриц (`prism_hadamard.affine`). Отдельный бит, чтобы поправку нельзя было вывести из одного `arch_name`; бит ⇔ дескриптор в обе стороны |
| 9   | `SKILLS_V2`    | в реестре есть запись навыка v2 (`skills[i].kind`, §9.5): каждая такая запись проверяется против генома, к которому привязана, и против каталога; неизвестный или зарезервированный `kind` — отказ |
| 10  | `ROUTER_V2`    | файл объявляет политику маршрутизации v2 (`header.router`, §9.4): автоматически маршрутизировать может ТОЛЬКО объявленная политика `backbone_gated`, по умолчанию исполняется ствол. Ридер, который откатился бы к argmin по навыкам, обязан отказать |
| 11  | `DECISION`     | негенеративный профиль решений (`cortiq-decision`: энкодер, контракт хеширования, резонансные навыки; метаданные — тензор `decision.manifest`). Исполняется рантаймом решений (`cortiq decide`, `cortiq serve`), НИКОГДА языковым конвейером. Писатель выводит бит из префикса `arch_name` `cortiq-decision-`; ридер отвергает файл, где бит и префикс расходятся |
| 12  | `BOUNDED_STATE` | файл несёт НАТИВНО ОГРАНИЧЕННЫЙ оператор внимания (`LayerType::BoundedAttention` + `arch.anchor_core`, §2.3): состояние каждого слоя — запись фиксированного размера, выводимая из заголовка. Ридер ОБЯЗАН исполнять якорь кольцом + обученными sink-векторами и не вправе подменять его маской поверх растущего KV; `CMF_O1_*`/`--o1` к такому файлу не применяются. Писатель ставит бит тогда и только тогда, когда запись `anchor_core` присутствует; ридер отвергает файл, где бит и запись расходятся |
| 13  | `GENOME`       | файл несёт ЗАМОРОЖЕННЫЙ ГЕНОМ (`header.genome`, §9.2): ридер пересчитывает `trunk_hash` по каталогу, `arch`, словарю, `tokenizer_config` и секциям масок/индекса и отвергает файл при расхождении — ствол нельзя изменить без нового генома |

Биты 7–13 **выводятся писателем из содержимого** (`CmfModel::write`,
`write_ref`, потоковый `CmfStreamWriter::finish`, дописывание в хвост —
общая функция `derive_required_features`) и никогда не ставятся вручную:
бит, выставленный экспортёром руками, тихо пропал бы при первой же
перезаписи (калибровке), и старый ридер открыл бы файл. `open()` проверяет
«бит ⇔ содержимое» в обе стороны, как для `BOUNDED_STATE`. Ридер до этих
битов такие файлы отвергает — это и есть fail-closed; файлы без новых битов
читаются как раньше. `python/cmf_reader.py` знает биты 0–8: файлы с битами
9–13 он отвергает, а Prism-биты 7–8 принимает (FWHT-базис и аффинную
поправку он сам не применяет — это справочный ридер тензоров, а не
исполнитель).

**Нумерация битов 12–13 (с 0.8.1).** `BOUNDED_STATE` и `GENOME` в
невыпущенных сборках ветки embryo-o1 занимали биты 7 и 8 — те самые, что в
выпущенных ридерах (0.6.9+) означают `PRISM_HADAMARD`/`PRISM_AFFINE`. Биты
выпущенного формата сохранили смысл; биты Embryo переехали на 12 и 13, биты
9–11 не менялись. Файл, записанный такой сборкой, ридер 0.8.1+ отвергает
как расхождение Prism-бита с метаданными (сообщение называет перенумерацию).
Такой файл переносится НА МЕСТЕ командой `cortiq migrate-embryo-bits
<file…>` (`--dry-run` — только показать): она решает по содержимому (бит 7
⇔ `arch.anchor_core`, бит 8 ⇔ `genome`; файл с `arch.prism_hadamard` не
трогает), берёт тот же `flock`, что дописывание, и меняет только байты
12..16 конверта. Их не покрывают ни `header_hash`/`dir_hash`, ни
`trunk_hash`, поэтому дописанные записи, сегменты и `lineage` сохраняются.
Переэкспорт из чекпойнта их ТЕРЯЕТ — для файлов с дописанными записями он
не годится (экспорт Embryo поверх геномного файла отказывает, в том числе
по старой нумерации). Отсоединённая подпись `<file>.sig` хеширует файл
целиком: после переноса её нужно выпустить заново (`cortiq sign`).
Бит 14 и выше не назначены — ридер отвергает их как неизвестные.

Неизвестные **поля** header-JSON игнорируются (аддитивная эволюция);
неизвестное **значение перечисления** (`layer_types[i]`, `linear_core.kind`,
`anchor_core.kind`, `dtype`) — отказ `Parse`, потому что это не новое поле,
а другой оператор, который старый ридер исполнить не может. Ломающие
изменения проходят только через биты фич, новые значения перечислений
(с отказом у старых ридеров) или инкремент `version`.

### 1.2 Правила валидации (нормативные)

Ридер ОБЯЗАН вернуть ошибку (не значение по умолчанию, не предупреждение),
когда:

- magic ≠ `CMF\x01` → `InvalidMagic`;
- `version` ≠ 2 → `UnsupportedVersion` (v1 мертва: реальных файлов v1
  не существует, программа поддержки не будет запущена);
- установлен неизвестный бит `required_features` → `UnsupportedFeature`;
- любая секция выходит за EOF, `data_off` не кратен 4096,
  `off + nbytes` тензора превышает `data_len` → `Bounds`;
- имя тензора не UTF-8, dtype неизвестен, `ndim > 6` → `Parse`;
- бит `GENOME`/`SKILLS_V2`/`ROUTER_V2` расходится с содержимым заголовка
  (в любую сторону), `genome.trunk_hash` не равен пересчитанному по
  каталогу, запись навыка v2 или политика роутера нарушают §9.4/§9.5 →
  `Parse`.

Проверка хэша тензоров — по требованию (`cortiq verify`, флаг загрузчика),
не при каждом open: страницы mmap читаются лениво.

## 2. JSON-заголовок

UTF-8 JSON, без выравнивания. Критичные для машины данные живут в бинарных
секциях; JSON несёт архитектуру и происхождение — те части, что читает
человек.

```jsonc
{
  "format": "cmf",
  "version": 2,
  "arch": {
    "arch_name": "qwen3.5",
    "hidden_size": 5120, "intermediate_size": 17408,
    "num_layers": 64, "num_attention_heads": 24, "num_kv_heads": 4,
    "head_dim": 256, "vocab_size": 248320,
    "layer_types": ["LinearAttention", "...", "FullAttention"],
    "rms_norm_eps": 1e-6,
    "norm_style": "qwen",            // "qwen": x̂·w | "gemma": x̂·(1+w)
    "rope_theta": 1000000.0,
    "tie_word_embeddings": false,
    "max_position_embeddings": 262144,
    "linear_conv_kernel_dim": 4,
    "linear_num_key_heads": 16, "linear_num_value_heads": 48
  },
  "quant_type": "Q4_BLOCK",          // informational default; truth = per-tensor dtype in the directory
  "provenance": { "tool": "…", "source_model": "…" }   // optional, free-form
}
```

`norm_style` обязателен для движка: gemma-стиль `(1+w)`, применённый к
весам Qwen, — это тихий мусор во всех ~130 нормализациях
прямого прохода.

Диспетчеризация возможностей **управляется наличием тензоров**: движок
решает по-слойно, какие операторы применять, по тому, что есть в каталоге
(q/k-смещения, qk-нормы, выходной гейт по ширине проекции, MoE-роутер,
GDN-проекции) — а не по совпадению имён моделей. Новые модели известного
семейства загружаются с нулевыми изменениями движка.

### 2.1 MTP — предсказание нескольких токенов (опционально)

Если модель несёт MTP-голову (в стиле DeepSeek/Qwen), arch объявляет:

```jsonc
"mtp": { "num_layers": 1, "share_lm_head": true, "share_embed": true }
```

Тензоры MTP — обычные записи каталога под каноническими именами
(`model.mtp.*`): `enorm.weight`, `hnorm.weight`,
`eh_proj.weight [hidden, 2·hidden]`, `layers.{i}.*` (стандартный
блок трансформера), `norm.weight`.

Семантика: `x = eh_proj·[enorm(embed(t_{p+1})); hnorm(h_p)]` — эмбеддинг
ПЕРВЫМ (проверено оракулом: обратный порядок даёт ровно 0% принятия)
→ блок → общий lm_head → черновик токена `t_{p+2}`. Ридер не
обязан исполнять MTP (метаданные + обычные тензоры, аддитивная
эволюция, без бита фичи); рантайм CMF использует голову для
спекулятивного декодинга со строгой гарантией: **выход в точности равен
обычному жадному декодингу** — отклонённый черновик откатывается из KV.

### 2.3 Операторы с ограниченным состоянием: `linear_core` и `anchor_core`

Два блока заголовка описывают исполняемые операторы, у которых состояние
последовательности не растёт с контекстом. Оба — **записи оператора, а не
подсказки**: ридер исполняет ровно то, что записано, переменные окружения
не могут их переопределить, а неизвестный `kind` — отказ.

`linear_core` (слои `LinearAttention`): `kind` ∈ {`gated_delta_net`,
`vmf_phase`, `vmf_phase_delta_v1`}, `num_heads`, `value_head_dim`, для
фазовых ядер `nphase`, для `vmf_phase_delta_v1` — обязательный список
`phase_delta_layers` (нулевой индекс, без дублей, только линейные слои).
Геометрия — поля `linear_num_key_heads`, `linear_num_value_heads`,
`linear_key_head_dim`, `linear_value_head_dim`, `linear_conv_kernel_dim`.
Состояние слоя: `S[heads·dk·dv]` + кольцо свёртки `(k−1)·c_dim`, f32.

`anchor_core` (слои `BoundedAttention`, бит 12 `BOUNDED_STATE` обязателен):

```jsonc
"layer_types": ["LinearAttention","LinearAttention","LinearAttention","BoundedAttention", "..."],
"anchor_core": {
  "kind": "swa_sink_v1",            // точное окно + обученные sink-векторы, один softmax
  "window": 128,                    // ёмкость кольца ключей/значений (сервинг)
  "sink": 4,                        // обученных sink-векторов на KV-голову
  "rope": "relative_in_window",     // кольцо хранит НЕповёрнутые ключи; q поворачивается на Δ∈[0,window)
  "sink_scores": "nope",            // sink-скоры без ротации: q̂·k̂ˢ
  "train_windows": [64, 128],       // окна обучения (стохастическое окно); информативно
  "far": null                       // резерв: {"m": 4..32, "rect": "aggregate|fm"} — пока не исполняется
}
```

Тензоры якоря: `self_attn.{q,k,v,o}_proj.weight` как у полного внимания
плюс `self_attn.sink_k.weight`, `self_attn.sink_v.weight`
`[num_kv_heads, sink, head_dim]` (f32, не квантуются). Состояние слоя —
`2·num_kv_heads·window·head_dim` f32 (кольцо K/V) + два счётчика; sink —
веса, не состояние. Валидация (`open`/`write`): запись обязательна при
любом `BoundedAttention` и запрещена без него; `kind` из белого списка;
`window ≥ 1`; `sink + window ≤ 160` (предел скретча GPU-ядер);
`rope`/`sink_scores` из белого списка; `train_windows ⊆ 1..=window`;
`far` принимается только `null`. Идентичность операторов
(`linear_core_identity`) включает `anchor_core` — скилл, испечённый на
базе с другим якорем, к файлу не привязывается.

Файл без `linear_core`/`anchor_core` (обычный трансформер) читается как
прежде; режим `--o1` (пост-хок Нюстрём, `provenance.o1_attn`) остаётся
подсказкой только для таких файлов.

### 2.2 MoE — FFN со смесью экспертов (опционально)

Если модель несёт MoE-слои (Qwen2-MoE / Qwen3-MoE / Qwen3.5-MoE),
arch объявляет:

```jsonc
"moe": {
  "num_experts": 256, "top_k": 8, "moe_intermediate_size": 512,
  "norm_topk_prob": true,                       // Qwen2-MoE: false
  "shared_expert_intermediate_size": 512        // absent if no shared expert
}
```

Тензоры — обычные записи каталога под HF-именами:

```
model.layers.{i}.mlp.gate.weight                    [num_experts, hidden]  router
model.layers.{i}.mlp.experts.{e}.{gate,up,down}_proj.weight
model.layers.{i}.mlp.shared_expert.{gate,up,down}_proj.weight
model.layers.{i}.mlp.shared_expert_gate.weight      [1, hidden]
```

Какие слои являются MoE — определяется ПРИСУТСТВИЕМ роутера в
каталоге (по-слойно, не по-модельно): `mlp_only_layers`/
`decoder_sparse_step` у Qwen2-MoE дают смешанные модели, и плотные
слои сохраняют обычные `mlp.*_proj`.

Семантика исполнения (паритет с HF, под воротами `tests/moe_parity.sh` по
четырём семействам, включая фьюженную раскладку AgentWorld): softmax по ВСЕМ
логитам роутера → top-k (ничьи: меньший индекс, порядок torch.topk) → если
`norm_topk_prob`, перенормировка выбранных k → Σwₑ·FFNₑ(x); общий
эксперт всегда добавляется с весом `sigmoid(shared_expert_gate·x)`.
Эксперты остаются квантованными в mmap; на токен затрагиваются только
страницы выбранных k — та же история резидентности, что и у скиллов.
Райтерам СЛЕДУЕТ раскладывать тензоры экспертов слоя ролево-смежно
(все `gate_proj` экспертов 0…N−1 подряд, затем все `up_proj`, затем все
`down_proj`) — GPU-бэкенды тогда работают с банком экспертов слоя как с
одним регионом вместо сборки сотен слайсов; нативный импортёр и
`moe-defrag` оба пишут такой порядок. Каждый
эксперт — отдельная запись каталога со СВОИМ dtype: это и есть носитель
по-экспертного распределения битов (P15 claim 12) — реализовано, под воротами
`tests/moe_vbit.sh`; B-поле (частоты выбора роутером через
`--route-stats`) измерено end-to-end на модели 35B.

## 3. Каталог тензоров

Байт-в-байт раскладка `.vmfc` v2 (единый канон, общий референсный
парсер):

```
[0 : 8 ]  count    : u64
[8 : 16]  pool_off : u64            (name-pool offset from section start)
[16 : 16 + count·56]  56-byte records:
   name_off : u32   (relative to pool_off)
   name_len : u16
   dtype    : u8    (§3.1)
   ndim     : u8    (≤ 6)
   shape    : u32 × 6  (zero-padded tail)
   off      : u64   (RELATIVE to data_off; multiple of 64)
   nbytes   : u64
   hash     : u64   (hash64 of the tensor bytes, §8)
[pool_off : …]  UTF-8 name pool
```

Имена тензоров **1:1 с исходной моделью**
(`model.layers.{i}.mlp.gate_proj.weight`, `model.embed_tokens.weight`,
`lm_head.weight`, …). Формат не предписывает набор тензоров:
каталог — единственный источник истины о том, что содержит блоб.
«Вычисляемой раскладки» не существует.

### 3.1 `dtype`

|----|-----------|------------------|

| 1  | `f16`     | ✅ чтение/запись (нормы и 1-D всегда f16) |
| 2  | `bf16`    | ✅ чтение/запись |

ни одно ядро их не декодирует, рантайм читает их как таблицы. Ридер до этих
id (`python/cmf_reader.py` показывает `?17`/`?18` и не декодирует; старый

встречаются только в файлах с битом `SKILLS_V2`, которые старый ридер и так
отвергает по биту (§1.1).

### 3.2 Раскладки квантования (канон = `.vmfc`: «сначала кванты, затем скейлы»)

- **`q8_row`** (только 2-D `[out, in]`):
  `[int8 : out·in][f16 : out]` — один скейл на строку,
  `w = q[o,i]·scale[o]`, `scale[o] = absmax(row_o)/127`.
- **`q4_block`**: группы по 32 над уплощённым тензором, с нулевым добиванием;
  `[u8 : ceil(n/32)·16][f16 : ceil(n/32)]`.
- **`q4tp`** (только 2-D, `in % 32 == 0`):
  `[ниббли: rows·gpr·16][параметры строки: rows × (f16 lo, f16 step)]
   [коды: rows × ceil(gpr·5/8), 5 бит LSB-first, выровнено по строке]`,
  `gpr = in/32`. Масштаб тайла — `2^(lo[r] + code·step[r])`, поэтому читатель
  раскрывает 32-ступенчатую лестницу строки один раз и дальше берёт масштабы
  из таблицы. Значения и порядок нибблов совпадают с `q4_tiled`, отличается
  только представление масштаба: 4.17 бит/вес против 4.50 — f16-масштаб
  занимал 11% q4t-файла. `lo`/`step` берутся из точных min/max логарифма
  масштаба по строке, поэтому код никогда не выходит за диапазон и
  escape-механизм не нужен. Кодировщик ОБЯЗАН округлить `lo`/`step` до f16
  **перед** выбором кодов и квантовать ниббли по восстановленному масштабу —
  иначе писатель и читатель разойдутся (та же ловушка, из-за которой q4-кодер
  сначала округляет свой масштаб).
  Ниблы: элемент `2k` младший, `2k+1` старший; `w = (q − 8)·scale`,
  `scale = absmax(group)/7`.
- **1-D тензоры и тензоры < 32 элементов всегда `f16`**
  (точность нормализации при максимальном сжатии матриц).
- **`q8_2f`**: `[int8][f16 row-scale][f16 col-scale]`,
  `w = q·scale[o]·col[i]` — независимые масштабы строки и входного канала,
  валидированные в vmfcore (+37% при равном размере; восстанавливают ~75%
  разрыва q8→f16 на выбросных входных каналах).
- **`vbit`** (только 2-D, `in % 32 == 0`; P13 FIG.3):
  `[u8 bits: rows][f16 scales: rows·in/32][bit-packed rows, MSB-first,
  each row padded to a byte]`; `w = (u − L)·scale[r,g]`,
  `L = 2^{b−1}−1`, уровни b ∈ {3,4,5,6,8}, пол 3 (claim 13).
  Распределение b_r: water-filling по логарифму амплитуды строки к
  средней битности тензора; для MoE-экспертов бюджет ОБЩИЙ на всё
  семейство (слой × проекция): сдвиг `ā_expert − ā_family`
  эквивалентен совместному water-filling по строкам всех экспертов — громкий
  эксперт получает больше бит, тихий прижимается к полу (P15
  claim 12; ворота `tests/moe_vbit.sh`). Опционально распределение берёт
  произведение с B-полем — частотами выбора роутером, собранными
  на калибровке (`b ∝ log2(A·B)`, усечённый Fisher).
- **`q1s`** (только 2-D, `in % 32 == 0`): база `q1` (те же 6-байтные
  тайлы; выбросы ИСКЛЮЧЕНЫ из группового скейла), затем разреженный
  оверлей: `[u32 count]` и `count × { [u32 плоский-индекс][f16 значение] }`
  — веса-выбросы, сохранённые в полной точности (оверлей в стиле SpQR)
  и восстанавливаемые дословно при деквантовании.
  Переменная длина: `expected_nbytes` не определён, ридер доверяет
  записанному в каталоге размеру. Позволяет ОБЫЧНОМУ чекпойнту пережить
  1 бит там, где чистый `q1` не может.
- **`q1t`** (только 2-D, `in % 32 == 0`, `in` должен помещаться в
  `u16`): тернарный BitNet-b1.58-стиль `{−s, 0, +s}`. База:
  `на 32-группу { [f16 scale][7B base-3 коды] }` — 9-байтные тайлы,
  5 тернарных значений на байт (3⁵ = 243 ≤ 256; код 0 → 0, 1 → +s,
  2 → −s), ~2.25 бит/вес. Затем построчный оверлей выбросов:
  `[u32 row_ptr[rows+1]]` и записи `{ [u16 col][f16 значение] }`,
  сгруппированные по строкам (выбросы строки `r` — диапазон
  `[row_ptr[r], row_ptr[r+1])`; `col` — индекс внутри строки) — 4
  байта на выброс, без бинарного поиска. Точное сохранение множества
  почти нулевых весов — решающий PTQ-выигрыш над бинарным. Переменная
  длина, правило размера как у `q1s`.

## 4. Блоб весов

`data_off` кратен 4096 (выровненный по странице mmap); каждый тензор
внутри начинается на границе 64 байт (SIMD-загрузки, кэш-линии). Нулевое
добивание между тензорами. Ридер интерпретирует блоб только через
каталог.

## 5. Секция масок

Маска задачи = битовые поля «что активно» над общими весами. Маска выбирает
строки и головы для задачи; общие веса при этом не меняются.

```
[0 : 4]  n_masks  : u32
[4 : 8]  meta_len : u32
[8 : 8 + meta_len]  JSON meta (§5.1)
[…]      mask blobs, each aligned to 8 from the section start
```

Один блоб маски (размеры выводятся из arch, без внутренних заголовков):

```
[n_layers × ffn_bytes]   FFN bitfields      ffn_bytes  = ceil(intermediate_size / 8)
[n_layers × head_bytes]  head bitfields     head_bytes = ceil(num_attention_heads / 8)
[gates_bytes]            layer_gates        gates_bytes = ceil(num_layers / 8)
[n_layers × expert_bytes] expert bitfields  ОПЦИОНАЛЬНО — только когда мета маски
                                            ставит "has_expert_fields": true;
                                            expert_bytes = ceil(moe.num_experts / 8)
```

Порядок битов LSB-first: нейрон `i` = бит `i % 8` байта `i / 8`; бит
установлен → активен. **Хвостовые биты за пределами размерности ОБЯЗАНЫ
быть нулём** (иначе popcount видит фантомные нейроны/головы).

Опциональная экспертная область (аддитивно: старые ридеры не читают
дальше gates, а `blob_len` каждой маски явный) позволяет задачной маске
сужать РОУТИНГ MoE: бит `e` строки слоя `l` установлен → эксперт `e`
маршрутизируем для этой задачи; выбор идёт только по маршрутизируемым,
softmax роутера ренормализуется по ним. Это переключаемый в рантайме
близнец физического дефрага экспертов из §11.1 — один файл с полным
набором экспертов обслуживает много специалистов (`cortiq moe-mask`
пишет такие маски, `run --task <имя>` активирует; проверено
токен-в-токен с эквивалентным рантайм-ограничением). Слой со строкой
все-единицы — без ограничения; маска без области ничего не сужает.

### 5.1 JSON-мета маски

```jsonc
{
  "default_task": "general",
  "masks": [{
    "task_id": 0, "name": "general", "description": null,
    "sparsity": 0.62,
    "quality": {                    // null = NOT MEASURED (declaring 1.0 is forbidden)
      "metric": "heldout_ppl_ratio", "value": 0.97,
      "baseline_dense": 6.10, "n_samples": 512, "dataset_sha256": "…"
    },
    "parent": null, "priority": "Fallback", "has_hot_pack": false,
    "blob_off": 4096, "blob_len": 139328   // relative to section start
  }]
}
```

`quality` — это **контракт на held-out**, а не декларация: конвертер
без измеренной метрики пишет `null`; рантайм логирует предупреждение при
переключении на неизмеренную маску.

## 6. Секция токенизатора

Байты HuggingFace `tokenizer.json`, дословно. Модель
самодостаточна: один файл = одна единица распространения. Sidecar-файл
остаётся отладочным запасным вариантом.

### 6.1 Chat-бандл (`header.tokenizer_config`)

Файл — а не рантайм-бинарник — определяет поведение чата. Заголовок
несёт опциональный блок (аддитивная эволюция, без бита фичи):

```json
"tokenizer_config": {
  "chat_template": "<Jinja template from chat_template.jinja or tokenizer_config.json>",
  "eos_token_ids": [248044, 248045],
  "bos_token_id": null,
  "pad_token_id": 248055
}
```

Рантайм рендерит шаблон с семантикой HF (trim_blocks,
lstrip_blocks, управление циклами, строковые методы Python) и
останавливает генерацию на любом id из `eos_token_ids`. Ворота:
`tests/chat_template_parity.sh` — рендер рантайма равен референсному
jinja2 байт-в-байт. Файлы без блока получают ChatML-fallback.

## 7. Разреженный индекс

Предвычисленный мост «маска → пропуск вычислений»: активные квант-группы
FFN (по 32 нейрона каждая) и головы, на пару (задача, слой).

> Честный статус: движок берёт активные индексы напрямую из битовых
> полей маски; индекс читается и отображается CLI, но в исполнении не
> использовался никогда. **Кандидат на деприкацию**: райтерам СЛЕДУЕТ
> перестать его писать (ридеры продолжают понимать существующие файлы);
> он оживёт, только если путь «маски × квантованный mmap»
> материализуется с измеренным выигрышем.

```
[0 : 4]  n_entries : u32
[4 : 8]  reserved  : u32 (0)
entry (4-aligned):
   task_id   : u32
   layer_idx : u32
   n_groups  : u32
   n_heads   : u32
   [u16 × n_groups]  active FFN-group indices (sorted)
   [u8  × n_heads]   active head indices (sorted)
   zero padding to a multiple of 4
```

Группа активна, если содержит хотя бы один активный бит маски.

## 8. `hash64`

Некриптографический 64-битный хэш байтов тензора: murmur3 `fmix64` над
64-битными LE-словами с позиционной солью `i·0x9E3779B97F4A7C15`, XOR-свёртка,
`xor len`, финальный `fmix64`. Бит-в-бит совместим с
`vmfcore.hash64` (Python) и `vmfcore::hash64` (Rust) — хэши
общих тензоров совпадают между `.cmf` и `.vmfc` (дедупликация базовой модели между
файлами скиллов бесплатна).

Использование: `cortiq verify` (детекция повреждений), дедупликация, ключи кэша.

### 8.1 Хэши секций

Целостность метаданных (не только тензоров):

- Резерв конверта `[0x70:0x78]` = hash64(JSON-заголовок), `[0x78:0x80]` =
  hash64(каталог). Ноль = «отсутствует» (старые файлы проходят).
- JSON-заголовок несёт `section_hashes` — hex hash64
  масок/словаря/индекса (u64 как JSON-число потерял бы точность за
  2^53). Хэш заголовка в конверте транзитивно покрывает их.
- Сам конверт (первые 0x70 байт) не хэшируется: хэш не может
  защитить сам себя; повреждённые смещения ловятся границами/хэшами дальше
  по цепочке.
- `cortiq verify` проверяет всю цепочку; единственный перевёрнутый байт
  заголовка — это ошибка.

### 8.2 Отсоединённая подпись (аутентичность, опционально)

Хэш-цепочка доказывает целостность, но не авторство. `cortiq sign`
пишет отсоединённый `<model>.sig` — JSON `{alg: "ed25519-sha256",
pubkey, sha256, sig}`, Ed25519 поверх SHA-256 файла — сам контейнер не
переписывается, старый инструментарий не затронут. `cortiq verify`
проверяет подпись автоматически, когда `.sig` лежит рядом с моделью;
отсутствие — не ошибка. Ключ — файл с 32-байтовым hex-сидом, который
подписант хранит приватно.

## Анти-фичи — чего формат намеренно НЕ имеет

- **Вычисляемой раскладки весов** — баг-класс #1 в v1 (райтер и ридер
  «вычисляли» раскладку независимо и расходились).
- **Тихих fallback'ов** — v1 интерпретировала любой мусорный файл как «модель
  27B»; v2 обязана падать.
- **JSON для битовых данных** — маски v1 в JSON раздувались в 3–4×.
- **Неподтверждённых деклараций** — оценки качества и заявления о ёмкости
  по умолчанию не записываются. Поле появляется только вместе с метрикой и
  зафиксированным измерением.

## 9. Скиллы — рой в одном файле (Patent 15, claims 2/12/15)

Одна общая базовая модель + K записей на скилл; ни одна запись не хранит полную
модель. Хранилище масштабируется как |backbone| + Σ|deltas|.

**Замещающие тензоры** — обычные записи каталога с именами
`skill.{skill_id}.{name_of_replaced_tensor}`, напр.
`skill.sql.model.layers.3.mlp.gate_proj.weight`. Полная логическая форма
замещаемого тензора (full-shape — НЕ low-rank, НЕ список diff, НЕ
маска), в любой кодировке §3. Помасочный delta-индекс (claim 2)
материализуется каталогом: префиксный фильтр даёт скилл →
байт-смещения; ленивая пейджинг = mmap-доступ ровно к тем смещениям
(claim 12).

**Реестр** — JSON-заголовок, аддитивный:

```json
"skills": [{
  "id": "sql",
  "name": "SQL assistant",
  "layers": [3, 4, 5],
  "selection": {"metric": "mse", "phi_layer": 20,
                 "mean": "<f16 base64>", "basis": "<f16 base64>"},
  "input_mask_task": null,
  "quality": {"metric": "ppl", "backbone": 21.4, "overlaid": 17.9,
               "dataset_sha256": "…"}
}]
```

`selection` держит параметры аффинного подпространства для маршрутизации
recon-argmin (`E = ‖r − BBᵀr‖²/‖φ‖²`, выбирается скилл с минимальным E);
файл самодостаточен для отбора. `quality` — честный контракт claim-16
(overlaid против backbone на held-out данных).

**Семантика исполнения (claims 1/3/18)**: индирекция источника тензора — для
каждого тензора рантайм читает ЛИБО запись базовой модели, ЛИБО
`skill.{active}.{name}`, если она есть; замещение вместо сложения,
полная модель на скилл никогда не собирается (все тензоры — указатели в
один mmap). Мягкая суперпозиция (claim 14): смешанные рабочие тензоры
`Σwᵢ·Tᵢ`, `wᵢ = softmax(−E/T)`.

**Только-добавочный рост (claim 11)**: добавление скилла = дописывание новых
тензоров в хвост файла + переиздание заголовка и каталога в хвост +
обновление конверта на месте, последним (механизм и порядок записи — §9.3).
Байты и смещения ранее записанных тензоров никогда не меняются; маски,
словарь и индекс остаются на месте; старые байты заголовка и каталога
становятся мёртвыми (совместимо: ридеры навигируют только через конверт).
Компактификация (`cortiq compact`) = обычная перезапись.

### 9.1 Самостоятельные скилл-файлы (`SKILL_FILE`, бит 6)

Скилл может путешествовать БЕЗ своей базы: `.cmf`, чей набор тензоров —
только то, что изменил бейк (плюс каталог масок), привязанный к базе
ключами идентичности в записи реестра:

```json
"skills": [{
  "id": "gfx-html",
  "layers": [0, 1, "...", 21],
  "base_dir_hash": "9f22593eb458bc6f",
  "base_arch": "nanbeige",
  "task": "specialist",
  "provenance": {"corpus": "…", "tensors": 30}
}]
```

- `base_dir_hash` — hex `hash64` байтов каталога тензоров БАЗЫ (то же
  значение конверт несёт по адресу `[0x78]`). Скилл — дельта против
  точных байтов, а не против архитектуры: `apply` ОБЯЗАН отвергнуть
  базу с другим хешем каталога (явный `--force` может переопределить;
  результат вне спецификации).
- `base_arch`, `task`, `provenance` — информационные ключи: человеческая
  проверка, задача каталога масок, происхождение.

Любая запись с `base_dir_hash` поднимает бит 6: читатель до этого бита
откажет громко, а рантайм, знающий бит, откажется ЗАПУСКАТЬ файл
(частичный набор тензоров — не модель) и укажет на
`cortiq skill apply <база> <скилл> -o out.cmf`, который проверит ключ,
наложит тензоры и маски поверх базы и запишет полный файл —
байт-эквивалент специалиста, из которого скилл был вырезан.

Жизненный цикл: `skill bake` (специалист) → `skill export --base`
(дельта + ключи) → публикация маленького файла → `skill apply` на любой
копии базы.

### 9.2 Замороженный геном и журнал (`GENOME`, бит 13)

Новое знание входит в модель только записью навыка поверх ЗАМОРОЖЕННОГО
ствола. Формат делает это проверяемым свойством файла, а не соглашением.

```jsonc
"genome": {
  "id": "embryo-o1-fam-a",           // семейство; градиентное обучение запечатанного
                                     // ствола = НОВЫЙ id (новое рождение), не generation+1
  "generation": 0,                   // 0 при рождении
  "status": "pre_chat",              // pre_chat | sealed | candidate | rejected
  "trunk_hash": "641809d659e73333",  // hash64 ствола в кодировке ЭТОГО файла
  "encoding": "f32",                 // f32 | f16 | q4tp | … (информационно)
  "master_trunk_hash": "641809d659e73333", // trunk_hash f32-мастера (= trunk_hash при f32);
                                     // к нему привязаны навыки, реквант их не сиротит
  "parent": null,                    // {id, generation, master_trunk_hash}
  "reference": {"val_ppl": {"value": 60.85, "dataset_sha256": "…"}},  // измеренная батарея
  "moe_experts": 4                   // E0: экспертов ствола на MoE-слой у резонансного MoE
                                     // (писатель берёт из arch.moe.num_experts; §9.5.1)
},
"lineage": [
  {"seq": 0, "event": "birth", "ts": "2026-09-24T12:00:00Z", "detail": {}},
  {"seq": 1, "event": "skill_committed", "ts": "…",
   "detail": {"skill": "herbs", "tensors": 4, "data": [1900544, 2203648]}}
]
```

**Ствол** — все записи каталога вне пространств имён `skill.` и `route.`.
`trunk_hash` = hash64 от конкатенации:

1. `b"cmf-trunk-v1\0"`;
2. каждая запись ствола в порядке байтовой сортировки имён:
   `name 0x00 dtype(u8) 0x00 ndim(u8) shape(u64 LE × ndim) 0x00 hash(u64 LE)`;
3. `0x1e` + канонический JSON объекта `arch` (ключи объектов отсортированы
   на всех уровнях, без пробелов — не зависит ни от порядка полей, ни от
   фичи `preserve_order` у serde_json);
4. `0x1e` + hash64 секции словаря (u64 LE; 0, если секции нет);
5. `0x1e` + канонический JSON `tokenizer_config` (`null`, если нет);
6. только если в файле есть секция масок или разреженного индекса:
   `0x1e b"exec\0"` и по каждой из двух секций (маски, индекс) байт-тег
   (1 — есть, 0 — нет) плюс hash64 её сырых байтов (u64 LE). Маски — часть
   исполнения ствола: `run`/`serve` применяют fallback-маску каталога к
   каждому запросу, к стволу тоже. У генома без масок хэш прежний (п. 6
   пуст), а каталог масок, добавленный позже, меняет `trunk_hash` — такой
   файл ридер отвергает, писатель отказывается его писать.

JSON-части берутся В ТОМ ВИДЕ, КАК ЗАПИСАНЫ: `open()` канонизирует сырой
JSON заголовка файла (`trunk_hash_json`), писатель — ровно те байты,
которые пишет. Поэтому поле `arch`, добавленное более новым писателем
(аддитивная эволюция), покрыто хэшем, а не отброшено структурой старого
ридера; f32-поля хэшируются в записанной форме.

Хэш уровня каталога: байты весов входят через `entry.hash`. Поэтому
`open()` пересчитывает его дёшево и отвергает файл при расхождении
(`trunk_hash mismatch: the genome's bytes changed without a new genome`),
а подмену payload при неизменном каталоге ловит `cortiq verify`
(пересчёт хэшей тензоров). Не входят в ствол: навыки, `router`,
`routing`, `lineage`, `segments`, `provenance`, сам блок `genome`.

Геном обязан встраивать токенизатор (секция VOCAB): без неё хэш покрывал бы
«словаря нет», а загрузчик взял бы `tokenizer.json`, лежащий рядом с
файлом. Писатель и `open()` отказывают, загрузчик на геноме sidecar не
берёт. Ключ `provenance.o1_attn` на геноме запрещён (писатель, `open()`,
загрузчик): оператор внимания ствола задаёт `arch`, который входит в хэш, а
подсказка в `provenance` переключила бы ствол на Нюстрём без нового
генома.

Писатель (`write`, `write_ref`, потоковый `finish`, дописывание):

- пустой `trunk_hash` заполняет из содержимого (рождение); при
  `encoding == "f32"` пустой `master_trunk_hash` становится равным
  `trunk_hash`;
- непустой `trunk_hash`, не совпадающий с содержимым, — ОТКАЗ записи:
  ствол изменился без нового генома. Переписать файл с тем же стволом можно
  (калибровка, компактификация), подменить ствол под старым геномом нельзя;
- геном в шардированном файле запрещён (хэш покрывает один каталог);
- перекодирование на месте (`CmfModel::recode_entries_in_place`: `cortiq
  patch-tensor`, `requant` на месте) на файле с `GENOME` отказывает. Реквант
  обязан писать новый файл, где переписаны `trunk_hash`/`encoding` и
  добавлено событие `requant`; этот путь пока не реализован;
- команды CLI, переписывающие файл целиком (`skill add|bake|apply|export`,
  `requant`, `compact`, `moe-mask`, `moe-defrag`, `tube-bake`,
  `ffn-transpose`, `quantize gptq`, `awnp`, `patch-tensor`), на входе с
  `header.genome` отказывают: полная перезапись раскладывает префикс заново
  (байтовое тождество G1 с F0 теряется) и может подложить то, с чем
  исполняется ствол (`skill add --sparse` — каталог масок). Навык входит в
  геном только дописыванием в хвост (§9.3).

Ридер дополнительно требует: `status` из перечня; `encoding == "f32"` ⇒
`master_trunk_hash == trunk_hash`; `lineage[].seq` строго возрастает;
`moe_experts`, если задано, равно `arch.moe.num_experts` (при `arch` без
блока MoE — отказ). Писатель заполняет пустое `moe_experts` при
`arch.moe.router_resonance` (аддитивно: у старых файлов поле отсутствует,
`genome_moe_experts(header)` берёт тогда значение из `arch`).
События журнала: `birth | skill_committed | skill_retired | requant |
recalibrate | compact | rollback`. Журнал информационный: неизвестное имя
события не приводит к отказу.

hash64 не криптографический: `trunk_hash` защищает от случайной и
небрежной подмены, но не от злонамеренной. Для импорта навыков из роя нужна
привязка через SHA-256 и подпись; это не реализовано.

API: `cortiq_core::trunk_hash(header, tensors, vocab)` (файл без масок),
`trunk_hash_exec(header, tensors, vocab, ExecHashes)`,
`CmfModel::trunk_hash()`, `CmfModel::exec_hashes()`,
`GenomeInfo::birth(id, status, encoding)`, `genome_moe_experts(header)`,
`LineageEvent::now(seq, event, detail)`.

### 9.3 Настоящее дописывание в хвост

`CmfModel::append_skill(path, record, tensors, router, routing, lineage_event)`:

```text
[0, 128)          конверт — переписывается НА МЕСТЕ и последним
[128, len(F0))    не трогается: старые заголовок и каталог, блоб ствола,
                  маски, словарь, индекс
[len(F0), …)      payload новых тензоров (64-выравнивание относительно
                  data_off, тензоры ≥ 16 КиБ — по странице), затем новый
                  JSON-заголовок и новый каталог (старые записи байт-в-байт,
                  новые — в конце)
```

- `data_off` не меняется, `data_len` расширяется до конца новых payload.
  Маски, словарь и индекс остаются на своих смещениях и теперь лежат внутри
  `[data_off, data_off + data_len)`. Это законно: секции адресуются только
  через конверт, границы проверяются против длины файла и `data_len`, а
  проверки непересечения секций нет ни в Rust-ридере (`parse_envelope`), ни
  в `python/cmf_reader.py`. Старые байты заголовка и каталога становятся
  мёртвыми.
- Порядок записи: payload → заголовок → каталог → `fsync` → 128 байт
  конверта (`required_features`, `header_off/len`, `dir_off/len`,
  `data_len`, хэши заголовка и каталога по `0x70`) → `fsync`. До записи
  конверта файл остаётся F0 (хвост никем не адресован), поэтому сбой в
  любой момент оставляет либо F0, либо F1. После записи конверта файл
  переоткрывается с полной проверкой; если это не удалось, старый конверт
  восстанавливается.
- Двухфазный API: `CmfModel::prepare_append_skill(…)` (хвост записан и
  синхронизирован, конверт нет) → `PendingAppend::commit()`. Брошенный
  `PendingAppend` — это ровно «процесс убит до конверта». Следующее
  дописывание начинается после брошенного хвоста.
- Отказ до записи первого байта: навык с таким `id` уже есть (перевыпечка —
  новый id или явное списание); тензоры вне `skill.{id}.`; запись с
  `base_dir_hash` (это самостоятельный скилл-файл, §9.1); шардированный файл
  или `SKILL_FILE`; всё, что `open()` отверг бы у результата (содержимое
  проверяется в памяти заранее). Одновременно пишет один процесс
  (advisory `flock`).
- `router`/`routing`: `Some` заменяет значение в заголовке, `None`
  оставляет прежнее. Устаревший роутер безопасен: по `skills_hash`
  исполняется ствол (§9.4). Для `ffn_replace` без `state_effect` писатель
  вычисляет его сам. В журнал добавляется `skill_committed` (событие
  вызывающего, если передано; `seq` назначается здесь).
- `header.segments` — таблица владения диапазонами данных (смещения
  относительно `data_off`): при первом дописывании
  `{kind: "genome"|"base", id, data_start: 0, data_end: data_len(F0)}`,
  затем по одной записи `{kind: "skill", id, data_start, data_end}` на
  дописывание. Полная перезапись (`write`, `cortiq compact`) — это
  компактификация, и таблица очищается.
- Только заголовок: `CmfModel::update_header_append(path, |h| …)`
  (перекалибровка, статус и гейт навыка, события журнала). Новый JSON идёт в
  конец файла, каталог и payload остаются на месте, конверт пишется
  последним. `section_hashes` и `segments` берутся из текущего файла, что бы
  ни сделало замыкание. Изменение ствола через заголовок (например, `arch`)
  отвергается геномом.
- Отсоединённая подпись `.sig` (§8.2) покрывает весь файл, поэтому после
  дописывания она недействительна, файл нужно переподписать. Подписи генома
  и сегментов не реализованы.

Гейт (юнит-тесты `crates/cortiq-core/tests/knowledge_v2.rs`): байты
`[128, len(F0))` у F1 совпадают с F0; все старые записи каталога равны
(смещение, хэш, форма, dtype); новая запись читается, её тензоры
разрешаются; второе дописывание работает; «убит до конверта» — F0
открывается тождественно (тот же заголовок, каталог и биты, `verify`
чист). Проверено и на файле с настоящей архитектурой Embryo
(`cortiq_embryo`, bounded + GDN): префикс совпал, а бинарник `cortiq`,
собранный до изменения, отказал F0 (`unsupported features 0x100`) и F1
(`0x300`) — числа в нумерации до 0.8.1 (§1.1); сейчас это `0x2000` и `0x2200`.

### 9.4 Маршрутизация v2 (`ROUTER_V2`, бит 10)

```jsonc
"router": {
  "version": 2,
  "policy": "backbone_gated",       // единственное значение
  "granularity": "request",         // единственное значение сегодня
  "phi": {"layer": 5, "pool": "span_mean", "norm": "unit",
          "prefix_ids": [/* токены "<|im_start|>user\n" */],
          "suffix_ids": [/* токены "<|im_end|>\n<|im_start|>assistant\n" */]},
  "base": {/* SelectionDescriptor класса СТВОЛА: metric "mse_unit",
              phi_layer = phi.layer, holdout = общие промпты */},
  "margin": 0.05,                   // навык должен обогнать ствол на столько в unit-ошибке E
  "skills_hash": "…",
  "measured": {"in_scope_recall": …, "false_accept": …, "false_accept_upper95": …,
               "n_in": …, "n_general": …, "general_sha256": "…", "in_sha256": "…"}
},
"routing": {"temperature": …, "novelty_theta": …, "samples": …, "target_fpr": …}
```

**Канонический φ(q)** пользовательского сообщения q. Тренер и рантайм
считают его одинаково:

1. `ids = prefix_ids ++ encode(q) ++ suffix_ids`, где `encode(q)` — ровно
   `Tokenizer::encode_plain(q)`: без BOS и без поиска added-токенов внутри
   q (литерал `<|im_end|>` в тексте пользователя остаётся байтами). Это
   `Bpe::encode` тренера, на котором построены дескрипторы и калибровка;
   обычный `Tokenizer::encode` выделил бы спецтокены, и φ ушёл бы из
   распределения калибровки;
2. ствол прогоняется до слоя `phi.layer` включительно, берётся скрытое
   состояние ПОСЛЕ этого слоя (выход остаточного потока, как у
   `probe_phi`);
3. `span_mean`: среднее только по позициям `encode(q)`, токены шаблона не
   входят;
4. `unit`: нормировка к единичной длине.

Хелперы: `router::phi_span_ids(phi, q_ids) -> (ids, span)`,
`router::pool_span_unit(hiddens, hidden, span)`.

Инварианты (проверяет `open()`): `version == 2`, `policy ==
"backbone_gated"`, `granularity == "request"`, `pool/norm ==
span_mean/unit`, `phi.layer < num_layers`; `base.metric == "mse_unit"`,
`base.phi_layer == phi.layer`; у каждой v2-записи с `selection`
`metric == "mse_unit"`, `phi_layer == phi.layer` и `phi.layer <
min(layers)` (φ не зависит от активного навыка); `margin` конечен и ≥ 0;
`skills_hash` — hex hash64; ни один навык не называется `@backbone` (id
класса ствола).

**`skills_hash`** (`router::skills_hash`) = hash64 от
`b"cmf-skills-v2\0"`, дескриптора ствола и дескрипторов всех калибруемых
классов (v2-записи с `selection`, кроме `retired`) в порядке id. По каждому
дескриптору: `id, metric, phi_layer, rank, mean, basis, err_mean, err_std`.
Holdout-выборки в хэш не входят. Смена статуса quarantine → active
калибровку не инвалидирует. Новый навык, изменённый дескриптор или списание
навыка её инвалидируют.

**Решение `backbone_gated`** (`router::decide_backbone_gated_with`, одно
на run/explain/serve/пробы). Строки — ошибки восстановления φ против ствола
и КАЖДОГО калибруемого класса (`calibration_classes`: v2 с `selection`,
кроме `retired` — тот же набор, по которому `calibrate_v2` подбирает T и θ
и который связывает `skills_hash`). Argmin и softmax идут по этому полному
набору. Выиграть может только МАРШРУТИЗИРУЕМЫЙ класс (`router::is_routable`:
v2, `status == "active"`, `gate.status == "measured"`; с отладочным
`--include-quarantine` — любой неотозванный класс, включая `quarantine`,
`stale_regate` и `active` без измеренного гейта). Если ближайший класс не
маршрутизируем, исполняется ствол («nearest class X is not routable»): его
in-scope-вопрос не уходит к следующему по близости активному навыку, а
softmax по урезанному набору не занижает новизну. Навык побеждает, только
если одновременно: политика объявлена; `skills_hash` совпадает с
пересчитанным по файлу; калибровка и строка ствола есть; φ не вырожден;
хотя бы один класс маршрутизируем; калиброванный победитель — навык и он
маршрутизируем; вход не новый (`novelty ≤ θ`); `E_skill + margin <
E_base`. Во всех остальных случаях исполняется СТВОЛ. v2-записи никогда не
маршрутизируются старым argmin (`error_rows` их пропускает). Файлы без
`ROUTER_V2` маршрутизируются как раньше, с одним исправлением: если вход
новый (`is_novel`), исполняется ствол, а не argmin-победитель.

В рантайме решение принимает `router::route_request(model, backbone,
user_text)`: φ считает `Pipeline::probe_phi_span` на пайплайне ствола без
оверлея, по span текста пользователя. Этот пайплайн только считает φ и
ничего не генерирует, потому что проба сбрасывает состояние
последовательности. Решение используют `run`, `explain`, `serve`,
`probe-utility`, `route-eval` и `dump-logits`. `serve` решает по
последнему сообщению `user`. Ствол исполняется на обычных слотах, у каждого
выбранного навыка своя полоса пайплайнов, загруженных вместе с навыком.
Полоса создаётся при первом запросе. `set_active_skill` не вызывается, и
`kv_prefix` каждой полосы переиспользуется отдельно. Решение попадает в
ответ (`x_cortiq_route`) и в лог. Потоковый `DynRouter` на файле с
`ROUTER_V2` не запускается, действует решение на запрос; на файле с
`SKILLS_V2` без роутера он тоже не запускается, а v2-записи в него не
попадают (их статус и гейт проверяет только решение на запрос).

**Контракт промпта** (`router::enforce_prompt_contract`, одна проверка для
run/explain/serve/инструментов). Навык с `prompt_contract == "cmf-im-v1"`
обучен и прогейчен только в рамке `<|im_start|>role\n…<|im_end|>\n`, ответ
после `<|im_start|>assistant\n`. Если кадр генерации рамку соблюдает
(шаблон с этими маркерами, ChatML-fallback при наличии обоих спецтокенов,
`dump-logits`/`probe-utility` с `chat_prefix`), навык исполняется как есть.
`run`/`explain` на сыром промпте (файл без шаблона) исполняют навык на
отрендеренном ходе `render_cmf_im_v1(q)`; ствол остаётся на сыром промпте
(тождество G2 с F0). Если соблюсти контракт нельзя (другой шаблон,
неизвестный контракт, сырой префикс `--state`), исполняется ствол с
причиной «prompt contract … not satisfied». `/v1/completions`
маршрутизирует только промпт, который в точности равен одному ходу
пользователя cmf-im-v1 (`cmf_im_v1_single_user_turn`): φ считается по q,
генерация идёт по тому же промпту. Сырой текст или отрендеренная клиентом
стенограмма исполняются стволом с причиной «completions: no user turn»,
без φ по всей истории.

**Резидентный граф и полосы.** Вердикт «граф не собирается» хранится в
каждом пайплайне (`Pipeline::graph_refused`), а не глобально: отказ графа
полосы навыка не переводит слот ствола посреди последовательности на хост,
а создание полосы не сбрасывает чужой вердикт. После позиции 0 устройство
продолжает только последовательность, образ которой держит
(`embryo_device_next_position`). Ключ переиспользования (`KvPrefix`,
`kv_history`) помечен владельцем (устройство или хост), и ход, который
продолжил бы его на другом пути, начинается с нуля. Отказ устройства
посреди его собственной последовательности — ошибка только этого запроса,
состояние и ключ слота при этом очищаются.

**Гейты в инструментах.** `route-eval` заранее определяет набор кандидатов
(политика, калибровка, совпавший `skills_hash`, хотя бы один класс,
маршрутизируемый при данных опциях). Если набор пуст или ожидаемый навык в
него не входит, измерение пустое: `gate.pass = false`, `gate.vacuous =
true` с причиной, код выхода ненулевой. Гейт ствола требует n ≥ 500.
Набор, sha256 которого совпадает с `router.measured.general_sha256` или
`in_sha256`, отвергается как калибровочный. `dump-logits` пишет во
временный файл и переименовывает его только после всех промптов; файл с
каталогом масок отвергает (run/serve применили бы маску, а дамп меряет
прямой проход без неё). `logits-compare`: `g2_pass` требует одинакового
числа записей, отсутствия индексов только в одном дампе, дублей и
расхождений формы, а запись B с маршрутом 0 сравнивает только с записью A,
у которой тоже маршрут 0.

**Калибровка v2** (`router::calibrate_v2`). Выборки — holdout каждого
калибруемого навыка (метка — навык) и holdout ствола `router.base` (метка —
ствол). Температура минимизирует NLL истинного класса по ВСЕМ классам,
включая ствол. θ — квантиль (1 − target_fpr) новизны на in-scope holdout
навыков. `measured` содержит recall и false-accept под полным решением на
этих же выборках и верхнюю границу Клоппера–Пирсона (двусторонний 95 %,
`router::clopper_pearson_upper`). Это числа калибровочного набора. Гейт
меряет false-accept на НЕПЕРЕСЕКАЮЩЕМСЯ общем наборе со своим sha256.
Результат публикуется так: `routing = cal`, `router.skills_hash =
hex(skills_hash(header))`, через `update_header_append`.

### 9.5 Записи навыков v2 (`SKILLS_V2`, бит 9)

Запись v2 — это `SkillRecord` с полем `kind`. Записи без `kind` (v1)
работают как раньше.

```jsonc
{
  "id": "herbs",                    // без точек: это префикс тензоров skill.{id}.X
  "layers": [7],
  "kind": "ffn_replace",
  "overrides": [{"name": "model.layers.7.mlp.shared_expert.up_proj.weight",
                 "base_hash": "…"}],  // хэш записи ствола, против которой учили
  "bound": {"genome_id": "embryo-o1-fam-a", "generation": 0,
            "master_trunk_hash": "…"},
  "state_effect": {"first_affected_layer": 7, "switch": "transparent",
                   "state_bytes_added": 0},
  "status": "quarantine",           // quarantine | active | stale_regate | retired
  "gate": {"status": "measured", "false_accept_upper95": 0.012, "…": "…"},
  "prompt_contract": "cmf-im-v1",   // шаблон, под которым учили навык (фиксация, не защита)
  "origin": {"trigger": "user_corpus", "dataset_sha256": ["…"], "recipe": "…"},
  "selection": {/* mse_unit, phi_layer = router.phi.layer */}
}
```

Виды записей:

| `kind` | в этом ридере | что это | позиционирование |
|---|---|---|---|
| `ffn_replace` | реализован | полноформатная замена FFN-тензоров слоёв `layers` (`skill.{id}.model.layers.N.mlp.*`) | запись P15 (per-skill record, индирекция источника тензора) |
| `expert_append` | реализован (§9.5.1) | новые эксперты поверх E0 экспертов ствола в слоях `layers`, выбираются встроенным резонансным роутером слоя на каждый токен | новые рёбра E_t DTG-MA и рост P3. НЕ запись P15: P15 [0019](vii) исключает экспертные тензоры MoE с потокенным гейтом; на запрос не переключается |
| `lookup` | реализован (§9.5.2) | явная справочная память: таблица ключ → карточка под `skill.{id}.lookup.*`, выбирается роутером `backbone_gated` на запрос и отвечает из таблицы | запись P15 (per-skill record) без единого тензора сети: точные факты по построению, ноль забывания по построению, O(1) на запрос |
| `anchor_sinks` | зарезервирован, отказ | синки якоря для задачи | число синков входит в `anchor_core_identity`, `switch` = `sequence_start` |
| `mask_only` | зарезервирован, отказ | только маска поверх ствола | по P15 [0019](iii) не запись P15 |
| `fcd_vector` | зарезервирован, отказ | Tucker-вектор задачи v_t | FCD-JMLR, P1 кл.7 |

Проверки при открытии (отказ `Parse` с точным сообщением):

- `kind` известен и реализован; для зарезервированного вида отдельное
  сообщение;
- id не пуст, без точек и не из `backbone`, `none`, `auto`: этими словами
  CLI и отчёты маршрута называют ствол и автоматическое решение (`--skill
  none`, `--route backbone|auto`, `target: "backbone"`);
- `bound` есть, в файле есть геном, `bound.genome_id == genome.id`,
  `bound.generation == genome.generation`, `bound.master_trunk_hash ==
  genome.master_trunk_hash`;
- для `ffn_replace`: у каждого тензора `skill.{id}.X` есть запись в
  `overrides` с именем X; X — тензор ствола вида `model.layers.N.mlp.*` той
  же формы; при `genome.encoding == "f32"` хэш записи ствола равен
  `base_hash` (после рекванта `base_hash` — хэш мастера, он несравним, и
  проверяются только имя и форма); нет override без тензора; `layers` равно
  множеству слоёв из имён тензоров;
- `state_effect` есть, `first_affected_layer == min(layers)`, `switch` не
  разрешительнее вычисленного;
- для `lookup`: правила §9.5.2 (`lookup` есть, ровно четыре тензора
  таблицы с их dtype/формами, `overrides` пуст, `experts` нет, `layers`
  пуст, `state_effect` прозрачный; значения таблицы проверяются по
  payload); поле `lookup` на записи другого вида — отказ;
- для `expert_append`: правила §9.5.1 (`experts` есть, `overrides` пуст,
  `selection` нет, ровно тензоры раскладки, `switch == sequence_start`);
  поле `experts` на записи другого вида — отказ;
- `status` из перечня; поля v2 на записи без `kind` — отказ; в файлах с
  новыми битами каждый `skill.*`-тензор принадлежит какой-то записи, а id
  уникальны.

`state_effect.switch` вычисляет писатель:
`ffn_replace_state_effect(arch, layers)`. Выход FFN слоя l питает все слои
j > l, поэтому `transparent` возможен тогда и только тогда, когда ни один
слой после `min(layers)` не несёт состояния последовательности (сейчас его
несут все типы слоёв) и стек не зациклен (`num_loops == 1`). Иначе —
`sequence_start`. Для fam-a (якоря 3 и 7, GDN на остальных) только FFN
слоя 7 даёт `transparent`, любой слой < 7 даёт `sequence_start`. Голова
MTP не учитывается: её состояние влияет только на черновики, которые
проверяет основная модель. `state_bytes_added` у `ffn_replace` равен 0.

`resolve_tensor` для v2-навыка: если имя есть в `overrides`, а тензора
`skill.{id}.X` нет, это ошибка (`try_resolve_tensor` → `MissingTensor`,
`resolve_tensor` → `None`), никогда не тихий откат на ствол.
Автомаршрутизация требует `status == "active"` и `gate.status ==
"measured"` (`SkillRecord::is_auto_routable`).

#### 9.5.1 Запись `expert_append` — рост экспертов поверх ствола

Эмбрион выбирает эксперта ВНУТРИ каждого MoE-слоя резонансом (без
gate-тензора, `arch.moe.router_resonance`): эксперт `e` выигрывает токен `x`,
если `bias_e − ‖(x−μ_e) ⊥ U_e‖²` наибольший. Новое знание = НОВЫЕ эксперты,
дописанные записью поверх запечатанного генома; старые тензоры байт-в-байт
те же, `trunk_hash` не меняется (тензоры `skill.*` в ствол не входят).
Запись — часть организма: на запрос она не переключается, роутер
`backbone_gated` (§9.4) её не видит.

```jsonc
{
  "id": "herbs",
  "kind": "expert_append",
  "layers": [4, 5, 6, 7],           // выращенные MoE-слои: любое непустое подмножество
  "experts": {"count": 2,           // новых экспертов в КАЖДОМ слое из layers (≥ 1)
              "shell_quantile": 0.99,  // квантиль ошибок, по которой тренер взял desc.shell
              "rank": 4},           // ранг desc.u == ранг эксперта 0 ствола в каждом слое
  "bound": {"genome_id": "…", "generation": 0, "master_trunk_hash": "…"},
  "state_effect": {"first_affected_layer": 4, "switch": "sequence_start",
                   "state_bytes_added": 0},   // писатель вычисляет сам, если не задано
  "status": "quarantine",
  "origin": {"trigger": "user_corpus", "dataset_sha256": ["…"], "steps": 1200, "…": "…"}
}
```

**Индекс эксперта по слоям** (правило цепочки; в записи не хранится, ридер
вычисляет): для слоя `l` записи на позиции `i` в `header.skills`

```text
base(i, l) = E0 + Σ count(j)  по записям j < i вида expert_append, у которых l ∈ layers(j)
e = base(i, l) + k,  k ∈ 0..count
```

`E0 = genome.moe_experts` (= `arch.moe.num_experts`). Слои вне `layers`
сохраняют своих экспертов. Индексы фиксируются при записи и не двигаются:
статусы `quarantine`/`active`/`stale_regate` цепочку не меняют. Списывать
(`retired`) можно только с ХВОСТА цепочки слоя: живая запись позади
списанной в том же слое — отказ (при `update_header_append` и при
`open()`); когда все более поздние записи слоя списаны, можно списать и
более раннюю; новая запись в слой, чья цепочка кончается списанной, —
отказ. Рантайм монтирует записи в порядке заголовка (по умолчанию только
`active`), поэтому имя тензора — декларация индекса, а не позиция в
исполняемом векторе экспертов.

**Тензоры** — ровно эти, никаких других под `skill.{id}.`; для каждого
`l ∈ layers`, `k ∈ 0..count`, `e = base(i, l) + k`:

| имя `skill.{id}.model.layers.{l}.mlp.experts.{e}.…` | форма | правило |
|---|---|---|
| `gate_proj.weight`, `up_proj.weight`, `down_proj.weight` | как у `experts.0` ствола в слое `l` | любая кодировка §3 |
| `desc.mu` | `[hidden]` | среднее описателя |
| `desc.u` | как у `experts.0.desc.u` ствола (Embryo пишет `[rank, hidden]`) | только при `rank > 0`; у ствола без `desc.u` — `rank = 0`, тензора нет |
| `desc.bias` | `[1]` f32 | конечное значение — балансирующее смещение, замороженное тренером на всё обучение: 0.0 (`bias_mode = zero`, копия перебивает источник) или смещение эксперта-источника ствола (`bias_mode = source`, копия равна источнику при вставке); режим пишется в `origin.bias_mode`; `NaN`/`±inf` — отказ |
| `desc.shell` | `[1]` f32 | конечный порог ошибки реконструкции `‖(x−μ)⊥U‖²`, вне которого эксперт не выигрывает; `+inf`/`NaN` — отказ |

Проверки (`open()` и каждый писатель, до первого байта): `kind`
реализован; `experts` есть; `count ≥ 1`; `shell_quantile ∈ [0, 1]`;
`layers` непустой без повторов, каждый слой — MoE-слой ствола с
пoэкспертными описателями (`experts.0.desc.mu`; стековая форма
`mlp.desc.*` не растится); `rank` равен рангу ствола в каждом слое;
геном — резонансный MoE (`arch.moe.router_resonance`, иначе gate-тензор
фиксирует E); `overrides` пуст; `selection` нет; ни одного лишнего и ни
одного недостающего тензора, формы по таблице, `desc.bias`/`desc.shell` —
f32; значения `bias` и `shell` конечны (ридер читает 4 байта из mmap,
писатели — из переданных payload; потоковый писатель перечитывает с
диска); `state_effect`: `first_affected_layer == min(layers)`, `switch ==
sequence_start`, `state_bytes_added == 0`; `bound` — как у `ffn_replace`.
Порядок проверки записей — порядок `header.skills`, поэтому цепочка
записи `i` опирается на уже проверенные записи `j < i`.

API (`cortiq_core::knowledge`): `ExpertAppend {count, shell_quantile,
rank}`; `SkillRecord.experts: Option<ExpertAppend>`;
`GenomeInfo.moe_experts: Option<usize>`; `skill_kind::EXPERT_APPEND`;
`expert_leaf::{GATE, UP, DOWN, MU, U, BIAS, SHELL, ALL}`;
`expert_tensor_name(layer, e, leaf)`, `expert_append_tensor_name(id,
layer, e, leaf)`; `moe_layers(tensors)`; `genome_moe_experts(header)`;
`trunk_expert_rank(header, tensors, layer)`; `expert_append_base(header,
at, layer)`; `expert_append_layout(header, tensors, at, record) ->
Vec<ExpertTensorSpec {name, shape, layer, expert, leaf}>` (план тензоров:
тренер строит по нему `TensorSpec` с `at = header.skills.len()`,
загрузчик восстанавливает имена смонтированной записи по её позиции);
`expert_append_state_effect(layers)`;
`validate_expert_append_values(header, tensors, f32_of)`.

Гейт (`crates/cortiq-core/tests/expert_append.rs`): запись на все
MoE-слои и на подмножество принимается, индексы по правилу цепочки,
`trunk_hash` и байты префикса равны F0; каждый отказ писателя оставляет
файл нетронутым; подмена `desc.bias`/`desc.shell` на диске — отказ
`open()`; списание только с хвоста; маски меняют `trunk_hash`, рост — нет.

**Исполнение в рантайме** (`cortiq-engine`, `cortiq-cli`):

- Загрузчик (`loader::mount_growth`) после E0 экспертов ствола каждого
  слоя монтирует экспертов записей `expert_append`, объявивших этот слой,
  в порядке `header.skills`; их тензоры берутся по плану
  `expert_append_layout(header, tensors, at, rec)` для позиции записи.
  `arch.moe.num_experts` остаётся E0; `MoeFfn.grown` описывает хвост
  `experts[E0..]` (`GrownExpert {record, record_index, layer, expert}` —
  `expert` = индекс из имени тензора). Одна строка журнала на запись и
  слой. `CMF_GROWTH` = `active` (не задано: только `status == "active"`)
  | `all` (все не списанные — измерение свежей записи в карантине) |
  `off` (ни одной: прямой проход F0). API: `loader::{GrowthMode,
  growth_mode(), mounted_growth_records(header)}`.
- Оболочка: `Resonance.shell: Vec<f32>` (`+inf` у ствола, `desc.shell` у
  выращенного); в `Resonance::scores` эксперт с ошибкой `d² − proj >
  shell[e]` получает `−∞` (строгое `>`; ствол — прежние биты).
  `moe_route` с `−∞`: softmax/sigmoid дают вес 0, top-1 = лучший конечный
  эксперт с ренормированным весом ровно 1.0. `CMF_GROWTH_SHELL=off`
  отключает оболочку для измерения; `pipeline::set_growth_shell(Some(_))`
  — тот же переключатель внутри процесса (`growth-eval --shell`).
- Резидентный wgpu-граф: слово 30 записи слоя = упакованная оболочка
  (`effective_shell`: E значений и сентинел `−∞` после них — в WGSL нет
  литерала бесконечности), ядра `embryo_core_route_finalize` /
  `embryo_chunk_route_finalize` применяют то же правило; отказа графа на
  выращенном файле нет, паритет граф ↔ per-op ≤ 5e-6 в обоих режимах
  оболочки. Оболочка пакуется при сборке графа: после переключения нужен
  новый `Pipeline`.
- Инструменты гейтов: `cortiq growth-eval F1 --prompts-jsonl X
  [--max-tokens 32] [--json] [--indices-out f.json] [--shell on|off|both]
  [--growth active|all|off]` — на промпт (cmf-im-v1, тот же проход, что у
  `dump-logits --tokens N`) счётчики маршрутизации до/после → победы
  выращенных экспертов по слоям, `hit` = хотя бы одна победа; сводка:
  доля хитов, n, верхняя граница Клоппера–Пирсона 95 %, по слоям /
  записям / `src` / `lang`; `--indices-out` — индексы без хита (набор
  shell-on, если считались оба режима); без смонтированной записи
  измерение «пустое» (VACUOUS, ненулевой код выхода). `cortiq
  logits-compare F0.bin F1.bin --only-indices f.json` (JSON-массив или
  объект `growth-eval`) сравнивает только эти записи; G2 = все они
  бит-в-бит. `cortiq genome-verify F0 F1` проходит на выращенном файле.
- **Один путь исполнения для хитов и дампов.** Счётчики побед
  `MoeFfn.stats` инкрементирует хостовый маршрут (`moe_route`); резидентный
  граф выбирает эксперта на устройстве (`embryo_core_route_pick`) и
  счётчиков не отдаёт, поэтому `growth-eval` всегда идёт per-op
  (`mark_graph_refused`, `--path per-op` — единственное допустимое
  значение). Ошибка `d² − proj` в графе — древовидная редукция, на хосте —
  последовательная сумма: паритет ≤ 5e-6 гарантирует близость, а не
  равенство, и токен у границы оболочки (или почти равный лучшему
  стволовому счёту) может выиграть на одном пути и проиграть на другом.
  Отсюда правило: множество no-hit действительно ТОЛЬКО для пути, на
  котором измерено; `dump-logits --path per-op|auto` (по умолчанию
  `per-op`: все полосы через `mark_graph_refused`; `auto` = выбор движка,
  то есть граф там, где он есть — то, что исполняет `serve`) пишет путь,
  режимы `growth`/`shell` и sha256 промптов в сайдкар `<out>.meta.json`;
  `growth-eval --indices-out` пишет `path` в файл индексов;
  `logits-compare` отказывает (ошибка, а не `g2_pass: false`), если два
  дампа записали разные пути или если набор индексов измерен на пути, не
  совпадающем с путём дампа либо неизвестном (дамп без сайдкара).
  **G2 и G3 доказаны только для измеренного пути (per-op)**: для графа
  (`serve`) они — следствие паритета ≤ 5e-6, а не бит-в-бит; выгрузка
  счётчиков побед из графа (`S_SEL` → `MoeFfn.stats`) — отдельная работа,
  после которой `growth-eval --path auto` станет измерением пути `serve`.
  Резонансный роутер per-op выбирает победителя по сырому счёту (первый
  максимум, как `resonance_winner` тренера и `embryo_core_route_pick`
  графа), вес ровно 1.0, минуя softmax: через softmax два счёта ближе
  2⁻²⁵ схлопывались в одну вероятность и побеждал меньший индекс.

#### 9.5.2 Запись `lookup` — явная справочная память под роутером

Десять ветвей роста и SFT ствола показали: геном в 56M параметров не
связывает факты «растение → семейство» параметрически. Запись `lookup`
хранит справочник ЯВНО — таблицей ключ → карточка, дописанной в хвост
запечатанного файла (§9.3). Факты точны по построению, забывания нет по
построению (когда роутер выбирает ствол или ключ не найден, вычисление
сети — тот же объект, что у F0, логиты бит-в-бит), O(1) на запрос
(бинарный поиск по хэшам). Это запись P15: роутер `backbone_gated` (§9.4)
переключает её на запрос, как `ffn_replace`, — но у неё нет ни одного
тензора сети, и `trunk_hash` не меняется (пространство имён `skill.*`).

```jsonc
{
  "id": "herbs",
  "kind": "lookup",
  "lookup": {"entries": 266,           // E ≥ 1 карточек
             "keys": 812,              // K ≥ 1 ключей (синонимы, языки → одна карточка)
             "key_norm": "cmf-key-v2", // нормализация ключей (единственная известная)
             "langs": ["ru", "en"],    // L ≥ 1 языков в порядке слотов, без повторов
             "fields": ["family", "parts", "compounds", "uses",
                        "preparations", "safety", "evidence"],   // справочно
             "policy": "key_first"},   // необязательно: router_and_key (умолчание) | key_first
  "layers": [], "overrides": [],       // сети запись не касается
  "bound": {"genome_id": "…", "generation": 0, "master_trunk_hash": "…"},
  "state_effect": {"first_affected_layer": 0, "switch": "transparent",
                   "state_bytes_added": 0},   // ровно так, иначе отказ
  "status": "quarantine",
  "selection": {/* как у любой записи v2; ставит route-fit */},
  "origin": {"trigger": "user_corpus", "dataset_sha256": ["…"],
             "entries": 266, "keys": 812, "duplicates_dropped": 3}
}
```

**Тензоры** — ровно эти четыре под `skill.{id}.`, сырые типы §3.1:

| имя `skill.{id}.lookup.…` | dtype | форма | содержимое |
|---|---|---|---|
| `keys.hash` | `u64` | `[K]` | hash64 нормализованного ключа, строго по возрастанию (уникальны — рантайм ищет бинарным поиском) |
| `keys.entry` | `u32` | `[K]` | индекс карточки ключа (`< E`), параллельно `keys.hash` |
| `entries.off` | `u64` | `[E·L + 1]` | байтовые смещения в `text`: слот `s = entry·L + lang` — это `text[off[s]..off[s+1]]`; монотонны, все ≤ N |
| `text` | `u8` | `[N]` | UTF-8-блоб; каждый слот — JSON-объект `{"card": "…", "fields": {поле: текст}}` |

**Нормализация ключа `cmf-key-v2`** (`normalize_key`, `KEY_NORM`): NFC
→ комбинирующие знаки (категория M) и невидимые форматные символы
(мягкий перенос U+00AD, ZWSP/ZWNJ/ZWJ, U+200E/F, U+2060–2064, BOM)
отбрасываются, НЕ разрывая слова (у ударения над кириллической гласной
нет прекомпонованной формы — NFC оставляет U+0301 отдельно: `Рома́шка`
→ `ромашка`; `ро­машка` → `ромашка`) → прекомпонованная ЛАТИНСКАЯ буква
(U+00C0–024F, U+1E00–1EFF) теряет диакритику (`Pínus` → `pinus`,
`école` → `ecole`; кириллица сохраняет знаки — `й`, `ё`, `ў` буквы, а не
ударения) → нижний регистр → каждый прочий не-буквенно-цифровой символ
(Unicode) → пробел → схлопнуть пробелы → обрезать. `«Пихта
бальзамическая (Abies balsamea)»` → `пихта бальзамическая abies
balsamea`; `St. John's wort` → `st john s wort`; разложенное `И +
U+0306` и `Й` дают один ключ, `Рома́шка апте́чная` и `ромашка аптечная`
— тоже. Хэш = `hash64` (§8) от UTF-8 нормализованного ключа
(`key_hash`); рантайм нормализует сообщение один раз и хэширует
n-граммы (`normalized_key_hash`). Обе функции живут в `cortiq-core` и
общие для сборщика и рантайма. Новое правило нормализации — новый id
`key_norm`, а не тихое изменение: `cmf-key-v1` (NFC → регистр → всё
не-буквенно-цифровое в пробел; рвал слово на ударении и мягком
переносе, не сворачивал латинскую диакритику) — дорелизное правило, ни
одна таблица под ним не выпущена, ридер отказывает ему с подсказкой
пересобрать. Длина ключа ограничена окном n-грамм рантайма:
`LOOKUP_MAX_NGRAM = 4` слова (`cortiq_engine::lookup::MAX_NGRAM` — то
же число); более длинный ключ сборщик не хранит и отчитывает как
недостижимый.

Проверки (`open()` и каждый писатель, до первого байта): `lookup` есть;
`key_norm == cmf-key-v2`; `policy`, если есть, у ПИСАТЕЛЕЙ
(`append_skill`, `update_header_append`, полная запись; `check_lookup_policies`)
— `router_and_key` или `key_first` (иное — отказ `lookup.policy '…'
(expected router_and_key | key_first)`), а `open()` незнакомое значение
(политика более нового писателя, ручная правка) НЕ отвергает: файл
открывается с предупреждением (`unknown_lookup_policies`), рантайм читает
запись как `router_and_key` — так же, как её прочёл бы ридер до 26.09,
и незнакомая политика не делает нечитаемым весь геном вместе со стволом
(ревью KF-6); `entries ≥ 1`, `keys ≥ 1`; `langs` непустой,
имена непустые и без повторов (то же для `fields`); `experts` нет,
`overrides` пуст, `layers` пуст; под `skill.{id}.` ровно четыре тензора
таблицы (лишний или недостающий — отказ), их dtype и формы по таблице
(`[K]`, `[K]`, `[E·L+1]`, одномерный `text`); `state_effect` равен
`{0, transparent, 0}`; `bound` — как у `ffn_replace`. По payload
(`validate_lookup_values(header, tensors, deep, bytes_of)`, один проход
O(K + N): ридер — из mmap, писатели — из переданных байтов, потоковый
писатель перечитывает с диска): хэши строго возрастают (дубликат и
нарушение порядка — разные сообщения), каждый `keys.entry < E`,
смещения монотонны и не выходят за блоб, блоб целиком — валидный UTF-8
(ошибка называет слот), каждая граница слота — на границе символа,
каждый слот по форме объект (первый непробельный байт `{`, последний
`}`). Полный разбор каждого слота как JSON (`deep = true`) делают
только писатели над тем, что собираются записать; `open()` слоты не
парсит (`deep = false`): рантайм читает карточку лениво и сообщает о
слоте, который не разбирается, в момент запроса, а разбор таблицы в
сотни МБ при каждом открытии файла (`cortiq info`, старт `serve`) стоил
бы секунды и не защищал бы ничего сверх границ. Автомаршрутизация —
как у любой записи v2: `status == active`, `gate.status == measured`,
`selection` есть (`is_auto_routable`).

API (`cortiq_core::knowledge`): `LookupInfo {entries, keys, key_norm,
langs, fields}` + `slots()`, `slot(entry, lang)`;
`SkillRecord.lookup: Option<LookupInfo>`; `skill_kind::LOOKUP`;
`KEY_NORM` (= `KEY_NORM_V2`; `KEY_NORM_V1` — отвергаемый дорелизный
id), `LOOKUP_MAX_NGRAM`; `lookup_leaf::{KEYS_HASH, KEYS_ENTRY,
ENTRIES_OFF, TEXT, ALL}`; `lookup_tensor_name(id, leaf)`;
`normalize_key(&str) -> String`;
`key_hash(&str) -> u64`; `normalized_key_hash(&str) -> u64`;
`lookup_state_effect()`; `read_u64_le` / `read_u32_le` (сырые таблицы);
`lookup_tensors(id, &info, &[(hash, entry)], &[slot_json]) ->
Vec<TensorSpec>` — сборщик четырёх тензоров (сортирует ключи, отказывает
на дубликате хэша, индексе ≥ E, расхождении счётчиков с `info`, слоте не
объекте); `validate_lookup_values(header, tensors, bytes_of)`. Типы
`TensorDtype::{U8 = 6, U32 = 17, U64 = 18}`, `is_raw()`.

**Исполнение в рантайме** (`cortiq_engine::lookup`; `run`,
`probe-utility`, `dump-logits`, `serve`). У записи `lookup` нет своей
дорожки: её обслуживает дорожка ствола — тот же объект `Pipeline`, что у
F0 (`Lanes::lane` в CLI и `SkillRouter::lane` в `serve` отдают ствол для
такой цели; `install_dynamic_routing` записи пропускает). Таблица
(`LookupTable::open(model, id)`) читает три малых тензора в память,
блоб `text` остаётся в отображении файла; `LookupTables` открывает
записи файла по первому обращению. Извлечение ключа из сообщения
(`extract_key`, O(len)): сначала латинская группа в скобках (биномен —
`(Abies balsamea)`, 1..4 слова латинского письма — ASCII плюс латиница
с диакритикой, которую нормализация не сворачивает: `æ`, `ø`, `ß`, `ł`;
у вложенных скобок `(имя (Binomial))` сначала внутренняя группа — текст
после ПОСЛЕДНЕЙ `(` до первой `)`, — затем вся группа), затем сообщение
нормализуется `cmf-key-v2`, и все n-граммы 1..4 слов хэшируются и
ищутся бинарным поиском от самой длинной — побеждает самое длинное
совпадение, при равной длине первое по позиции. До n-грамм пробуется
ещё и биномиал БЕЗ скобок: каждая пара `Genus species` исходного (с
регистром) сообщения — заглавное латинское слово ≥ 3 букв и строчное
≥ 3 букв, допускается дефис (`nux-vomica`); только как точный ключ, род
сам по себе не ключ (`capitalised_binomials`). Затем те же n-граммы СО
СТЕМАМИ (`stem_key`: лёгкий
детерминированный стеммер; русские окончания из фиксированного списка
`RU_SUFFIXES` снимаются по самому длинному, повторно, пока в основе ≥ 3
букв: «тойона» → «тойон», «магнолии лекарственной» → «магнол
лекарственн»; латиница от 5 букв: `ies`→`i`, `es`/`s` при ≥ 4 буквах,
конечное `y`→`i`) ищутся во втором отсортированном индексе стемов
(`StemIndex`). Формат не меняется: файл хранит только хэши, поэтому
индекс стемов строится при открытии из текстов ключей, которые сами
карточки пишут (`recover_key_texts`: n-граммы текста слотов, чей хэш
есть в основном индексе; ключ, которого ни одна карточка не пишет,
стема не имеет); стем двух разных записей — неоднозначен и выброшен.
Однословный стем короче 5 букв не ищется («виды» → «вид», «чая» — никогда
по стему; точные однословные ключи как были). Правило выбора одно для
всех путей (ревью KF-3: выбор φ-роутера, `key_first`, память диалога):
побеждает первый СИЛЬНЫЙ кандидат в этом порядке (скобки → пара с
заглавной → точные n-граммы → стем-n-граммы; `is_strong_key`, ниже), а
без сильного — первый кандидат любой силы, причём слабый стем-кандидат
— только когда точного совпадения не было вовсе. Поэтому
«Как заварить чай из ромашки аптечной?» — это ромашка (двухсловный
стем-ключ) и на пути роутера, и на пути `key_first`, а не «чай»
(однословный точный ключ). СИЛЬНЫЙ ключ: ни одного слова с цифрой
(`sts 135`, `pti 2`, `5f pb 22`) и не меньше `STRONG_KEY_MIN_WORDS = 2`
чисто буквенных слов из ≥ `STRONG_WORD_MIN_LETTERS = 3` букв
(`ромашки аптечной`, `pot marigold`, `st john s wort`; не `thc b`, не
`чай`) — по тексту ключа, из какого бы источника он ни пришёл: любой
точный ключ, найденный парой с заглавной, — это и n-грамма того же
сообщения, так что более строгое правило для пар ничего бы не отсекло
(`Common box` — это и n-грамма `common box`; её снимает только
стоп-лист, см. ниже), а лишь переставило бы кандидатов: на реальном
корпусе «Spring vetchling (Lathyrus vernus (L.) Bernh.)» ушёл бы в
запись-заглушку с биноменом вместо полной записи с народным именем.
Итог несёт `lookup_match` = `exact` | `stem`. Нет ключа — запрос идёт в
ствол без изменений. Язык карточки — по письму вопроса (кириллица →
`ru`, иначе `en`; нет такого языка → `en`, затем первый язык записи);
пустой слот (у записи нет карточки на этом языке — сборщик хранит
`{"card": "", "fields": {}}`) → первый язык записи с текстом; пусто
везде → промах (`Found::EmptyCard`, ствол), а не пустое сообщение
ассистента. Поле — по ключевым словам вопроса, правила в порядке
`family, parts, compounds, safety, evidence, preparations, uses`
(частные раньше `uses`, которое упоминает почти любой вопрос — «safe to
use», «parts used»): `семейств|family → family`; `части|часть|частей|
частям|частях|частью|частями|part(s) → parts` (целые слова: «частуха»
— растение, «часто» — наречие); `веществ|соединен|состав|компонент|
ингредиент|compound|constituent|ingredient|chemical → compounds`;
`противопоказ|безопас|побочн|опасн|ядовит|токсич|contraindic|toxic|
poison|safety|safe|risk(s)|side effect → safety`; `доказ|исследован|
evidence|study|studies|research|clinical|trial(s) → evidence`; `форм|
препарат|дозиров|preparation|dosage|form(s)|dose(s) → preparations`;
`примен|use(s|d)|usage → uses`; короткие латинские слова — только
целиком, стемы — по префиксу слова; поля, которого в карточке нет, или
без совпадения — вся карточка. Режим `LookupMode` (флаг `--lookup-mode
answer|context|off` у `run`/`probe-utility`/`dump-logits`/`serve`,
умолчание — переменная `CMF_LOOKUP_MODE`, иначе `answer`): `answer` —
текст поля (или карточки) и есть ответ, сеть не запускается; `context` —
ствол генерирует из сообщения с приставкой `Справочная карточка /
Reference card:\n{card}\n\n`, где `card` при выбранном поле — выжимка
`{первая фраза карточки}\n{Подпись поля}: {текст поля}`
(`context_excerpt`, `LookupAnswer.card`; вся карточка — в `full_card` и
в приставке, когда поле не выбрано): у генома с окном внимания 128
строка «Семейство: …» в начале карточки на 1000 символов лежала бы за
окном от позиции ответа; `off` — таблица игнорируется. Общий шаг
`resolve_lookup(tables, decision, text, mode) -> (RouteDecision,
LookupOutcome)`: решение `route_request` с целью-записью `lookup`
становится `Answer` / `Context` (цель остаётся, к причине дописывается
ключ и поле), а при `off`, без ключа или с пустой карточкой — цель
`Backbone` с причиной «the backbone runs unchanged» (`Off` / `Miss`);
иная цель — `NotLookup`. В сводке `route` каждой строки `target` — это
дорожка, которая ВЫПОЛНИЛА запрос (после промаха — ствол), а
`decided_target` — запись, которую выбрал роутер (есть у `Off`, `Miss`
и попаданий): по ним считается доля промахов ключа.
В `probe-utility --json` каждая строка несёт `lookup_hit` и в `route`
поля `lookup_hit`, `lookup_key`, `lookup_entry`, `lookup_lang`,
`field`, `lookup_mode`, `lookup_match`, `lookup_turn`; в сводке —
`lookup_mode`, `lookup_hits`. В
`dump-logits` попадание в режиме `answer` записывается кодом маршрута
записи с логитами СТВОЛА на исходном промпте (бит-в-бит с F0 —
сеть не тронута), в режиме `context` — с логитами ствола на промпте с
карточкой; `<out>.meta.json` несёт `lookup_mode`. В `serve` решение на
файле с записью `lookup` принимается ДО рендера промпта (pre-pass):
попадание в `answer` возвращается сообщением ассистента (и потоком из
четырёх SSE-чанков), в `context` карточка приставляется к последнему
сообщению пользователя; `x_cortiq_route` несёт те же поля
`lookup_key`/`field`/…. Память диалога: решение (φ) принимается по
ПОСЛЕДНЕМУ сообщению пользователя, а ключ ищется в нём и, если там его
нет, в предыдущих ходах пользователя назад по времени — всего до
`MEMORY_TURNS = 6` ходов (`resolve_lookup_turns`,
`LookupTable::find_answer_turns`): первый ход с ключом побеждает, поле
и язык — по формулировке последнего сообщения; `lookup_turn` = на
сколько ходов назад найден ключ (0 — в самом сообщении). «Для чего
применяется это растение?» после хода с названием растения отвечает о
нём. `/v1/completions` — тот же путь на одном cmf-im-v1-ходе
пользователя, без памяти; `run`/`probe-utility` — один промпт. Гарантия G2: с примонтированной записью
логиты любого запроса без ключа бит-в-бит равны F0
(`cortiq-engine/tests/lookup_runtime.rs`, `cortiq-cli/tests/lookup_cli.rs`).

**Политика маршрутизации `lookup.policy`** (26.09, аддитивное поле;
нет поля — `router_and_key`, файлы до 26.09 читаются как прежде, поле
не входит в `skills_hash`, калибровка роутера не устаревает):

- `router_and_key` — как описано выше: запрос в таблицу посылает только
  φ-роутер, ключ ищется в том, что он прислал.
- `key_first` — когда роутер выбрал СТВОЛ (ближайший класс — ствол,
  новизна выше θ, запас не побит, контракт промпта), а в ПОСЛЕДНЕМ
  сообщении пользователя есть СИЛЬНЫЙ ключ записи (`is_strong_key`,
  определение выше: ≥ 2 буквенных слов по ≥ 3 букв без цифр — точная или
  стем-n-грамма, латинская группа в скобках, пара с заглавной; поиск
  `find_strong_key` — тот же порядок, что у
  обычного, только сильные кандидаты, и обычный поиск берёт ту же запись,
  если сильный ключ есть), — запрос
  идёт в таблицу: цель — запись, оценки роутера сохраняются, причина
  `key_first: lookup '<id>' takes the request on the strong key … [router
  decision: …]; lookup key … → entry …`, в сводке `decided_by:
  "key_first"`. Однословный ключ (`чай`, `мята`, `календулы`, одиночный
  `(Calendula)`) по-прежнему требует решения роутера. Ключ из прежних
  ходов диалога `key_first` не включает (память служит только решениям
  роутера). Не срабатывает: при `--lookup-mode off`; на закреплённом
  решении (`--route backbone|<id>`, `--skill none|<id>`) — вызывающий
  передаёт `KeyFirstGate` только для решения самого роутера; в
  fail-closed-состоянии роутера, когда он не может выбрать ни один навык
  (ревью KF-4, проверяет сам движок: `router::is_router_v2` и
  `router::no_candidate_reason` — нет `header.router`, нет
  `header.routing`, устаревший `skills_hash` после дописанного без
  `route-fit` навыка, ни одного маршрутизируемого класса; legacy-файл без
  роутера сюда же); на решении в пользу другого навыка; для записи,
  которую роутер сам выбрать не мог (`router::is_routable` при тех же
  `RouteOptions`: `active` + `measured`, либо `include_quarantine`) или
  чей `prompt_contract` не выполняется кадром запроса
  (`enforce_prompt_contract`); на ключе с пустой карточкой. Записи
  перебираются в порядке заголовка, первая ответившая побеждает. Без
  сильного ключа решение роутера не трогается — дорожка ствола
  бит-в-бит F0 (G2).
- Общие фразы, которые одновременно и народные названия растений
  (`running pop` — *Passiflora foetida*, `scrambled eggs` — *Corydalis
  aurea*, `live forever`, `gas plant`, `tree of life`, `rice paper`),
  правилу сильного ключа удовлетворяют: их отсекает только прогон
  собранной таблицы по большому ОБЩЕМУ набору и стоп-лист (ревью KF-1).
  `cortiq lookup-build … --general-prompts general.jsonl
  [--general-stop-out stop.txt]` прогоняет каждый промпт через
  `find_strong_key` рантайма на собранной таблице (стемы и биномены — как
  их строит рантайм) и отчитывает `general_probe {prompts, strong_hits,
  strong_hit_rate, distinct_keys, keys: [{key, via, source, entry, words,
  hits, example, stored_keys}]}`; `--general-stop-out` пишет хранимые
  ключи за этими попаданиями (для стем-попадания — все ключи записи с
  этим стемом) по строке — это вход `--drop-keys` пересборки.
  `--policy key_first` без `--general-prompts` — предупреждение. Записи
  не о растениях (люди, болезни) и записи, у которых все поля «not
  stated», снимаются из корпуса до сборки.
- API (`cortiq_engine::lookup`): `LookupPolicy::{RouterAndKey, KeyFirst}`
  (`parse` — строгий, `of(&LookupInfo)` — незнакомое значение читается
  как `RouterAndKey`, `is_known`, `label`), `DecidedBy::{Router, KeyFirst}`,
  `LookupAnswer.decided_by`, `LookupOutcome::decided_by()`,
  `KeyFirstGate {opts, frame, can_render}`, `resolve_lookup_gated(tables,
  decision, Option<KeyFirstGate>, turns, mode)`,
  `LookupTable::{find_key, find_strong_key, answer_for_key, policy}`,
  `is_strong_key`, `is_strong_key_text`, `STRONG_KEY_MIN_WORDS`,
  `STRONG_WORD_MIN_LETTERS`; `KeyHit.strong`;
  `resolve_lookup`/`resolve_lookup_turns` берут решение как есть.
  Ядро: `LookupInfo.policy: Option<String>`, `LookupInfo::policy_label()`,
  `lookup_policy::{ROUTER_AND_KEY, KEY_FIRST, ALL, DEFAULT}`,
  `unknown_lookup_policies`, `check_lookup_policies`.
- Сводки: строка маршрута несёт `decided_by` (`router` | `key_first`)
  рядом с `decided_target` и `lookup_key_words` при попадании;
  `probe-utility` — `decided_by_counts` (сумма = `lookup_targets`),
  `dump-logits` — `lookup_key_first` и в `<out>.meta.json`
  `key_first_indices` (записи, которые `key_first` забрал у ствола) и
  `key_first_records`; `route_counts`/`decided_counts` считают попадание
  `key_first` записью в обоих.
- Гейты (ревью KF-2). G3: `route-eval` на файле с `key_first`-записью
  принимает решение как `serve` — φ-роутер, затем шаг `key_first`;
  взятие `key_first` — принятие записи (на общем наборе — ложное
  принятие), в сводке `key_first_step: true`, `key_first_records`,
  `decided_by_counts`, `key_first_accepts`, у строки — `decided_by`.
  `--router-only` меряет один φ-роутер (диагностика). `skill-gate
  --status active` для `key_first`-записи принимает только гейт с
  `key_first_step: true`, где `key_first_records` содержит эту запись
  (`gate_covers_key_first`; иначе отказ, `--allow-unmeasured` — с
  предупреждением). G2: `logits-compare` считает `a_backbone_b_key_first`
  — промпты, на которых F0 работал стволом, а F1 ответил таблицей через
  `key_first` (запись `answer` несёт логиты ствола и бит-в-бит равна F0,
  поэтому одно побитовое сравнение этого не видит), и `g2_pass` требует
  0; дамп без `key_first_indices` (старая сборка) — предупреждение.
- CLI: `cortiq lookup-build … --policy key_first` пишет поле при сборке;
  `cortiq lookup-policy <file> --id <id> --policy router_and_key|key_first
  [--keep-gate]` переключает готовый файл одним header-only дописыванием
  с событием родословной `lookup_policy` (таблица, ствол и калибровка не
  меняются; политика, которой запись уже читается, — ничего не
  дописывается, в том числе `router_and_key` на файле без поля).
  Переход АКТИВНОЙ записи на `key_first` ставит ей `stale_regate` (её гейт
  мерили без шага `key_first`), если сохранённый гейт записи уже не
  покрывает `key_first`; `--keep-gate` оставляет `active` с
  предупреждением. Возврат на `router_and_key` статус не меняет:
  принятия `key_first` — надмножество принятий роутера.

**Сборщик и подгонка роутера (`cortiq-cli`, без тренера).**
`cortiq lookup-build <F0> --entries entries.jsonl --id herbs --out F1.cmf
[--langs ru,en] [--name …] [--on-duplicate first|last|error]
[--drop-keys stop.txt] [--probe-prompts herbs-q-train.jsonl
[--suspicious-share 0.02]]`: строки `entries.jsonl` — `{"keys": ["Пихта
бальзамическая", "Abies balsamea", …], "ru": {"card": "…", "fields":
{"family": "…", …}}, "en": {…}}` (каждый объект-значение, кроме `keys`,
— язык; `card` обязателен, `fields` — объект строк). Ключи нормализуются
и хэшируются; повтор ключа внутри записи отбрасывается
(`duplicates_same_entry`); ключ, общий для двух записей
(`duplicates_cross_entry`), — конфликт корпуса: по умолчанию
(`--on-duplicate error`) сборка отказывает и перечисляет пары, `first`
/ `last` явно отдают ключ первой / последней записи по порядку файла
(в объединённом справочнике растение часто лежит дважды, и первая
копия — заглушка «нет данных в источнике»); каждый отброшенный
дубликат перечисляется с `same_entry` и `kept_entry`. Пустой после
нормализации ключ отбрасывается; ключ длиннее `LOOKUP_MAX_NGRAM` = 4
слов рантайм никогда не проверит — он не хранится и перечисляется
(`unreachable_keys`; составные ключи «A; B (syn. C)» надо резать в
корпусе); ключи из стоп-листа `--drop-keys` (по строке, `#` —
комментарий, нормализуются так же) не хранятся (`dropped_by_list`).

рантайма по набору промптов и перечисляет ключи, попавшие в долю
промптов больше `--suspicious-share` (`probe.suspicious_keys`,
предупреждение): родовое слово-ключ (`plant`, `растения`, `species`)
отдало бы свою карточку любому вопросу без имени растения. Слоты
`entry·L + lang`; язык из `--langs`, которого нет у записи, — пустая
карточка (`missing_slots` — счётчик и список `{entry, lang}`); языки вне
`--langs` не хранятся (`ignored_slots`); без `--langs` берутся все языки
записей, отсортированные по имени. Запись дописывается через
`CmfModel::append_skill` в КОПИЮ F0: копия делается под временным
именем рядом с `--out` и переименовывается в него только после удачного
дописывания и проверки `trunk_hash` (у копии снимается бит
только-для-чтения запечатанного генома; отказ удаляет только временный
файл); `--out`, равный базе — тот же путь, жёсткая или символическая
ссылка на неё (сравнение `(dev, ino)`), — отказ до копирования, как и
файл без `header.genome`. `status: quarantine`, `origin {trigger:
user_corpus, dataset_sha256, entries, keys, on_duplicate,
duplicates_*, unreachable_keys, dropped_by_list, missing_slot_list,
probe, …}` (списки в `origin` обрезаны до 100), событие

`cortiq route-fit <F1> --id herbs --skill-prompts herbs-q.jsonl
--general-prompts general-calib.jsonl --phi-layer 5 [--rank 16] [--max
4000] [--margin 0.05] [--target-fpr 0.05]`: φ каждого промпта считает
РАНТАЙМ (`Pipeline::probe_phi_span` + `router::phi_span_ids`,
канонический кадр cmf-im-v1 — `prefix_ids = encode("<|im_start|>user\n")`,
`suffix_ids = encode("<|im_end|>\n<|im_start|>assistant\n")` токенизатора

`router::fit_descriptor` (порт `fit_selection` тренера в `cortiq-engine`:

по 8 отложенных промптов каждого класса ровно путём `route_request`
(`encode_plain` → `phi_span_ids` → `probe_phi_span` → решение по новой
политике и калибровке, карантин в счёт): unit-φ в пределах
`PHI_PARITY_TOL = 1e-5` на компоненту, то же решение, `E_base`/`E_skill`

отчёте). Каждая АКТИВНАЯ запись v2 файла (включая подгоняемую) получает
`status: stale_regate` — её измеренный гейт относился к прежним
дескрипторам и калибровке (как `recalibrate` тренера); список — в
`router_fitted.stale_regate` и в отчёте; повторная активация — через

`router.phi.layer`; смена кадра при других откалиброванных классах —
отказ; `--max` берёт первые N промптов каждого набора; в наборе не
меньше 5. На stdout — JSON со сводкой калибровки (`in_scope_recall` на
отложенных промптах навыка, `false_accept`/`false_accept_upper95` на
отложенных общих, `novelty_theta`, `temperature`, `skills_hash`,
`stale_regate`, `runtime_check`, `phi_backend`, `auto_routable`);
активирует запись по-прежнему `skill-gate --status active` после гейтов.

Сводка `route-eval` — валидный гейт-файл: несёт `status: "measured"` у
настоящего замера и `"vacuous"`, когда ни один навык не мог победить

`phi_backend` / `phi_backend_fitted` в сводку. В сводке `probe-utility`
— `lookup_targets` (решений роутера за запись до переписывания
промаха), `lookup_hits`, `lookup_misses` (ключ не найден → ствол),
`lookup_off`, `decided_counts` (выбор роутера) рядом с `route_counts`
(дорожка, которая выполнила), и `lookup_src_known` /
`lookup_src_matches` — у строк с `src` (имя растения) попадание
проверяется на совпадение записи с той, в которую разрешается `src`
(`route.lookup_src_entry`, `route.lookup_src_match`): доля попаданий
на ПРАВИЛЬНУЮ карточку, а не просто попаданий.

## 10. Шардинг — модель в N файлах

Именование: `{base}-{no:05}-of-{count:05}.cmf` (духовно совместимо с
safetensors). Пользователь открывает ЛЮБОЕ имя; рантайм нормализует к
шарду 1 и подбирает соседей по паттерну.

**Каждый шард — самодостаточный валидный .cmf**: полный конверт, JSON-заголовок,
каталог СВОИХ тензоров, свой блоб данных, свои хэши
(`section_hashes` + по-тензорные). `cortiq verify` работает на любом отдельном
шарде без его соседей.

Заголовок каждого шарда несёт:

```json
"shard": { "no": 1, "count": 5 }
```

Нет блока = обычный одиночный файл (обратно совместимо: старые ридеры видят
шард 1 как валидную, но неполную модель и честно падают на отсутствующем
тензоре).

**Распределение содержимого**: тензоры разбиваются жадно в каноническом порядке
(порог `--shard-max-gb`, грубый размер f32); секции масок/словаря/разреженного
индекса, `tokenizer_config` (chat-бандл) и реестр `skills`
живут ТОЛЬКО в шарде 1 — у остальных секции пустые и
`tokenizer_config: null`. Тензоры скиллов (`skill.{id}.*`) распределяются
как обычные записи каталога — реестр шарда 1 ссылается на них по
имени через объединённый каталог.

**Загрузка** (`CmfModel::open_sharded`): открыть шард 1 → mmap всех соседей
→ слияние каталогов (каждая запись помнит свой индекс шарда — рантайм-поле,
никогда не пишется на диск) → рантайм далее работает как с одним
файлом. Ошибки: прямое открытие не-первого шарда, отсутствующий сосед,
несовпадение `count`.

Ворота (Qwen3.5-0.8B q8_2f, 5 шардов ≤ 0.6 GB): шардированная PPL ==
нешардированной байт-в-байт на том же бинарнике; `verify` зелёный на каждом шарде
по отдельности.

## 11. Дефрагментация — физический прунинг (USPTO App. 19/452,464, claims 9/10 — [PATENTS.md](../PATENTS.md))

Маска (§5) — это **виртуальная разреженность**: вырезанные нейроны
помечены, но хранятся целиком (все задачи делят один бэкбон — резать
физически нельзя, пока не выбрана ОДНА задача). Дефрагментация
превращает виртуальную разреженность в **физическое сжатие**: мёртвые
FFN-нейроны выбрасываются из файла — они **не хранятся и не
вычисляются**.

**Представление — без нового фичебита, обратная совместимость.**
Физический прунинг выражается ТОЛЬКО меньшими формами тензоров в
каталоге (§3 «нет вычислимой раскладки»; каталог — единственный
авторитет форм). Рантайм выводит размер FFN из формы тензора
(`gate_proj.rows()`), а не из `arch.intermediate_size`, поэтому
дефрагированный файл — обычная меньшая dense-модель, которую
существующие ридеры грузят без изменений. Секция масок в
дефрагированном файле **отсутствует** (после прунинга маска —
тождество). `arch.intermediate_size` становится номиналом (= максимум
по слоям); истинный размер живёт в каждом тензоре — и каждый слой
сжимается до СВОЕГО числа живых нейронов (лучше патента, который обязан
резать все слои под `max(active)`).

**Инварианты (обязательные):** тройка слоя `gate_proj.rows() ==
up_proj.rows() == down_proj.cols() == inter'ₗ` и `down_proj.rows() ==
hidden_size`; ось нейронов — строки для `gate/up`, столбцы для `down`;
квант-группа 32: `down_proj` с `inter' % 32 ≠ 0` пишется как `q8_2f`
(конвертер даунгрейдит сам); это НЕ байтовое усечение — деквант → выбор
живых → **переквант** в меньшей форме, хэши пересчитываются;
`hidden_size`, эмбеддинги, `lm_head` и нормы не трогаются.

**Одна задача — автономный файл.** Дефраг деструктивен: один `.cmf`
запекает ровно одну задачу. Мульти-задачность остаётся на масках (§5)
или скиллах (§9). Провенанс — честный контракт в
`provenance.defrag {source_skill, pre_intermediate,
post_intermediate_max, kept_per_layer, pruned_ratio}`.

Производство (нативный Rust): `cortiq convert --model … --defrag
<skill_dir> --quant q8_2f --output model.cmf`.

**Охват:** здесь — dense-FFN-нейроны; MoE-эксперты — в §11.1. Прунинг
голов внимания вне охвата.

### 11.1 MoE-дефраг экспертов (`cortiq moe-defrag`)

MoE-близнец §11, управляемый B-полем роутинга вместо нейронной маски:
использование экспертов сильно задачно (замерено на кодере 34.7B:
top-64 наборы экспертов для кода и прозы пересекаются с Jaccard 0.25),
поэтому однозадачный файл может выбросить экспертов, к которым задача
не маршрутизирует. Из дампа `CMF_MOE_STATS` (пер-слойные счётчики
выбора экспертов на репрезентативном прогоне) для каждого слоя
сохраняется минимальный top-набор, покрывающий `--cover` записанной
массы роутинга; остальные выбрасываются.

**Представление — та же философия, без фичебита.**

- Оставленные эксперты перенумеровываются в ПЛОТНЫЙ пер-слойный префикс
  `mlp.experts.0 … mlp.experts.{k−1}` с сохранением относительного
  порядка; ридер перечисляет экспертов слоя по НАЛИЧИЮ тензоров до
  `arch.moe.num_experts`, который становится номиналом (= исходное
  число) — зеркально правилу §11 для `intermediate_size`.
- Строки роутера собираются в соответствие в том же порядке:
  `mlp.gate.weight` становится `[kept_l, hidden]`, и
  `router.rows() == (число присутствующих экспертов)` — инвариант
  загрузки. `top_k` клампится к пер-слойному числу экспертов.
- Семантика выбора не меняется (§2.2): softmax просто ренормализуется
  по оставшимся. То же ограничение применимо В РАНТАЙМЕ без перезаписи
  файла (`CMF_MOE_MASK=<stats.json>` + `CMF_MOE_MASK_COVER`) —
  математически идентично, так cover-уровень гейтится перплексией до
  физического выброса.
- Payload'ы экспертов копируются дословно (переквант не нужен — ось
  экспертов режет целые тензоры, не квант-группы), выжившие веса
  байт-в-байт равны исходным, перезапись стримится из mmap источника.

Замеренный референс (KAT-Coder 34.7B-A3B, кодовая калибровка, cover
0.95): 19.6 → 12.7 ГБ (−35%), ppl held-out кода +2.8%, а на машине с
24 ГБ — где полная модель пейджилась — декод ×1.8, префилл ×3.3.

Вне задачи качество падает по построению; как и в §11, один
дефрагированный файл запекает одну задачу.

## 12. Pipeline-контейнеры — text-to-image в одном файле

Та же машинерия конверт/каталог/блоб несёт не-LLM конвейеры. Отличия —
только тег `arch_name` и неймспейсы имён тензоров; ни новых секций, ни
фичебита (ридер, не исполняющий конвейер, всё равно валидирует и
инспектирует файл).

Текущий экземпляр — `arch_name: "lumina2-image"` (Lumina-Image 2.0,
`cortiq imagine-pack` / `cortiq imagine`): один файл содержит весь
text-to-image стек.

- **Неймспейсы**: `te.*` — трансформер текст-энкодера (LLM класса
  Gemma-2; блок `arch` заголовка описывает ИМЕННО эту компоненту, так
  что общие инструменты читают осмысленные размерности), `dit.*` —
  денойзер Next-DiT, `vae.*` — VAE-декодер. Config-JSON'ы компонент
  едут u8-тензорами `{prefix}.config_json` — файл самодостаточен.
- **Квантование**: пер-тензорное как всегда (§3, каталог — истина) —
  обычно q4t/q8 матрицы для te/dit, f16 для свёрток VAE и норм.
- **Секция токенизатора** (§6) несёт токенизатор текст-энкодера;
  `provenance.pipeline` + `provenance.components` называют рецепт.
